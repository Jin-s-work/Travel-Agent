# Travel Agent V3 — 도시·날짜부터 시작하는 간편 여행 준비

작성: 2026-10-06 · 상태: 실행 가능한 제품 설계. 아래 ‘현재 반영’과 ‘후속 구현’을 구분한다.
대상: 본인과 초대받은 최대 5명 내외. 기존 Render Free + Supabase Free 재사용. 새 결제/유료 API 활성화는 범위 밖이다.

## 1. 이번 개편의 결과

사용자는 여행 도시와 날짜를 입력하고 바로 탐색한다. 숙소가 있으면 한 번 선택해 주변 음식점을 찾고, 마음에 드는 곳을 저장해 일정에 넣는다. 여행 이름, 시간대, 위경도, 같은 인원·날짜의 반복 입력이 시작을 가로막지 않는다. 예약 메일 없이도 사용할 수 있다.

**기본 경로:** 도시·기간 → 선택적으로 숙소 연결 → 추천/장소 저장 → 하루 일정.

**숙소가 없는 경로:** 도시·기간 → 기준점 없이 취향 탐색 → 장소 저장. 거리·도보시간은 미확인으로 표시한다.

**추천 자료가 없는 경로:** 도시·기간 → ‘이 도시의 추천 자료를 준비 중’ → 지도/공식 링크·장소명 저장 → 수동 예약·일정 준비. 다른 도시의 결과나 합성 카드를 끼워 넣지 않는다.

## 2. 확인한 문제와 원인

‘방문일에 해당 도시 체류 구간이 없습니다’는 단순 문구 문제가 아니다. 여행은 Madrid로 등록할 수 있지만 탐색은 Tokyo/Barcelona만 고르는 모델이었고, 도시를 바꿔도 방문일은 이전 도시 날짜로 남았다. 같은 Europe/Madrid 시간대라고 Madrid와 Barcelona를 같은 도시로 처리하면 안 된다. 저장한 조건도 여행 수정 뒤 체류일 검증을 다시 받아야 한다.

기존 거리 계산은 숙소 이름이 아닌 위경도가 있어야 작동한다. 숙소 이름만 입력한 사용자가 거리 추천이 된 것으로 오해하지 않도록 좌표 확인 상태를 분리한다. 지금의 계산은 Haversine 직선거리이며 실제 도보 경로/소요시간이 아니다.

| Before | After | Why |
|---|---|---|
|여행 생성에 이름·도시·시간대·여행일·도시별 날짜를 한꺼번에 요구|도시·여행 기간을 먼저 입력, 이름 자동 제안, 시간대 자동 적용|같은 정보를 두 번 입력하지 않음|
|탐색에서 도시·방문일·인원 재입력|현재 여행·도시 구간을 물려받고 요약 칩에서 필요한 값만 수정|준비 단계가 탐색을 막지 않음|
|‘도시 체류 구간 없음’ 일반 오류|정확한 체류일 선택 및 도시/자료 지원 상태별 안내|입력을 고칠 일과 공급 자료가 없는 일을 구분|
|숙소 이름과 위경도를 따로 입력|숙소 이름/지도 링크 하나로 후보 확인, 좌표 직접 입력은 고급 도구|사용자가 지리 좌표를 몰라도 됨|
|조건 저장 → 닫기 → 추천 요청|한 행동 ‘추천 보기’, 서버에서 입력 snapshot 확정|저장 버튼의 내부 순서를 사용자가 기억하지 않음|
|날짜 연도에 6자리 입력 가능|달력 유지, 연도 0001~9999와 실제 날짜 검증|오입력이 서버 오류로 넘어가지 않음|
|10개 기능을 같은 우선순위로 표시|홈·탐색·일정·예약 4개 주요 경로, 부가 기능은 맥락/더보기|사용자가 지금 할 행동을 찾기 쉬움|
|기술 버전/작업 상태가 소비자 본문을 차지|작업 실패만 다음 행동과 함께 표시, 세부 기록은 펼치기|중요한 미확인과 방문 정보를 먼저 읽음|

## 3. 현재 반영한 범위와 후속 구현

현재 코드 반영: 공통 100개 도시 등록부, 도시 별칭/시간대/통화, 여행 도시 자동 시간대, 간소화한 여행 폼, 탐색 체류일 자동 제안, 오래된 조건의 서버 차단, 날짜 입력의 네 자리 연도 범위, 합성 메일 12개와 다운로드. 정확한 시험/배포 결과는 `IMPLEMENTATION_STATUS.md`에 남긴다.

1단계 구현 완료(2026-10-06): 전체 메뉴 재편, 검색형 도시 선택기, 단일 탐색 행동 API, 여행 조건 상속/override, 빠른 날짜 선택, 빈 결과 회복과 시작부터 저장까지 E2E. [실제 검증·제약](reports/stage1-validation.md), [schema11 이관](MIGRATION_11.md)을 함께 확인한다. 운영 revision은 진행 기록을 따른다.

후속 2단계: 구조화된 숙소와 지점 확인, 숙박일에 따른 출발점, 숙소 주변 거리 추천, 선택적으로 실제 경로 제공자, 일정의 양쪽 이동 검증, 통합 카드/지도 링크/비교.

숙소 자동 위치 확인·실제 도보시간·100개 도시의 실제 추천 데이터 확보는 현재 완료 기능으로 보고하지 않는다.

## 4. 도시 범위: 100개를 실제로 다루는 방식

등록부: `src/destinations/cities.json`, 버전 `world-100-v1`. [도시 목록](CITY_COVERAGE.md)을 함께 관리한다. 한국어/영문/등록한 현지어 별칭으로 같은 도시 ID에 연결한다. 국가 코드와 IANA timezone, 기본 통화를 보존한다. 도시 중심점을 숙소 좌표로 쓰지 않는다. 지명 모호성은 도시+국가로 해소하고 공항·섬·광역 지역을 임의의 도시로 치환하지 않는다.

도시 지원 상태는 다음 기능별로 나눈다.

|기능|기본 지원|준비 조건|
|---|---|---|
|여행 생성·예약 저장·날짜 질문|등록 100도시, 목록 밖 수동 도시도 기존 흐름 유지|유효한 날짜·IANA timezone|
|탐색 조건·개인 장소 저장|100도시|여행의 해당 체류일, 소유권 검증|
|출처 기반 장소 추천|도시별 `no_live_candidates / limited_catalog`|실제 지점·표시권한·필드 근거 검수|
|숙소 주변 직선거리|좌표 확보 후|숙소 지점과 후보 좌표 정확성|
|도보 경로/시간|공급자별 OFF/available/degraded|공급자 설정·이용 범위·예산·응답 검증|
|엄격 리뷰 언어|도시별 별도 OFF|현지어 집합 검토, 실제 언어 평가, 이용권한·관측 품질|

현재 운영 자료는 도쿄·바르셀로나 포함 검수된 실후보가 없는 상태다. 100개 도시 ‘등록’과 100개 도시 ‘맛집 추천 완성’을 합산하지 않는다. 도시 신규 등록만으로 리뷰 언어, 영업, 아동 허용, 예약 인원, 경로 신뢰도를 활성화하지 않는다. 서울의 한국어 리뷰 비율을 ‘한국인 관광객 적음’으로 해석하지 않는다. 다언어 도시도 도시별 검토 전 strict 기능을 꺼 둔다.

시간대는 고정 UTC 오프셋 대신 IANA ID로 계산한다. 규칙은 변경될 수 있으므로 배포 tzdata 버전을 기록하고 업데이트 시험을 한다. [IANA 공식 설명](https://www.iana.org/time-zones).

## 5. 정보 구조와 화면 흐름

### 5.1 주요 메뉴

- **홈:** 선택 여행 요약, 오늘/다음 일정, 준비가 필요한 항목 1~3개, 숙소 설정과 예약 추가.
- **탐색:** 현지 탐색/대표 명소, 음식점/카페/볼거리, 저장한 장소 탭. 저장한 장소는 별도 메뉴를 강제하지 않는다.
- **일정:** 날짜별 타임라인, 후보 넣기, preview/apply/undo. 오늘 보기는 현재 날짜에 자동 진입하는 동일 화면의 보기 방식.
- **예약:** 메일 업로드와 직접 입력, 예약 확인·교정, 예약 준비 할 일. 실제 예약과 ‘예약해야 할 일’은 상태를 섞지 않는다.
- **더보기:** 여행 질문, 기록·예상 지출, 오프라인, 설정. 기존 기능 URL/딥링크를 유지한다. 관리자 검수는 역할별 별도 입구.

현재 여행·기간·도시는 모든 주요 화면 상단에서 보인다. 사용자에게 매번 여행을 다시 고르게 하지 않는다. 여행 전환은 한 번에 완료하고 이전 여행의 늦은 응답/모달/비교 목록이 섞이지 않는다.

### 5.2 첫 여행 생성

상단 질문은 ‘어디로, 언제 떠나나요?’ 하나. 도시 검색 → 시작/종료 날짜 → 생성. 기본 성인 1명은 요약으로 보여 수정 가능하게 한다. 이름은 ‘마드리드 여행’ 등으로 제안하고 편집은 선택. 숙소는 생성 전에 강요하지 않는다.

다중 도시는 ‘도시 추가’를 누른 뒤에만 구간 날짜를 묻는다. 한 도시이면 체류일=전체 여행일을 상속한다. 여러 도시 사이 공백/겹침이 있으면 어떤 구간인지 보여주되 예약 원본을 이동시키지 않는다. 자동 제안과 사용자 확정은 구분한다.

아동/식단/이동 지원은 필요할 때 추가한다. 아동이 있다고 선택한 경우에만 인원/나이를 묻고 모르면 미확인을 허용한다. 아동 없음으로 확인한 것과 아직 질문하지 않은 상태를 데이터에서 구분한다. 기왕 저장한 조건은 이동 화면마다 다시 묻지 않는다.

### 5.3 날짜 공통 계약

저장 형식 `YYYY-MM-DD`, 연도 4자리 0001~9999. 0000은 유효한 연도가 아니다. 6자리 연도를 자르거나 올해로 바꾸지 말고 입력 단계에서 범위를 제한하고 잘못된 전체 날짜를 필드 옆에 알린다. 달력 선택·타이핑·붙여넣기·키보드 이동을 모두 시험한다. 단순 maxlength는 native date 입력의 해결책이 아니다.

처음 입력은 여행 날짜 범위 선택, 탐색은 날짜 칩으로 이동한다. 짧은 여행은 전 날짜, 긴 여행은 주 단위/달력 전환을 제공하고 임의로 뒤 날짜를 버리지 않는다. 도시를 바꾸면 해당 구간 안의 날짜를 유지하거나 첫 유효일을 제안하며 ‘체류일로 맞췄어요’를 표시한다. 왕복 재방문 구간 사이 공백은 선택 불가/명확한 오류다. 기기 timezone으로 하루가 밀리지 않는다.

종료일이 앞서면 종료 필드에서 수정한다. 실패/409에서 입력을 보존한다. 날짜만 있는 예약에 00:00을 생성하지 않는다. DST 중복/없는 시간은 기존 validator로 확인한다.

## 6. 입력 상속과 단일 탐색 행동

원본은 여행/도시 구간, 임시 변경은 화면 draft, 확정 요청은 immutable snapshot이다. `trip_version`, `stop_id`, `conditions_version`, `origin_version`, 정책/알고리즘 버전을 연결한다.

- 여행의 도시·날짜·일행은 기본값. 사용자가 ‘이 식사는 2명만’으로 바꾸면 해당 방문 조건 override이며 여행 전체 인원을 바꾸지 않는다.
- 값마다 `origin=trip_default / booking / user_override / planning_default / unknown`을 갖고 상속 해제/원복이 가능해야 한다.
- 저장한 override는 여행 수정으로 조용히 삭제하지 않는다. 유효하지 않은 값만 변경 이유와 함께 재확인.
- 탐색 화면 기본 입력은 날짜 칩, 장소 분류, 추천 관점, 인원 요약. 예산/식사창/반경/식단/이동/엄격 리뷰는 ‘필터’에 넣는다. 중요한 필수 조건은 요약 칩에 계속 보인다.
- ‘추천 보기’ 한 번으로 조건 snapshot과 durable job을 연결한다. 조건만 저장되고 job 접수가 실패했다면 다음 행동은 기존 intent 재시도다. 동일 Idempotency-Key+payload는 같은 결과, 다른 payload는409.
- 아직 저장하지 않은 필터가 있어도 이전 결과를 숨기지 않는다. ‘이전 조건 결과’와 ‘새 조건 적용’을 표시한다. draft를 저장된 결과의 근거처럼 표시하지 않는다.
- 필터 변경/키 입력/카드 열기마다 리뷰 수집, 지오코딩, 경로 호출을 수행하지 않는다.

## 7. 숙소와 출발 기준점

### 7.1 숙소를 한 번만 입력

숙소는 예약 메일의 숙박 예약에서 연결하거나 ‘숙소 이름 또는 지도 링크’ 한 필드로 추가한다. 이름 검색과 지점 확인은 다른 상태다. 사용자가 동일 상호 지점 후보에서 이름·주소·지도 링크를 확인해야 한다. 자동으로 가장 유명한 지점/도시 중심/0,0을 선택하지 않는다.

상태: `unresolved / candidates / confirmed / needs_reconfirmation / unavailable`. 저장 자체는 항상 가능한 범위에서 완료하고 위치 미확인만 표시한다. 사용자 입력 주소/메모는 개인 데이터이고 공용 장소팩에 섞지 않는다. 지도 페이지를 무제한 크롤링하거나 메일 속 링크를 자동 fetch하지 않는다. URL은 기존 SSRF 보호와 공개 호스트/redirect/MIME/크기/시간 상한을 통과해야 한다.

### 7.2 숙박과 기준점 모델

개인 `trip_accommodations`: 서버 ID, owner/trip/stop 참조, 표시명, 지점/공급자 ID, 확인 주소/좌표/확인 상태, timezone, checkin_date, checkout_date, 선택 시각, booking 참조, version, 출처·확인일. 숙박 날짜는 `[checkin, checkout)`로 관리한다. 기존 trip_stop.base_location은 label-only 미확인 숙소 후보로 이관하며 좌표를 만들어 넣지 않는다.

`origin_choice`: 방문일, 선택 숙소/다른 출발점, 오전/오후 맥락, version, 사용자 override. 체크아웃 당일 낮 일정의 출발점은 전날 숙소로 제안할 수 있지만 그 숙소에 그날 투숙 중이라고 표시하지 않는다. 숙소가 겹치면 선택이 필요하고, 공백일은 미확인이다. 체크인 전 짐 보관/조기 입실은 따로 확인한다.

항공 도착이 있어도 호텔 도착을 확정하지 않는다. 사용자의 정확한 실시간 위치는 기본 필수 아님. ‘숙소 기준 / 선택 지점 기준 / 현재 위치 기준’을 구분하며 위치 권한 거절에도 전체 화면을 유지한다.

## 8. 숙소 기준 음식점 추천

후보 구성 → 지점 확인 → 필수 조건 → 근거 자격 → 숙소/일정 이동 계산 → 점수 → 다양성 → 설명 순서. 숙소와 같은 도시에 있다는 이유만으로 가깝다고 표현하지 않는다.

### 8.1 거리의 의미

|상태|카드 표현|배치/필터 처리|
|---|---|---|
|좌표 없음|거리 미확인 · 숙소 위치 확인|거리 필수 조건은 unknown|
|좌표 있고 경로 없음|숙소에서 직선거리 850m · 도보시간 미확인|직선 반경 필터에만 사용|
|provider 도보 경로 있음|숙소에서 도보 약12분 · 경로850m · 확인일|해당 모드/출발 기준에만 사용|
|오래된/실패 경로|이동시간 재확인 필요|0분 대체 금지|

기본 무료 버전은 검증 좌표 기반 직선거리로 충분히 정직하게 시작한다. 직선거리/보행 속도 나눗셈을 실제 도보시간으로 표시하지 않는다. ‘도보15분 이내’가 필수이면 유효 경로 없는 후보는 통과하지 않는다. 선호이면 ‘이동 미확인’ 별도 묶음으로 둘 수 있지만 충족 후보보다 유리하게 점수 주지 않는다.

왕복/경유는 방향을 구분한다. 숙소→음식점과 음식점→다음 예약을 모두 계산한다. 강·다리·도로·계단·대중교통 대기 때문에 직선거리와 경로는 달라진다. 사용자가 선택한 이동 수단에 맞는 결과만 비교한다.

### 8.2 제공자·캐시·비용

`GeocodingProvider`와 `RouteProvider`를 교체 가능한 인터페이스로 둔다. fake / disabled / 실제 공급자 어댑터를 구분한다. 지점 확인 요청은 명시 검색 버튼으로, 경로 matrix는 이미 좁힌 후보에만. 공급자 호출은 기존 budget/job wrapper로 예약·정산한다. 0원 설정에서는 유료 요청 자체를 만들지 않는다.

캐시 키: 출발 지점+버전, 도착 지점+버전, 방향, mode, 날짜/출발시각 bucket, 인원/접근성 영향 조건, provider/version. 이용 약관에 맞는 TTL·표시권한을 확인한다. 개인 숙소 좌표를 공용 로그/분석 이벤트에 남기지 않는다. 실패/취소/응답불명 과금 처리는 기존 계약 유지.

Google Routes의 matrix는 출발/도착 쌍별 거리와 시간, 개별 오류를 반환하므로 요청 전체 성공과 모든 구간 성공을 구분한다. 실제 상한/단가는 활성화 시 재확인한다. [공식 Routes matrix](https://developers.google.com/maps/documentation/routes/compute_route_matrix).

공용 Nominatim은 무제한 무료 주소검색 서버가 아니다. 현재 정책은 앱 전체 최대1요청/초, 식별/출처 표기, 자동완성 금지, 개인·기밀 데이터 전송 금지 등을 요구한다. 기본값으로 내장하거나 숙소/주소를 자동 전송하지 않는다. 사용한다면 담당자가 용도를 검토하고 명시적으로 공급자를 선택한 경우에만 규정을 적용한다. [공식 사용 정책](https://operations.osmfoundation.org/policies/nominatim/).

### 8.3 추천 점수와 결과

기존 local_editorial_v1/iconic_v1/local_observed_v1 가중치는 임의로 변경하지 않는다. 거리 성분 변경은 새 version으로 계산·비교한다. 비교 실험에서는 조건/후보/사실/clock을 고정한다. 필요한 성분이 없으면 null/자료 부족이며 다른 가중치로 몰래 분배하지 않는다.

‘숙소 근처 저녁’ 빠른 버튼은 저녁 선호와 숙소 기준점을 draft로 채워준다. 평점·리뷰 품질·인원·식단의 필수 조건을 풀지 않는다. 후보가2개면2개만 보여주고 이유를 설명한다. 현지 탐색과 대표 명소는 별도 구획, 음식점/카페/볼거리는 독립 필터를 유지한다.

카드: 이름/원어명, 추천 이유 최대3개, 숙소 기준 거리와 종류, 가격의 인원/통화 기준, 운영/예약의 중요한 미확인, 확인일, 상세/저장. 비교/관심 없음은 보조 행동. 총좌석/예약 링크를 오늘2명 잔여석으로 바꾸지 않는다.

## 9. 일정으로 연결

저장한 장소에서 ‘일정에 넣기’ → 날짜 제안 → preview → 적용. 체류시간은 유형별 planning_default임을 표시하고 수정 가능. 고정 예약·잠금·식사창·경로 양쪽·휴무·마지막 입장·아동/인원 조건을 기존 validator로 검사한다. 미확인은 엄격 모드에서 미배치, 사용자가 선택한 잠정 초안에서만 provisional이다.

화면 단계를 줄이기 위해 preview와 적용을 한 모달에 둘 수 있지만 서버 검증 경계를 없애지 않는다. 적용 직전 version/소유권/삭제/근거 신선도를 재확인한다.409에서 원 일정과 입력을 보존하고 차이를 보여준다. undo는 현재 조건을 검증한 새 revision이다. 일정 제거는 외부 예약 취소가 아니다.

## 10. 오류·성능·접근성 계약

- 입력 오류: 해당 필드 옆, 입력 유지, 첫 오류로 포커스, 접힌 필드는 자동 펼치기.
- 도시 등록 없음/자료 없음/필수 조건 불충족/자료 부족/공급자 장애/예산0/세션 만료를 별도 상태와 CTA로 표시.
- 세션 만료 시 개인 데이터/오프라인 namespace 정리, 로그인 복귀. 인증을 우회해 계속 탐색시키지 않음.
- 409는 재시도 무한 루프가 아닌 최신 상태 비교. 5xx/타임아웃은 기존 결과 유지, idempotent 재개.
- 로딩은 실제 단계/건수. 무료 호스팅 최초 기동 지연을 가짜 진행률로 숨기지 않음.
- 도시 검색은 로컬100개 metadata로 즉시 필터. 공용 도시 정보를 못 읽어도 기존 예약 조회를 막지 않음.
- 320/390/1280px, 글자200%, 긴 한국어·일본어·스페인어명, 키보드, 모달 포커스, reduced motion을 검증.
- 조작 목표 최소44px, 색만으로 상태를 구분하지 않음. `transition: all`과 상시 장식 모션 금지. 빈 카드보다 다음 행동을 보여줌.
- 일반 개인 API는 service worker 캐시 금지. public asset hashes와 shell 버전 갱신. 개인정보는 브라우저 로그·분석 이벤트에 넣지 않음.
