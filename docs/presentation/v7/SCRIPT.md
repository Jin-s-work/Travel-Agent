## 1. 고잉

*제목을 보여주며 개인적인 계기부터 말합니다.*

안녕하세요. 제가 만든 여행 서비스, 고잉을 소개하겠습니다.

저는 여행하는 것도 좋아하고 새로운 음식점을 찾아다니는 것도 좋아합니다. 그런데 여행을 갈 때마다 식당을 검색하고, 리뷰를 읽고, 숙소에서 얼마나 먼지 비교하는 과정이 꽤 번거로웠습니다. 예약을 해 놓고도 시간을 확인하려고 메일함을 다시 찾아야 했고요.

그래서 제가 여행을 준비할 때 직접 쓰고 싶은 서비스를 만들어 봤습니다. 오늘은 어떤 불편함에서 시작했고, 그걸 어떤 기능으로 해결하려 했는지 보여드리겠습니다.

## 2. 여행할 때마다 다시 찾는 정보

*식당을 고르는 질문과 예약을 확인하는 질문을 차례로 짚습니다.*

예를 들어 도쿄 여행을 간다고 하면, 먼저 어디에서 밥을 먹을지 검색합니다. 한국어로 많이 소개된 곳도 좋지만, 현지어 리뷰가 많은 다른 식당도 찾아보고 싶었습니다. 그러다 마음에 드는 곳을 찾으면 이번에는 숙소와의 거리, 영업시간, 예약 방법을 따로 확인해야 했습니다.

이미 예약한 항공권이나 호텔 정보는 메일에 있고, 가고 싶은 장소는 지도에 있고, 하루 일정은 메모에 있었습니다. 정보를 하나씩 찾는 것보다 그걸 서로 맞춰 보는 과정이 더 번거로웠습니다.

그래서 고잉은 여행 하나 안에서 예약과 장소, 일정을 이어서 볼 수 있게 기획했습니다.

## 3. 추천과 질문을 메인에서

*홈의 추천 카드와 바로 아래 AI 질문 입력창을 차례로 짚습니다.*

사용할 때는 도시와 날짜로 여행을 하나 만듭니다. 그다음에는 같은 정보를 매번 입력하지 않아도 됩니다. 숙소나 음식 취향은 필요할 때 추가하면 됩니다.

기능을 늘리다 보니 오히려 어디서 시작해야 할지 알기 어려워진 적이 있었습니다. 그래서 가장 많이 쓰는 추천과 AI 질문을 메인으로 꺼냈습니다. 최근 살펴본 장소 세 곳에서 상세를 보거나 바로 저장하고, 아래에서는 예약에 대해 물어볼 수 있습니다.

추천을 기다리다가 다른 화면으로 가도 진행 상태가 이어집니다. 여행을 바꿀 때도 보고 있던 메뉴를 유지하도록 고쳤습니다. 화면은 배포된 서비스에 넣은 가상 도쿄 여행입니다.

## 4. 메일을 예약으로 정리하기

*호텔의 체크인·체크아웃 시간과 확인 필요 상태를 짚습니다.*

가장 먼저 만든 기능은 예약 메일 분석이었습니다. 항공권이나 숙소 확인 메일을 올리면 날짜, 시간, 장소 같은 내용을 예약으로 정리합니다. 한 메일에 여러 예약이 있거나 왕복 항공편이 들어 있는 경우도 구분해서 보관합니다.

이때 AI가 읽은 내용을 바로 확정된 사실로 취급하지는 않습니다. 사용자가 확인하고 잘못된 값을 수정할 수 있게 했습니다. 사용자가 고친 값은 원래 추출한 값과 따로 저장해서 다시 분석해도 사라지지 않도록 했습니다.

실제 AI 분석에는 OpenAI gpt-5-mini를 사용합니다. 지금 화면은 발표용 가상 메일을 비용 없는 기본 분석으로 처리한 예시입니다. 분석이 실패했을 때 기존 예약을 지우지 않고, 작업 상태를 다시 확인할 수 있도록 만드는 데도 신경 썼습니다.

## 5. 메인에서 묻고, 출처로 확인하기

*최신 답변과 직접 입력 출처를 짚고, 메일 원문 질문과 구분합니다.*

AI 질문은 이제 더보기를 찾지 않아도 메인에서 바로 시작할 수 있습니다. 예시 질문을 고르거나 직접 입력하면 대화 화면으로 이어집니다.

왼쪽은 첫날 예약을 모두 알려 달라고 물은 결과입니다. 테스트용 수동 예약 한 건을 정확히 가져왔고, 오른쪽에서는 직접 입력한 예약이라는 출처를 보여줍니다. 이 예약에는 메일 원문이 없다는 점도 표시합니다.

날짜별 질문은 검색 점수가 높은 몇 개를 고르는 대신 저장된 예약을 날짜 범위로 모두 조회합니다. 환불 규정처럼 본문이 필요한 질문은 관련 메일을 검색해 답하고 원문을 연결합니다. AI가 답해 주는 것과 함께, 제가 다시 확인할 수 있는 근거를 남기는 데 신경 썼습니다.

## 6. 장소를 고르고 바로 저장하기

*사진이 있는 이전 마드리드 예시와 현재 무료 사진의 한계를 함께 설명합니다.*

장소 추천에서는 여행에 입력한 날짜와 인원을 그대로 사용합니다. 음식점이나 카페를 고른 뒤, 더 필요한 경우에만 취향이나 예산을 바꾸도록 했습니다. 모든 카드에 반복되던 긴 확인 문구는 줄이고 상세 보기와 저장을 중심으로 정리했습니다.

사진이 확보된 곳은 최대 세 장까지 볼 수 있습니다. 다만 무료 지도 자료에는 사진이 없는 식당이 많습니다. 이번에는 사진 출처 하나가 실패하면 다른 정상 출처까지 막히던 처리를 고쳤고, 파리 식당 한 곳의 실제 표시를 확인했습니다. 화면은 사진 기능을 보여주는 이전 마드리드 예시이고, 모든 식당의 사진이 나온다는 뜻은 아닙니다.

숙소 좌표가 확인되면 숙소 기준으로 거리를 비교합니다. 출발점을 고르지 않았으면 도심 기준이라고 명시합니다. 마음에 드는 곳은 바로 저장하고 같은 조건으로 최대 세 곳을 비교할 수 있습니다.

## 7. 현지 탐색과 유명한 곳

*현지 탐색과 유명한 곳을 비교한 뒤 하단의 개발 상태를 설명합니다.*

추천은 두 가지 방향으로 나눴습니다. 하나는 현지 탐색입니다. 제가 특히 해보고 싶었던 기능은 현지어 원문 리뷰가 충분하고 한국어 리뷰가 적게 관측된 곳을 찾아보는 것이었습니다. 직접 외국어 리뷰를 하나씩 살펴보는 수고를 덜고 싶었습니다.

다른 하나는 유명한 곳입니다. 여행지에 가면 꼭 가보고 싶은 대표 명소나 잘 알려진 식당도 있으니까요. 이쪽은 공식 소개 자료나 같은 플랫폼의 평가 규모처럼 유명함을 설명할 수 있는 근거를 따로 봅니다.

현지어로 리뷰를 썼다고 현지 주민이라고 단정할 수는 없습니다. 그래서 관측한 리뷰의 언어 구성으로 설명하고, 언어를 모르는 리뷰도 함께 계산하도록 했습니다. 엄격한 현지어 추천은 실제 데이터 이용 범위와 언어 품질 검증을 마친 뒤 켤 계획입니다. 지금은 꺼 둔 상태입니다.

## 8. 예약 사이에 들어가는 일정

*두 시간의 빈칸과 필요한 150분을 비교하고 미리보기 흐름을 설명합니다.*

고른 장소는 실제로 갈 수 있는 일정으로 이어져야 합니다. 그래서 이미 확정된 예약을 먼저 두고, 남은 시간에 다른 장소를 넣을 수 있는지 계산하게 했습니다.

점심이 한 시에 끝나고 다음 예약이 세 시라면 빈 시간은 두 시간입니다. 여기에 90분 머무는 장소를 넣고 앞뒤 이동에 각각 30분이 걸리면 총 150분이 필요합니다. 머무는 시간만 보면 들어갈 것 같지만 실제로는 30분이 부족한 겁니다.

일정을 편집할 때도 바로 원본을 바꾸지 않고 먼저 영향을 미리 보여줍니다. 확인한 뒤 적용하고, 다시 되돌릴 수 있습니다. 이동시간이나 영업시간을 모르면 확인이 필요하다고 남기고, 확정 예약을 임의로 옮겨서 일정을 맞추지 않도록 했습니다.

## 9. 어떻게 만들었는지

*각 기술 이름보다 맡긴 역할을 중심으로 설명합니다.*

처음에는 메일을 읽고 질문에 답하는 기능으로 시작했습니다. 그다음 사용자별 여행 저장, 장소 추천, 일정 편집을 차례로 연결했습니다.

화면은 웹으로 만들고 FastAPI 서버가 요청을 처리합니다. Render에 배포하고 여행 데이터와 비공개 파일은 Supabase에 보관합니다. 오래 걸리는 작업은 상태를 저장해서 새로고침한 뒤에도 확인하게 했습니다.

메일에서 정보를 읽는 데는 gpt-5-mini를, 본문 검색에는 text-embedding-3-small을 사용합니다. 날짜 조회와 일정의 시간 충돌은 서버 코드로 검사합니다.

현재 추천 모델은 hybrid_v5입니다. 취향 태그의 유사도, 평가 수를 고려한 평점, 거리 등을 계산합니다. 이번에는 여러 언어의 음식 이름을 더 연결하고 공개 음식 종류와 도심 거리도 반영했습니다. 사용자 행동을 학습한 모델은 아직 아니고, 실제 여행에서 추천이 얼마나 유용한지는 별도로 평가할 계획입니다.

## 10. 직접 써 보며 확인할 것

*사진 확보, 리뷰 품질, 독립 평가의 순서로 설명합니다.*

이번에는 메인에서 추천을 확인하고 저장한 뒤, 예약을 질문하고 출처를 여는 흐름까지 배포 화면에서 확인했습니다. 기능을 더 넣는 것만큼 기존 기능을 쉽게 쓰게 만드는 일이 중요하다는 걸 느꼈습니다.

다음에는 사진과 영업 정보가 비어 있는 장소를 먼저 보강하려고 합니다. 현지어 리뷰 추천은 실제 자료의 이용 범위와 언어 판별 품질을 확인한 뒤 켤 계획입니다. 추천 평가는 제가 만든 예시를 넘어, 순위를 모르는 다른 사람이 후보를 평가하는 방식으로 진행하고 싶습니다.

도시 입력은 백 개를 지원하지만 도시마다 자료 수준은 다릅니다. 실제 여행과 휴대폰에서 사용해 보면서 불편한 부분을 계속 줄여 나가겠습니다. 마지막으로 짧은 화면 영상입니다.

## 11. 고잉 사용 화면

*70초 캡처 편집 영상. 최신 도쿄 화면과 이전 예시 화면의 표시를 참고합니다.*

[영상 시작 전]
실제 서비스 화면 캡처를 편집한 영상입니다. 도쿄는 오늘 확인한 가상 여행이고, 메일과 일정은 이전에 촬영한 발표용 예시입니다.

[0~20초]
메인에서 최근 장소를 보고 바로 저장할 수 있습니다. 아래 입력창에서 예약 질문을 시작하고, 필요한 기능으로 이어갑니다.

[20~38초]
첫날 예약을 모두 조회한 답변과 출처입니다. 직접 입력한 예약에는 메일 원문이 없다는 점도 확인할 수 있습니다.

[38~54초]
추천 화면에서는 여행 날짜를 이어받고 필요한 필터만 고릅니다. 사진이 없는 곳에는 지도에서 사진을 확인하는 경로를 제공합니다.

[54~64초]
예약 메일과 일정은 기존 발표용 화면입니다. 메일을 확인하고, 일정에서는 고정 예약과 충돌을 살펴봅니다.

[영상 종료 후]
제가 좋아하는 여행과 음식점 탐색을 조금 더 편하게 만들고 싶어서 시작했습니다. 앞으로도 직접 쓰면서 고쳐 나가겠습니다. 감사합니다.

## 5분 발표로 줄일 때

1장은 20초, 2장은 25초로 계기만 설명합니다. 3~8장은 각 25초, 9장은 25초, 10장은 10초로 줄이고 영상 70초를 재생하면 5분입니다. 슬라이드에 보이는 내용을 모두 읽기보다 한 장에 한 가지를 이야기합니다.

## 예상 질문

**추천 모델은 무엇인가요?**

현재 기본값은 `hybrid_v5`입니다. 콘텐츠와 여행 조건을 조합하는 모델입니다. 취향은 TF-IDF 코사인 유사도, 평점은 평가 수를 고려한 평균 수축, 거리는 직선거리 감소 함수로 계산합니다. v5에서는 허용된 공개 음식 종류를 잠정 취향 자료로 사용하고, 출발점을 고르지 않았을 때 도심 기준 거리를 추가했습니다. 이름만 보고 메뉴나 식단 적합성을 만들어 내지는 않습니다.

**성능 수치가 있나요?**

이전 `hybrid_v4`는 같은 입력의 합성 개발 사례 12개에서 `general_v3`와 비교했습니다. NDCG@3은 0.4155와 0.9954, Precision@3은 0.3889와 0.7778이었습니다. 개발자가 만든 자료의 순위 회귀 결과이며 실제 정확도 99.54%라는 뜻은 아닙니다. v5의 독립 순위 평가와 실제 여행 만족도는 아직 미측정입니다. 이전 수치를 v5의 결과로 옮겨 쓰지 않았습니다. [기존 평가](../../service-v4/reports/hybrid-v4-benchmark.md), [v5 변경](../../service-v3/MAIN_RECOMMENDATION_UX.md).

**어디까지 실제로 확인했나요?**

2026-10-08 배포 Chrome에서 도쿄와 파리의 공개 후보 12곳 생성, 메인 진행 상태와 최근 장소, AI 날짜 질문과 출처, 저장 성공을 확인했습니다. 코드 회귀 시험은 Python 1,191개, Node 196개, 별도 PostgreSQL 시험 65개가 통과했습니다. 이 숫자는 추천 정확도와는 다릅니다. 모바일 실기기는 미검증이고, 간헐적 서버 오류의 근본 원인도 추가 확인이 필요합니다.

**현지인 맛집인지는 어떻게 아나요?**

거주지는 알 수 없습니다. 관측한 원문 리뷰의 언어 구성을 참고하려는 기능입니다. 한국어가 적어도 미판별 리뷰가 많으면 낮은 한국어 비율이라고 확정하지 않습니다. 실제 이용 범위와 언어 품질 검증 전에는 엄격 추천을 켜지 않습니다.

**왜 사진이 없는 곳도 있나요?**

무료 공개지도에는 사진 링크가 없는 식당이 많습니다. 지점과 이용 조건을 확인한 사진만 표시합니다. 연결 오류를 고치고 실제 파리 식당 한 곳의 표시를 확인했지만, 모든 식당에 사진을 확보한 상태는 아닙니다. 유료 사진 공급자는 키와 예산을 정한 뒤 별도로 검토해야 합니다.

**일반 챗봇과 어떤 점이 다른가요?**

사용자별 여행과 현재 예약, 직접 교정한 값을 보관합니다. 날짜 질문은 저장된 예약을 모두 조회하고, 일정 변경은 서버가 시간과 조건, 버전을 검사합니다. 답변의 원문을 확인하고 저장된 여행을 이어서 사용할 수 있습니다.

**영상이 실시간 시연인가요?**

화면 캡처를 편집한 70초 영상입니다. 메인·AI 질문·출처·도쿄 탐색은 2026-10-08 운영 화면, 메일과 일정은 2026-10-07 로컬 합성 예시입니다. 날짜 질문은 구조화된 예약 조회이며 LLM 답변 품질 실험이 아닙니다. 장면별 날짜를 자막에 표시했고 처리 시간이나 클릭을 재현하지 않았습니다.
