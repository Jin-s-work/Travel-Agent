## 1. 고잉 · 45초

*화면 안내: 제목과 여행 가방 로고를 보여주고, 만든 계기부터 이야기합니다.*

안녕하세요. 제가 만든 여행 서비스 고잉을 소개하겠습니다.

저는 여행하는 것도 좋아하고, 새로운 음식점을 찾아다니는 것도 좋아합니다. 그런데 여행을 갈 때마다 어디를 가야 할지 다시 검색하고, 리뷰를 읽고, 숙소에서 얼마나 먼지 비교하는 게 생각보다 번거로웠습니다. 예약을 해 놓고도 시간이 기억나지 않아서 메일함을 다시 찾는 일도 있었고요.

그래서 제가 여행을 준비할 때 직접 쓰고 싶은 서비스를 만들어 봤습니다. 예약 메일을 정리하는 기능에서 시작해서, 지금은 식당을 찾고 일정에 넣는 과정까지 연결했습니다. 오늘은 어떤 기능이 있는지 먼저 보여드리고, 추천은 어떻게 계산하는지 설명드리겠습니다.

## 2. 여행 하나를 중심으로 · 40초

*화면 안내: 홈 화면의 여행 기간과 주요 진입점을 차례로 가리킵니다.*

먼저 여행을 하나 만듭니다. 도시와 날짜를 정해 두면 메일을 올리거나 장소를 찾을 때 같은 내용을 계속 입력하지 않아도 됩니다. 숙소나 음식 취향처럼 추가로 필요한 정보는 나중에 넣을 수 있습니다.

홈에서는 지금 어떤 여행을 보고 있는지, 예약은 어떻게 정리돼 있는지 확인할 수 있습니다. 메일을 먼저 올려도 되고, 아직 예약한 게 없으면 장소부터 찾아도 됩니다. 처음부터 모든 칸을 채워야 하는 방식은 피하려고 했습니다.

지금 보여드리는 화면은 가상 예약을 넣어 둔 예시입니다. 실제 개인 메일이 화면에 나오지는 않습니다.

## 3. 예약 메일과 질문 · 60초

*화면 안내: 메일 업로드 화면을 보여주며 질문 예시를 읽습니다.*

항공권이나 숙소 확인 메일을 올리면 날짜, 시간, 장소를 예약으로 정리합니다. 한 메일에 예약이 여러 개 있거나 왕복 항공편이 들어 있어도 나눠서 보관합니다. AI가 잘못 읽은 부분은 제가 직접 수정할 수 있고, 수정한 값은 다시 분석하더라도 따로 유지합니다.

메일 분석에는 OpenAI의 gpt-5-mini를 사용하고, 본문 검색에는 text-embedding-3-small을 사용합니다. 분석이 실패했다고 이전 예약을 지우지는 않습니다. 새로고침해도 어디까지 처리됐는지 다시 확인할 수 있습니다.

정리가 끝나면 ‘2일차 예약을 전부 알려줘’처럼 물어볼 수 있습니다. 이런 질문은 날짜에 해당하는 예약을 모두 가져옵니다. 반면 환불 규정 같은 질문은 메일 본문을 검색하고 근거를 보여줍니다. 답변만 보고 넘어가기보다 원문을 직접 확인할 수 있게 했습니다.

## 4. 현지어 리뷰와 유명한 곳 · 65초

*화면 안내: 왼쪽은 언어 관측, 오른쪽은 공식·인기 근거라는 차이를 설명합니다.*

식당을 고를 때 저는 한국어 리뷰로 이미 많이 알려진 곳 외에도 찾아보고 싶었습니다. 그래서 현지어 원문 리뷰가 충분하고, 한국어가 적게 관측된 곳을 찾아보는 기능을 만들었습니다.

여기서 주의한 점은 현지어로 썼다고 해서 현지 주민이라고 단정할 수는 없다는 겁니다. 여행객도 그 언어를 쓸 수 있으니까요. 그래서 화면에서는 현지인 비율이라고 쓰지 않고, 실제로 관측한 리뷰의 언어 구성을 보여주도록 했습니다. 언어를 판단하지 못한 리뷰도 빼버리지 않고 함께 계산합니다.

반대로 여행지에 가면 누구나 아는 유명한 곳에 가보고 싶을 때도 있습니다. 그래서 공식적으로 소개된 명소나 평가가 많이 쌓인 식당을 찾는 ‘유명한 곳’을 별도로 뒀습니다. 음식점, 카페, 볼거리는 여기서 다시 선택합니다.

엄격한 현지어 추천은 실제 리뷰의 이용 범위와 언어 품질 검증이 끝나기 전까지 꺼 두었습니다. 코드는 준비했지만, 실제 자료 검증까지 마쳤다고 소개하지는 않으려고 합니다.

## 5. 살펴보고, 저장하고, 비교하기 · 45초

*화면 안내: 사진, 추천 이유, 확인 필요 항목이 있는 실제 장소 화면을 가리킵니다.*

결과에서는 이름만 나열하기보다 사진과 추천 이유를 먼저 볼 수 있습니다. 사진은 이용 권한과 지점을 확인한 자료가 있을 때 최대 세 장까지 보여줍니다. 모든 식당에 사진이 있는 것은 아닙니다.

장소를 열면 영업시간, 예약 방법, 가격을 보고 그 정보의 출처도 확인할 수 있습니다. 마음에 들면 보관함에 저장하고, 같은 날짜와 인원 조건으로 세 곳까지 비교할 수 있습니다.

숙소 위치를 확인했다면 거리도 같이 봅니다. 다만 지도상의 직선거리와 실제 도보시간은 다르기 때문에 구분해서 표시합니다. 예약 가능 여부처럼 확인하지 못한 것은 가능하다고 채우지 않고, 방문 전에 확인할 항목으로 남깁니다.

## 6. 추천 순위를 계산하는 방법 · 65초

*화면 안내: 취향 → 평점 → 거리 순으로 설명하고 필수 조건 문구를 짚습니다.*

처음에는 리뷰 비율이나 평가 수를 기준으로 순서를 정했습니다. 그런데 초밥을 좋아한다고 입력해도 그 취향이 순위에 충분히 반영되지 않는 문제가 있었습니다.

지금은 콘텐츠 기반 추천 모델을 사용합니다. 사용자가 고른 취향과 장소의 태그를 TF-IDF라는 벡터로 만들고, 코사인 유사도로 얼마나 가까운지 계산합니다. 예를 들어 초밥과 스시처럼 연결할 수 있는 태그는 작은 사전으로 정리했습니다.

평점도 그대로만 비교하지 않습니다. 평가 한 건의 5점과 수백 건의 4.8점은 다르기 때문에, 평가가 적은 장소는 같은 플랫폼과 도시의 평균 쪽으로 보정합니다. 여기에 숙소 등 출발점과의 거리도 반영합니다.

취향과 출발점이 모두 있으면 기본 근거 40, 취향 40, 거리 20의 비중을 씁니다. 이 비중은 아직 초기 설정입니다. 사용자 행동을 학습한 모델은 아니고, 선택한 조건과 장소 정보를 계산하는 방식입니다. 또 휴무나 인원 조건을 위반한 곳은 점수가 높아도 먼저 제외합니다.

## 7. 확정 예약을 지키는 일정 · 50초

*화면 안내: 일정 화면과 오른쪽의 120분·150분 예시를 번갈아 짚습니다.*

고른 장소를 일정에 넣을 때는 이미 확정한 예약을 먼저 배치합니다. 그 사이에 다른 장소를 넣어도 되는지 영업시간, 체류시간, 앞뒤 이동시간을 검사합니다.

예를 들어 빈 시간이 두 시간인데 식당에서 90분을 보내고 양쪽 이동에 각각 30분이 필요하면, 총 두 시간 반이라 넣으면 안 됩니다. 머무는 시간만 보고 일정이 된다고 판단하지 않도록 했습니다.

편집은 바로 원본을 바꾸는 대신 먼저 미리보기를 보여줍니다. 뒤 일정에 어떤 영향이 있는지 보고 적용하고, 마음에 들지 않으면 되돌릴 수 있습니다. 고정 예약끼리 겹쳐도 임의로 이동하지 않습니다. 그리고 일정에서 항목을 지우는 것과 실제 외부 예약을 취소하는 것은 별개입니다.

## 8. 이전 모델과 비교한 결과 · 55초

*화면 안내: NDCG 막대를 보여준 뒤 하단의 합성 개발 평가라는 한계를 설명합니다.*

추천이 달라졌다는 걸 확인하기 위해 이전 모델과 같은 입력으로 비교하는 평가 도구도 만들었습니다. 도쿄와 바르셀로나를 대상으로 취향, 거리, 평점, 조건 위반 등을 다룬 열두 개의 합성 시나리오입니다.

여기서 NDCG는 적합한 후보가 앞에 오는 정도를 보는 지표입니다. 이전 모델은 약 0.42, 새 모델은 약 1.00으로 나왔습니다. 상위 세 칸 중 적합한 후보의 비율인 Precision도 약 0.39에서 0.78로 높아졌습니다.

다만 이것을 실제 추천 정확도가 99퍼센트라고 말할 수는 없습니다. 제가 만든 시나리오와 기대 등급에 대한 개발 시험이기 때문입니다. 독립적인 평가 자료는 아직 없습니다. 실제 성능은 다른 사람이 순위를 모르는 상태에서 후보를 평가한 자료와 방문 경험으로 확인해야 합니다. 계산 시간도 조금 늘어서, 속도까지 개선됐다고 보지는 않습니다.

## 9. 여행 전과 여행 중에 · 40초

*화면 안내: 예약 준비, Plan B, 오늘 보기, 예상 지출의 사용 상황을 짧게 설명합니다.*

장소를 고른 뒤에 필요한 기능도 만들었습니다. 예약이 언제 열리는지 할 일로 정리하고, 캘린더에 넣을 ICS 파일이나 현지어 문의문 초안을 만들 수 있습니다. 문의를 자동으로 보내거나 대신 결제하지는 않습니다.

여행 중 비가 오거나 너무 피곤하면, 전체 일정을 다시 만드는 대신 영향을 받는 구간의 대체안을 먼저 볼 수 있습니다. 오늘 보기에서는 현지 날짜 기준으로 다음 일정을 확인합니다.

예상 지출은 엔화와 유로처럼 통화별로 나눠 보여주고, 가격을 모르는 항목도 함께 표시합니다. 오프라인 읽기 기능도 구현했지만, 실제 기기별 검증을 더 진행한 뒤 사용 범위를 넓힐 계획입니다.

## 10. 앞으로의 개발 방향 · 45초

*화면 안내: 실제 리뷰 → 독립 평가 → 현장 사용 순서로 설명하고 마칩니다.*

다음에는 기능 수를 늘리는 것보다 실제 자료와 사용 경험을 더 확인하려고 합니다.

먼저 도쿄와 바르셀로나의 리뷰 원문과 이용 범위, 언어 판별 품질을 검증하고, 통과한 자료에서 현지어 추천을 켜고 싶습니다. 그다음에는 다른 사람이 평가한 후보로 지금의 추천 모델을 비교하려고 합니다. 실제 선택과 방문 피드백이 충분히 쌓이면 그때 학습 기반 개인화도 시도할 수 있습니다.

도시 입력은 백 개 도시를 지원하지만 모든 도시의 추천 자료가 같은 수준으로 준비된 것은 아닙니다. 영업·예약 정보와 이동 경로를 더 채우고, 모바일과 오프라인을 실제 여행 환경에서도 확인할 계획입니다.

제가 여행을 갈 때 매번 찾느라 불편했던 부분을 조금 덜어보려고 시작한 프로젝트입니다. 앞으로도 직접 써 보면서 고쳐나가고 싶습니다. 감사합니다.

## 10분 발표에서 시연을 넣을 때

기본 대본 뒤에 60~90초만 추가합니다. 네트워크가 느리면 새 외부 작업을 기다리지 말고 슬라이드 화면으로 설명합니다.

1. 미리 열어 둔 합성 여행에서 메일로 만든 예약 한 건과 원문 출처를 보여줍니다.
2. 저장된 장소의 상세를 열어 영업·가격의 확인 여부를 짚습니다.
3. 기존 일정의 변경 미리보기를 보여준 뒤 취소합니다. 외부 예약은 건드리지 않습니다.

실제 개인 메일·예약번호·계정 정보는 발표 화면에 띄우지 않습니다. 최신 추천 화면은 발표 전에 직접 열어 확인하고, 확인하지 못했다면 이 자료의 기존 촬영 화면을 사용합니다.

## 예상 질문

**추천 모델을 학습시켰나요?**

아직 사용자 행동으로 학습하지 않았습니다. 장소 태그와 취향을 TF-IDF로 벡터화해 코사인 유사도를 계산하고, 보정 평점과 거리를 조합하는 콘텐츠·조건 기반 모델입니다. 가중치는 초기 가설이며 독립 평가 자료로 검증할 계획입니다.

**99% 정도 정확한 건가요?**

아닙니다. NDCG는 정답 등급과 순서를 비교하는 지표이고, 이번 0.9954는 개발자가 만든 합성 12개 사례에서 나온 값입니다. 독립적인 실제 추천 정확도·방문 만족도는 미측정입니다.

**현지인 맛집인지 어떻게 아나요?**

거주지를 알 수는 없습니다. 관측한 원문 리뷰의 언어를 참고하는 기능입니다. 미판별을 포함해 보수적으로 계산하며, 이용 범위와 언어 품질을 실제로 확인하기 전에는 엄격 추천을 켜지 않습니다.

**ChatGPT에 그냥 물어보는 것과 어떤 차이가 있나요?**

내 여행의 현재 예약과 교정값을 보관하고, 날짜 질문은 전체 예약을 조회합니다. 장소 추천도 서버가 확인한 후보와 조건을 기준으로 계산합니다. 일정 변경은 충돌 검사와 버전 확인을 거쳐 적용하고 되돌릴 수 있습니다.

**백 개 도시에서 바로 똑같이 쓸 수 있나요?**

도시 입력과 시간대는 지원하지만 추천 자료의 확보 수준은 다릅니다. 검수 후보와 공개지도 자료를 구분하고, 자료가 없으면 없는 이유를 표시합니다.

**앞으로 어떤 모델을 쓰고 싶나요?**

먼저 실제 후보를 독립 평가해 현재 방식을 검증하려고 합니다. 충분한 선호 자료가 모이면 pairwise 학습 순위 모델을 비교할 수 있지만, 지금은 학습 데이터가 부족하므로 태그·리뷰 품질부터 보완하는 게 우선입니다.
