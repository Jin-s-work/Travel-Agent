# Travel Agent 여행 추천과 일정 서비스 PRD

2026년 10월 1일 개정한 상세 제품 명세입니다. 목표는 예약 확인 중심의 앱을 **내 여행 일정에 맞춰 먹을 곳과 볼거리를 고르고, 확인 가능한 근거로 방문 계획까지 만드는 서비스**로 확장하는 것입니다. 현재 예약 메일 업로드·검색·답변을 유지하며 개발합니다. 이번 개정은 크롤링 검증, 관측 범위가 있는 리뷰 언어 신호, 일정 편집·대안·예약 준비·여행 중 사용까지 포함합니다. 아직 구현된 기능을 설명하는 문서는 아닙니다.

## 사용자와 해결할 문제

사용자는 여행 날짜, 숙소, 동행 인원과 이미 잡힌 예약을 가지고 있습니다. 그러나 좋은 장소를 찾는 일, 관광객에게 유명한 곳과 현지 취향의 곳을 구분하는 일, 영업시간과 이동 시간을 맞추는 일이 여러 플랫폼에 흩어져 있습니다.

서비스는 다음 세 질문에 답해야 합니다.

- 내 취향과 여행 동선에 맞는 장소는 어디인가?
- 왜 추천하며, 현지에서 선호한다는 근거는 무엇인가?
- 내 방문 날짜와 인원으로 언제 방문하고 어떻게 예약을 확인할 수 있는가?

첫 출시는 사용자가 확인한 **본인과 소수 지인용 비공개 베타**입니다. 낮은 비용으로 일본과 바르셀로나를 지원하고 싶다는 요청에 맞춰 도쿄·바르셀로나의 소규모 후보팩을 제안합니다. 정확한 예산은 미정이며 다중 사용자 데이터 격리는 첫 베타부터 필수입니다.

## 제품 원칙

1. 추천 근거와 방문 가능 여부를 분리합니다. 좋은 장소라도 휴무이거나 인원 조건이 맞지 않으면 일정에 자동 확정하지 않습니다.
2. 현지어 리뷰를 현지인 신분으로 해석하지 않습니다. 현지 탐색은 증거에 기반한 추천 유형이며 주민 방문 비율을 보장하는 표현이 아닙니다.
3. 예약 방법, 예약 가능한 인원, 실제 남은 좌석은 각각 다른 정보입니다. 마지막 항목은 실시간 연결이 없으면 `미확인`입니다.
4. 개인 예약은 사용자 소유 데이터입니다. 공개 장소 검색과 구분하고 다른 사용자·여행으로 넘어가지 않도록 서버에서 차단합니다.
5. 모델은 확보된 사실을 정리하고 설명합니다. 권한, 점수 계산, 일정 충돌 판정과 비용 한도는 코드가 처리합니다.

## 핵심 사용자 흐름

### 여행 만들기

필수 입력은 목적지, 여행 시작·종료일, 성인·아동 인원, 현지 시간대입니다. 숙소 위치, 예산, 음식 취향, 알레르기·식단 제한, 이동수단, 걷기 허용량, 일정 밀도는 선택 입력입니다. 위치는 도시 중심·역·숙소 주소로 지정할 수 있습니다.

예약 메일을 올리면 날짜·위치·예약 인원을 추출해 확인 화면을 보여줍니다. 한 문서에 왕복 항공이나 여러 예약이 있으면 모두 추출하는 `SourceDocument 1:N Booking` 관계를 지원합니다. 출도착 시간대와 주소가 불분명하면 사용자 확인 전 고정 일정으로 확정하지 않습니다. 메일이 없어도 직접 여행을 만들 수 있습니다. 사용자 교정값은 추출값과 별도 보관하고 재추출로 덮어쓰지 않습니다.

### 장소 찾기

상단에 날짜·방문 시간대·기준 위치·인원이 표시됩니다. 추천 유형은 **현지 탐색 / 대표 명소**로 구분합니다. 그 안에서 **음식점 / 카페 / 볼거리**를 필터링합니다. 유명 음식점도 대표 명소에 들어가며 덜 알려진 볼거리도 현지 탐색에 들어갈 수 있습니다.

현지 탐색은 선택 이유와 근거 수준을 먼저 보여줍니다. 대표 명소는 방문 가치, 예상 소요시간, 혼잡과 사전 예약 필요 여부를 먼저 보여줍니다. 두 유형에 해당하는 장소는 동일 장소 ID를 공유하며 일정에는 중복 추가하지 않습니다.

초기 결과는 유형별 최대 5개를 보여주고 부족하면 실제 확보한 개수만 보여줍니다. 조건을 조용히 낮추지 않고 반경·예산·시간대 변경을 제안합니다.

### 장소 상세와 일정 추가

상세 화면에서 운영시간, 휴무, 가격 범위, 예약 경로, 인원 조건, 공식 링크와 마지막 확인 시각을 확인합니다. `일정에 추가`를 누르면 가능한 시간대를 제안합니다. 운영 정보가 부족하면 `확인 필요` 상태로 추가할 수 있지만 방문 가능이 확정된 일정으로 표시하지 않습니다.

`예약 확인하기`는 외부 공식 사이트 또는 검증한 예약 플랫폼으로 연결합니다. 초기 버전은 결제·예약을 대신 실행하지 않습니다. 사용자가 예약 후 확인 메일을 올리거나 직접 예약됨을 표시하면 예약 기록과 연결합니다. 사용자 표시와 메일 근거 확인은 서로 다른 상태로 보관합니다.

## 제품 사용 시나리오

### 도쿄 4인 여행

사용자는 4명, 4박 5일, 숙소 위치와 확정된 투어를 입력합니다. 첫날 도착편과 마지막 날 귀국편은 시간대가 있는 고정 이벤트입니다. 저녁은 일본어 리뷰 신호가 강한 음식점을 원하고, 낮에는 처음 방문하는 대표 명소도 가고 싶어합니다.

서비스는 현지 탐색 음식점과 대표 명소를 따로 보여줍니다. 4인 예약 조건이 확인된 후보와 미확인 후보를 구분하고, 투어 종료 후 이동 가능한 저녁 식당을 제안합니다. 리뷰 언어 조건을 통과했어도 1회 예약이 2인까지만 가능하면 엄격한 4인 조건에서는 제외합니다. 2명씩 두 예약을 대신 만들지 않습니다.

### 바르셀로나 2인 여행

사용자는 유명 건축물을 꼭 방문하고 싶지만 식사는 관광지 바로 앞을 피하고 싶어합니다. 예약한 입장 시간을 고정하고 점심 후보는 스페인어·카탈루냐어 원문 리뷰와 지역 자료를 함께 살펴봅니다.

방문 날짜의 입장 마감과 식당의 중간 휴식 시간을 각각 확인합니다. 비가 오거나 긴 대기줄을 사용자가 알리면 실내 대안과 인근 식당을 제시합니다. 현재 날씨를 확인할 수 없으면 앱이 비가 온다고 단정하지 않고 사용자가 선택한 상황에 대한 대안을 제공합니다.

### 당일 일정 변경

사용자가 “너무 피곤해서 오후를 줄이고 싶어”라고 입력합니다. 서비스는 먼저 변경안과 영향 범위를 보여줍니다. 확정된 입장권·식당 예약은 유지하고 선택한 자유 일정만 줄입니다. 실행 전후의 시간과 빠지는 장소를 비교하고, 적용 뒤 되돌리기를 지원합니다.

## 기능별 상세 요구사항

### F01 초대와 처음 사용

초대된 사용자는 로그인 후 자신의 여행만 봅니다. 공개 가입, 결제와 요금제 화면은 첫 베타에 필요하지 않습니다. 만료된 초대·허용되지 않은 계정·세션 만료를 각각 안내하고, 잘못된 접근에 다른 사용자의 여행 존재 여부를 알려주지 않습니다.

첫 화면의 핵심 행동은 `여행 만들기`와 `예약 메일로 시작`입니다. 로그인 직후 모든 취향을 묻지 않습니다. 최소 여행 조건을 받고 첫 결과를 보여준 다음 추가 선호를 수집합니다. 예시 여행은 명확한 데모이며 개인 여행에 자동으로 섞지 않습니다.

**완료 조건:** 초대 계정 두 개로 여행·메일·작업·저장 장소가 격리됩니다. 세션이 만료돼도 서버에 저장한 일정은 유지되고 재로그인 뒤 복원됩니다.

### F02 여행 생성과 여행 구간

입력은 4단계로 나눕니다. 목적지와 날짜 → 동행 인원과 숙소 → 꼭 가고 싶은 곳 → 취향과 이동 선호입니다. 선택 입력은 건너뛸 수 있고 나중에 수정할 수 있습니다. 날짜·도시는 항상 결과 상단에서 확인할 수 있습니다.

여행은 여러 도시 구간을 가질 수 있도록 모델링합니다. 첫 베타의 추천은 도쿄·바르셀로나 지원 구간에 한정하지만, 기존 메일의 하코네나 다른 도시 예약을 삭제하거나 도쿄로 바꾸지 않습니다. 미지원 지역은 예약과 사용자 직접 일정을 표시하고 자동 추천 범위 밖임을 알립니다.

날짜 변경은 기존 일정을 자동 삭제하지 않습니다. 변경되는 일정 항목과 예약의 범위 이탈을 미리 보여주고 사용자가 적용합니다. 성인·아동·연령대 정보는 실제 조건 판정에 필요한 최소한만 받습니다.

**완료 조건:** 메일 없는 여행, 왕복 메일 한 통, 중간 도시 이동, 날짜 단축, 숙소 변경을 처리합니다. 시간대·도시가 불명확하면 해당 구간을 확정하지 않습니다.

### F03 저장한 장소와 링크 가져오기

사용자는 장소 URL, 이름, 직접 쓴 메모를 여행의 보관함에 추가할 수 있습니다. 공식 사이트와 지도 링크를 먼저 지원하며 소셜 게시물 링크는 원문 접근이 되지 않아도 사용자의 참고 링크로 저장할 수 있습니다.

가져오기는 `링크 확인 → 지점 후보 → 사용자 선택 → 저장` 순서입니다. 상호가 같거나 주소가 여러 개면 지점을 확인합니다. 링크를 저장했다는 사실과 내용을 검증했다는 사실을 구분합니다. Google 링크는 허용된 장소 식별에 사용하고 페이지 전체를 자동 영구 복사하지 않습니다.

중복 후보를 발견하면 기존 메모에 병합할지 별도 항목으로 남길지 보여줍니다. 개인 메모는 공유용 장소 데이터에 섞지 않습니다. 비공개 문서 링크의 토큰이나 개인 주소는 공개 검색어로 전달하지 않습니다.

**완료 조건:** 같은 지점 두 URL, 잘못된 URL, 접속 불가, 단축 URL, 지점 모호, 메모만 있는 장소를 구분합니다. URL fetch에는 내부망 접근 차단을 적용합니다.

### F04 취향과 필수 조건

선호는 `좋아함`, `피하고 싶음`, `반드시 지켜야 함`으로 구분합니다. 예를 들어 카페 선호는 순위 요소이고, 최대 이동거리와 알레르기 조건은 별도의 제약입니다. 가격을 알려주지 않은 장소를 자동으로 저렴하다고 평가하지 않습니다.

알레르기·휠체어·유아 동반 등은 “확인됨 / 미확인 / 부적합”으로 판정합니다. 엄격 조건을 선택한 사용자는 미확인도 자동 일정에서 제외할 수 있습니다. 알고리즘은 자료가 없는 상태를 안전하다는 의미로 바꾸지 않습니다.

좋아요·저장·제외 이유는 `이미 방문`, `너무 멂`, `비쌈`, `취향 아님`, `정보 불확실` 등으로 받습니다. 제외 한 번으로 영구 성향을 단정하지 않고 이번 여행 적용과 계정 기본값 적용을 나눕니다.

**완료 조건:** 같은 사용자라도 도쿄와 바르셀로나 여행의 예산·식성이 독립적입니다. 선호 변경은 추천 버전을 갱신하지만 확정 예약을 바꾸지 않습니다.

### F05 두 추천 구획과 후보 비교

현지 탐색과 대표 명소는 항상 구획이 드러납니다. 화면이 좁으면 탭으로 전환하되 두 유형의 존재를 숨기지 않습니다. 각 구획에서 음식점·카페·볼거리를 고를 수 있습니다. 일정 생성에서 `현지 탐색 위주 / 균형 / 대표 명소 위주`를 선택해도 유형을 하나로 합쳐 설명하지 않습니다.

결과 카드에 추천 이유, 여행 동선과의 관계, 인원·영업 확인 상태, 가격 범위, 자료 확인일을 표시합니다. 상세한 통계와 출처는 펼쳐 볼 수 있지만 예약 조건 미확인은 카드에서 보여줍니다. 공급자 가격·언어 수치와 자체 추천 점수의 출처를 구분합니다.

후보는 최대 3개를 비교합니다. 비교 항목은 동선, 방문 가능 시간, 인원 적합성, 가격, 예약 필요, 리뷰 언어 범위, 지역 근거입니다. 한쪽만 데이터가 있으면 없는 쪽을 0점처럼 그리지 않습니다. `추천을 바꾼 이유`에서 입력 변경 또는 갱신된 근거를 확인할 수 있습니다.

**완료 조건:** 조건을 충족하는 후보가 2개면 2개만 표시합니다. 반경·예산·언어 조건 완화는 변경될 조건을 먼저 보여주고 사용자 선택으로 적용합니다.

### F06 리뷰 언어와 근거 탐색

수집 범위, 원문 확보 수, 언어 판별 수, 미판별 수, 관측 기간과 마지막 갱신일을 확인할 수 있어야 합니다. 한국어 원문 0개와 한국어 여부 미확인은 다른 표시입니다.

후보의 언어 자료가 없을 때 `분석 요청`을 제공할 수 있습니다. 요청은 비동기 작업이며 예상 범위와 상한을 확인하고 실행합니다. 여러 사용자가 같은 장소를 요청해도 사용 가능한 공개 집계는 중복 실행하지 않습니다. 개인 여행 조건은 공개 집계 키에 넣지 않습니다.

이 기능은 데이터 검증을 통과하면 초기 핵심 기능으로 활성화합니다. 단순히 나중으로 미루는 것이 아니라 [수집 실험](CRAWLING_FEASIBILITY.md)을 개발 초기에 병행합니다. 조건을 충족하지 못하면 현재 부족한 이유를 기록하고 해당 상태를 UI에 반영합니다.

**완료 조건:** 5개·부분 수집·번역문만 있음·최신순 200건·관측 전수·언어 미판별 과다 사례가 서로 다르게 표시됩니다.

### F07 장소 상세와 방문 준비

상세 화면은 `왜 추천하는지`, `방문 조건`, `예약 준비`, `근거` 순서입니다. 우선 행동은 일정 추가와 공식 예약 확인이며 모든 상세 정보가 끝날 때까지 탐색을 막지 않습니다.

예약 조건은 예약 필요 여부, 예약 1건의 최소·최대 인원, 아동 규칙, 예약 오픈일, 취소·보증금 조건, 실제 슬롯 확인 시각으로 나눕니다. 검증한 공식 예약 경로가 없으면 검증되지 않은 임의 결제 사이트를 추천하지 않고 공식 홈페이지·전화 확인을 안내합니다.

`예약 문의 문장 만들기`는 날짜·시간·인원·필요 조건으로 일본어 또는 스페인어 등의 초안을 만듭니다. 사용자 검토용 초안이며 자동 발송·전화·예약 확정은 하지 않습니다. 예약번호·민감정보를 기본 포함하지 않습니다.

**완료 조건:** 사용자는 “영업 중이지만 해당 시간 자리 미확인”, “4인 입장 가능하지만 1건 예약은 2인”, “입장 마감과 폐관 시간이 다름”을 구분할 수 있습니다.

### F08 예약 준비 목록과 마감

예약 업무를 일정과 연결합니다. 상태는 `확인 필요 → 예약 전 → 사용자 예약 신고 또는 증빙 확인 → 취소`입니다. 예약 링크 클릭만으로 상태를 완료로 바꾸지 않습니다.

예약 오픈 규칙이 공식 자료에서 확인되면 목적지 시간대와 한국 시간 표시를 함께 제공합니다. “매월 1일 다음 달 예약 오픈”과 “방문 30일 전”은 다른 규칙이며 코드로 계산합니다. 규칙이 모호하면 날짜를 만들어내지 않고 확인 작업만 생성합니다.

초기 저비용 버전은 앱 안의 할 일과 캘린더 파일 내보내기를 먼저 제공합니다. 캘린더 파일은 스냅샷이라 예약 조건 변경이 자동 반영되지 않음을 설명합니다. 이메일·푸시 알림은 사용자가 채널과 시각을 설정한 경우에만 추후 활성화합니다.

**완료 조건:** 예약 오픈일의 현지 시간대, DST, 날짜 변경, 취소 상태가 보존됩니다. 동일 업무를 갱신하면서 중복 캘린더 항목을 만드는 문제를 테스트합니다.

### F09 일정 초안과 제약 검사

일정 생성 전 사용자에게 활동 가능 시간, 꼭 포함할 장소, 확정 예약, 여유·균형·빽빽함을 보여줍니다. 기본은 하루 주요 방문 2~3개와 식사·이동·휴식이며 숫자는 사용자가 조절할 수 있습니다.

생성 결과에는 방문 순서뿐 아니라 배치하지 못한 장소와 이유가 있어야 합니다. 같은 지역을 묶되 이동 시간을 허위로 줄이지 않습니다. 영업시간·입장 마감·브레이크타임·예약 시간은 서로 다른 제약입니다. 긴 항공편과 숙박은 일반 관광 체류와 별도 이벤트 유형입니다.

초안에는 `검증된 항목`, `잠정 항목`, `충돌`을 표시합니다. 확인되지 않은 교통·영업 정보 때문에 빈 시간이 남는 것도 유효한 결과입니다. “한 번에 최적 일정”이라는 표현 대신 현재 입력과 근거에 맞춘 초안으로 설명합니다.

### F10 편집과 변경 영향

장소 추가·제거, 시작 시각 변경, 날짜 이동, 핀 고정을 지원합니다. 드래그만 제공하지 않고 키보드·모바일용 `시간 바꾸기`, `다른 날짜로 이동`도 제공합니다.

변경은 미리보기에서 적용 전후 시간과 충돌을 비교합니다. 후속 일정 전체를 조용히 이동하지 않습니다. 되돌리기는 최소 마지막 10개의 사용자 편집을 대상으로 하고 자동 갱신과 사용자 편집 버전을 구분합니다. 다른 탭에서 이미 수정한 경우 version 충돌을 보여줍니다.

**완료 조건:** 이동 실패 시 기존 일정 유지, 고정 예약 보존, 동시 수정 알림, 적용·취소·되돌리기가 일관되게 동작합니다.

### F11 대체 일정

사용자가 `비가 옴`, `휴무`, `긴 줄`, `피곤함`, `예약 실패`를 선택하면 남은 일정에서 바꿀 수 있는 범위를 정합니다. 확인된 기상 데이터가 없을 때는 사용자가 선택한 상황을 입력으로 사용합니다.

대안은 가능하면 같은 종류·유사 예산·허용 이동시간의 후보 2~3개를 제안합니다. 후보가 부족하면 이동 반경을 늘릴지 물어보고, 다음 확정 예약과 충돌하는 대안은 제외합니다. 실제 대기시간 정보가 없으면 “대기 없음”이라 쓰지 않습니다.

**완료 조건:** 대안을 적용해도 이미 지난 일정이나 확정 예약이 바뀌지 않습니다. 원래 일정을 남기고 되돌릴 수 있습니다. 비가 온다는 사용자 보고와 외부 예보의 출처가 구분됩니다.

### F12 여행 중 보기와 오프라인

오늘 화면은 다음 일정, 출발 권장 시각의 근거, 공식 주소, 현지어 장소명, 지도 열기와 예약 확인 상태를 우선 표시합니다. 현재 위치 사용은 선택사항이며 저장된 숙소·직접 선택한 위치만으로도 작동합니다.

오프라인은 사용자가 선택한 여행에 한해 명시적으로 내려받습니다. 최초 범위는 사용자 일정·직접 메모·보관 가능한 주소·긴급 참고 링크입니다. 메일 원문, 예약번호, 정책상 오프라인 보관 불가 공급자 데이터는 기본 제외합니다.

오프라인 정보에는 저장 시각을 표시하고 영업·잔여석을 실시간 정보처럼 보여주지 않습니다. 로그아웃·여행 삭제·공용 기기 모드에서 기기 저장 내용을 지웁니다. 서버의 일반 API 응답 캐시 금지는 유지하고 별도 제한된 오프라인 묶음으로 구현합니다.

**완료 조건:** 비행기 모드에서 저장 일정이 열리고, 로그아웃 후 다른 계정이 내용을 볼 수 없습니다. 지원하지 않는 정보는 빈 값 대신 오프라인 미지원으로 안내합니다.

### F13 예상 지출과 선택 기록

식사·티켓·이동의 예상 비용을 현지 통화로 합산합니다. 범위 가격은 합계도 범위로 표시하고 모르는 비용을 0원 처리하지 않습니다. 통화 변환을 추가하면 환율 출처·기준일을 표시하며 실제 결제 금액으로 보장하지 않습니다.

방문 후 피드백은 별점 하나보다 `좋았음`, `기대와 다름`, `정보 오류`, `방문 못함`과 선택 이유를 수집합니다. 방문하지 않은 사용자의 예상 선호와 방문 경험을 분리합니다. 작은 베타의 친구 평가를 일반 대중 평가처럼 표시하지 않습니다.

### F14 운영자 검토 도구

운영자는 지점 불일치, 영업시간 충돌, 만료된 원문, 크롤링 부분 실패, 사용자 오류 신고와 비용을 볼 수 있어야 합니다. 사용자 원문 메일은 일반 운영 지표 화면에 노출하지 않습니다.

사실을 수정하면 이유·출처·수정자를 기록하고 영향을 받는 추천과 일정에 `다시 확인 필요`를 붙입니다. 업데이트로 사용자의 확정 일정을 조용히 변경하지 않습니다. 공급자를 끄더라도 저장한 여행과 자체 근거는 이용 가능한 범위에서 유지합니다.

접근성 기준은 색상 외 상태 텍스트, 키보드 조작, 읽을 수 있는 대비, 작은 화면의 겹치지 않는 버튼, 스크린리더용 진행 안내입니다. 숫자는 통화·분모·시간대를 함께 표시하고 출처 링크는 무엇을 확인할 수 있는지 설명합니다.

## 현지 탐색 추천 기준

### 첫 버전에서 사용할 수 있는 근거

초기에는 운영자가 도쿄·바르셀로나에 각각 약 15곳, 합계 30곳을 준비하는 것을 목표로 합니다. 도시별 현지 탐색 10곳, 대표 명소 5곳이 제안 범위이며 실제 수집 완료 수가 아닙니다. 첫 실제 여행지의 숙소 주변부터 보강합니다. 후보가 여행 조건에 맞지 않을 때는 부족함을 그대로 표시합니다.

현지 탐색의 근거는 지역 생활 매체·지역 편집 가이드의 구체적인 추천, 독립적인 지역 커뮤니티의 허용된 자료, 운영자의 직접 확인 기록입니다. 검색은 원문을 찾기 위한 수단이며 검색 스니펫이나 같은 보도자료를 재전재한 기사 수를 독립 근거로 세지 않습니다. 현지어 공식 홈페이지가 있다는 사실만으로 현지 선호를 인정하지 않습니다.

근거 수준은 다음처럼 정의합니다. 수치 가중치는 제품 가설이며 초기 평가로 조정합니다.

- **충분한 근거:** 독립 출처 2개 이상에서 구체적인 지역 이용 맥락을 확인하거나, 검증 가능한 직접 확인과 독립 출처가 함께 있음.
- **일부 근거:** 유효한 독립 출처 1개. 추가 검증 필요로 표시.
- **확인 필요:** 출처가 부족하거나 광고성·시점·장소 일치 여부가 불분명. 기본 상위 추천에서 제외하고 탐색 후보로만 제공.

사용자 화면에는 “현지인 비율 90%”, “관광객 없는 맛집”처럼 입증하지 못한 표현을 쓰지 않습니다. 관측한 사실인 “지역 매체 2곳 소개”, “운영자 방문 확인”을 보여줍니다.

### 사용자가 원하는 리뷰 언어 필터

기능 이름은 **리뷰 언어 조건**으로 정합니다. 실제 거주지 필터로 부르지 않습니다. Google Places의 최대 5개 관련도순 리뷰만으로 전체 언어 분포를 계산할 수 없습니다. 하지만 이 제한은 공식 API에 관한 것이며, 크롤링 공급자의 페이지네이션을 이용한 5개 초과 수집과 구분해야 합니다. [공식 Place 자료형](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places), [수집 방법과 비용 조사](CRAWLING_FEASIBILITY.md)

활성화하려면 공급자 또는 검증된 자체 처리로 원문 언어, 관측 텍스트 수, 수집 범위·기간·방법을 확보하고 통계 생성·저장·표시의 이용 조건을 확인해야 합니다. 공급자가 원문 언어 코드를 제공하지 않아도 원문이 있으면 검증한 로컬 판별기를 사용할 수 있습니다. 평점·규모 조건에는 같은 플랫폼의 전체 평가 수를 별도로 사용하며, 전체 비율 추정은 추가적인 전수·표본 근거를 요구합니다. 플랫폼·지점·기간이 다른 수치를 하나로 합치지 않습니다. 번역된 화면 언어와 작성자 이름·국적 추정은 사용하지 않습니다.

다음은 **향후 파일럿용 가설 값**입니다. 실제 서비스 기준으로 확정하기 전에 도시별로 평가합니다.

| 조건 | 실험 기본값 | 불충분할 때 |
| --- | --- | --- |
| 평점과 규모 | 동일 플랫폼 5점 척도 4.2 이상, 전체 평가 200개 이상 | 텍스트 리뷰 수와 구분. 다른 척도는 별도 평가 |
| 언어 관측량 | 원문 언어를 판별할 수 있는 리뷰 100개 이상 | 통계 필터 비활성 |
| 현지어 비율 | 관측 범위 내 60% 이상 | 조건 불충족 |
| 한국어 비율 | 관측 범위 내 10% 이하 | 조건 불충족 |
| 관측 범위 품질 | 최신순 연속 구간과 종료 사유 확인 | 관련도순·키워드 선별·누락 구간은 엄격 필터 판정 불가 |

표시용 “분류 가능한 리뷰 중 비중”의 분모는 동일 플랫폼·지점·기간에서 중복을 제거하고 원문 언어를 분류한 본문 수 C입니다. 엄격 판정은 아래처럼 미판별도 포함한 본문 수 T를 사용합니다. 전체 평가 수는 어느 언어 비율의 분모로도 쓰지 않습니다. 관측 텍스트 수, 분류 가능 수, 미판별 수와 수집 방법을 함께 표시합니다.

첫 버전은 `observed_window`로 시작합니다. 최신순 최대 200레코드·최근 180일이라는 제안 범위에서 확보한 텍스트의 언어 비중을 계산합니다. 최신순 수집은 무작위 표본이 아니지만, 실제로 관측한 범위의 비중을 설명하는 데 사용할 수 있습니다. 엄격 조건은 미판별을 포함한 보수적 범위로 판정합니다. 본문 수 T, 현지어 L, 한국어 K, 미판별 U일 때 현지어 최소 `L/T ≥ 60%`, 한국어 최대 `(K+U)/T ≤ 10%`이고 판별 가능 본문 100개 이상·미판별률 10% 이하를 요구합니다. 모두 파일럿 가설 값입니다.

장소 전체를 추정하는 `population_estimate`는 별도입니다. 전수 또는 표본 설계 검증이 필요하며 최신순 자료에 Wilson 구간을 붙여 전체를 대표한다고 하지 않습니다. 원문·중복·미판별 처리, 통계 예시와 기능 활성화 조건은 [리뷰 데이터 명세](REVIEW_DATA_SPEC.md)를 기준으로 구현합니다.

한국어 관측이 0건이어도 전체에 대해 “한국어 리뷰 없음”으로 표현하지 않습니다. 수집 기간과 범위를 좁게 명시합니다.

다언어 국가는 도시별 허용 언어 집합을 명시합니다. 도쿄는 `ja`, 바르셀로나는 `es`와 `ca`를 초기 집합으로 삼고 원문 태그와 정규화한 언어를 함께 보존합니다. 스페인어 사용자가 바르셀로나 주민이라는 뜻은 아닙니다. 영어권에서는 언어로 현지 선호를 구분하기 어렵다는 제한을 표시합니다. 한국 여행에서는 이 한국어 감소 조건을 적용하지 않습니다. 모르는 언어는 현지어로 편입하지 않습니다.

### 순위 결정

먼저 권한·지점 일치·폐업·명시적인 식단 또는 인원 불일치를 검사합니다. 방문 시간에 영업이 불가능한 장소는 그 시간대 추천에서 제외합니다. 정보가 없으면 `불가능` 대신 `미확인`으로 분리합니다.

초기 순위는 이용 가능한 자체·허가 데이터로 계산합니다. 각 점수는 0~1이고 결측값을 좋은 점수로 처리하지 않습니다.

| 유형 | 제안 가중치 |
| --- | --- |
| 현지 탐색 | 지역 근거 35%, 취향 25%, 동선 20%, 방문 조건 확인도 10%, 가격 적합도 10% |
| 대표 명소 | 대표성 근거 30%, 취향 25%, 동선 20%, 방문 조건 확인도 15%, 가격 적합도 10% |

대표성 근거는 공식 관광기관의 주요 명소 소개, 문화기관 정보 등으로 정의합니다. 두 유형 모두 지역·음식 종류가 과도하게 겹치지 않도록 다양성을 적용합니다. 추천 이유에는 가장 강한 근거 2~3개와 중요한 미확인 조건을 함께 보여줍니다.

Google 콘텐츠를 자체 점수·LLM·영구 DB에 자유롭게 사용할 수 있다고 가정하지 않습니다. 초기에는 독립 근거로 후보와 순위를 만들고 Google 상세 정보는 별도 표시합니다. 리뷰 평점·개수 필터나 Google 기반 계산은 해당 이용 방식의 계약·정책 검토 후 별도 기능 플래그로 연결합니다. 구체적인 경계는 [데이터와 운영 검토](DATA_AND_OPERATIONS.md)에 있습니다.

### 추천 엔진의 실행 단계

후보 발견과 최종 추천을 분리합니다. 후보팩·사용자 보관함·허용된 검색 공급자에서 후보를 찾고, 지점 ID를 정규화한 뒤 지점 검증을 수행합니다. 한 요청에서 무제한으로 웹을 검색하지 않고 후보 발견 상한과 상세 조회 상한을 따로 둡니다.

1. **범위 확정:** 여행 구간, 방문일·시간대, 기준 위치, 인원과 조건 버전을 고정합니다.
2. **후보 구성:** 검증한 도시 후보팩과 사용자 저장 장소를 합칩니다. 기존 후보로 충분하면 새 검색을 생략합니다.
3. **지점 대조:** 이름만 같은 다른 지점을 병합하지 않습니다. 주소·외부 ID·공식 링크의 일치 여부를 확인합니다.
4. **필수 제약:** 폐업, 방문 시각 불가, 명시적 인원·식단 부적합, 사용자가 제외한 장소를 검사합니다.
5. **자료 자격:** 권한, 만료, 리뷰 관측 모드와 분류 품질을 확인합니다. 미확인은 필터 상태로 남깁니다.
6. **순위 계산:** 사용할 수 있는 신호만 대상으로 버전이 고정된 점수 모델을 적용합니다.
7. **다양성:** 동일 지점·동일 체인·같은 종류에 과도하게 집중하지 않도록 후보를 조정합니다.
8. **설명 생성:** 서버가 선정한 이유를 근거와 함께 한국어로 설명합니다. LLM이 점수·인원 적합성을 변경하지 않습니다.
9. **저장과 갱신:** 추천 입력·모델·출처 버전을 기록하고 여행 조건이 바뀌면 이전 결과임을 표시합니다.

리뷰 이용 조건까지 통과한 `local_observed_v1`의 실험 가중치는 언어 신호 25%, 지역 편집 근거 20%, 취향 20%, 동선 15%, 같은 플랫폼 품질 10%, 방문 조건 확인도 10%입니다. 원래 편집 근거 중심 모델은 `local_editorial_v1`로 유지합니다. 데이터가 없는데 일부 점수를 조용히 재분배하지 않고 어떤 모델로 추천했는지 기록합니다.

각 성분은 0~1 범위이며 함수와 입력을 버전 관리합니다. 지역 근거는 검증된 독립 출처와 직접 확인 수준으로, 취향은 명시한 선호 태그·가격 범위로, 동선은 확인된 이동 또는 명시한 추정으로 평가합니다. 좌표가 없으면 동선 성분은 null이고 `동선 미확인 후보`로 별도 표시합니다. 사용자가 이동거리 제한을 필수로 둔 경우 해당 후보를 자동 일정에 넣지 않습니다.

평점이 사용 가능한 경우 소수 평가로 생긴 5.0점과 많은 평가의 4.5점을 단순 비교하지 않도록 보정 점수를 실험할 수 있습니다. 같은 플랫폼·도시·업종에서 `Q=(v×R+m×C)/(v+m)`을 사용하고, R은 장소 평점, v는 평가 수, C는 비교 집단 평균, m은 사전 가중치입니다. m=50은 실험값이며 비교 집단이나 사용 권한이 없으면 이 보정은 비활성입니다. 서로 다른 사이트 별점을 같은 값으로 합치지 않습니다.

사용자에게 내부 종합 점수를 주민 비율이나 추천 성공 확률처럼 표시하지 않습니다. 실제 선택에 도움이 되는 근거와 제약을 보여주고, 가중치는 평가셋·저장율·방문 후 피드백으로 조정합니다.

| 인원 | 예약 1건 최대 인원, 최소 인원, 아동·연령 규칙, 단체 문의 기준 | 현재 여행 인원과의 적합 여부 |
| 시설 정원 | 식당 총 좌석 또는 시설 수용 정원 | 자료가 있을 때 별도 항목으로 표시 |
| 가격 | 통화, 성인·아동·시간대 구분, 세금·수수료 확인 여부 | 범위 또는 확인된 가격과 기준일 |
| 실시간 자리 | 조회 인원·날짜·시간, 공급자 확인 시각, 상태 | 연결 전에는 항상 미확인 |

모든 사실은 `value`, `status`, `source_id`, `checked_at`, `valid_for_date`를 가집니다. `status`는 `verified`, `provisional`, `unknown`, `conflict` 중 하나입니다. `null`은 0이나 제한 없음과 다릅니다. 상세 링크를 확보해도 읽지 못한 내용은 검증된 사실이 아닙니다.

출처끼리 충돌하면 해당 날짜에 적용되는 시설·공식 예약 페이지를 우선 확인하고 충돌을 보존합니다. “좌석 20석”에서 “20인 예약 가능”을 추론하지 않습니다. `reservable=true`와 `goodForGroups=true`도 원하는 시간의 자리나 숫자 인원을 보장하지 않습니다.

먼 날짜의 영업시간은 통상 영업표를 바탕으로 한 잠정 정보입니다. Google의 `currentOpeningHours`는 오늘을 포함한 7일 범위이므로 먼 여행 날짜를 검증했다고 표시하지 않습니다. [공식 Place 자료형](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places)

## 일정 생성 규칙

입력은 여행 날짜·시간대, 항공·숙소·투어 등 고정 예약, 선택한 장소, 하루 활동 시간, 이동수단, 식사·휴식 선호입니다. 숙박 기간 전체를 활동 불가 시간으로 막지 않고 체크인·체크아웃 제약과 숙소 위치로 모델링합니다. 항공 출발·도착 시간대는 각각 보존합니다.

생성은 다음 순서로 수행합니다.

1. 사용자가 확정한 예약과 직접 고정한 일정을 잠급니다.
2. 날짜별 빈 구간을 만들고 장소의 허용 방문 시간과 대조합니다.
3. 같은 지역을 묶고 이동 시간, 체류 시간, 휴식과 버퍼를 더합니다.
4. 제약을 만족하는 초안을 계산하고 코드로 다시 검증합니다.
5. 배치하지 못한 장소와 사유를 반환합니다. 예약이나 영업 조건을 임의로 바꾸지 않습니다.

초기 알고리즘은 지역별 묶음과 탐욕적 삽입으로 충분합니다. LLM이 시간표를 단독 생성하지 않습니다. 이동시간 API가 없거나 실패하면 허용된 좌표가 있을 때만 거리 기반 추정을 제공하고 교통 시간으로 확정하지 않습니다. 좌표도 불분명하면 동선 점수·시간을 만들어내지 않고 `미확인`으로 남깁니다. 교통이 확인되지 않은 구간은 `잠정`입니다.

식사 60~90분, 관광 60~120분, 일반 이동 버퍼 15분 등은 사용자 수정 가능한 **기획 기본값**입니다. 식사 시간대를 전 세계에 동일하게 강제하지 않습니다. 도쿄의 `Asia/Tokyo`와 JPY, 바르셀로나의 `Europe/Madrid`와 EUR를 지원하고 서머타임은 IANA 시간대로 처리합니다. 항공·공항 이동과 예약 체크인 버퍼는 별도 설정하며 임의의 공통 15분으로 대체하지 않습니다.

일정 저장은 미확인 항목이 있어도 허용하되, `확인 필요` 상태를 보존합니다. 시간 충돌이나 명시적인 휴무가 있는 초안을 `방문 가능 검증 완료`로 확정할 수 없습니다. 변경 시 고정 항목을 건드리지 않고 영향을 받은 구간만 재계산합니다. 동시 수정은 버전 충돌로 알립니다.

## 데이터와 API 설계

초기에는 단일 인스턴스에서 SQLite를 구조화 데이터의 기준으로 쓰고 Chroma는 예약 검색용 파생 인덱스로 유지합니다. 두 저장소는 하나의 트랜잭션이 아니므로 문서·인덱스 generation을 `staged/active`로 관리하고 준비된 버전만 활성화합니다. 중단 후에는 이전 활성 버전을 유지하거나 안전하게 재개합니다. 파일 원문은 접근 통제된 영구 저장소에 둡니다. 공개 가입·다중 인스턴스 전환 전 관리형 PostgreSQL과 객체 저장소로 이관합니다.

| 엔터티 | 핵심 내용 |
| --- | --- |
| User / TripMember | 인증 주체와 여행 소유·접근 권한. 첫 버전은 여행 공유 미지원 |
| Trip | 소유자, 목적지, 날짜, 시간대, 인원, 예산, 선호, version |
| Booking / SourceDocument | 여행 ID, 예약 사실, 원문 참조, 해시, 추출 상태, 사용자 수정 이력 |
| PlaceIdentity | 내부 ID, 공식 지점명·주소, 허용된 geo_point와 정확도·출처·확인 상태, 외부 ID 연결 |
| EvidenceSource / PlaceFact | 출처 유형·URL·발행일·확인일·유효기간·권한과 필드별 사실 |
| ResearchCandidate | 추천 유형, 지역 근거, 독립 출처 수, 품질 상태 |
| ReviewCollectionRun / ReviewLanguageObservation | P1 조건부. 공급자·범위·방식·기간·언어별 수·판별 불가 수·권한, 관측과 전체 추정 모드 분리 |
| RecommendationRun | 여행 조건 버전, 결과 내부 ID, 허용된 점수 근거, 비용·실패 상태 |
| Itinerary / ItineraryItem | 버전, 날짜·시간대, 시작·종료, 고정 여부, 이동·체류, 검증 상태 |
| Job / UsageLedger | 사용자·여행, idempotency key, 상태·lease·시도 수·예상 및 실제 비용 |

`PlaceIdentity`는 모든 공급자 데이터를 영구 복제하는 테이블이 아닙니다. Google ID 외 정보는 보관 권한이 확인된 출처에서 가져옵니다. 라이브 공급자 응답은 별도 DTO로 분리하며 권한이 없으면 저장·로그·임베딩하지 않습니다.

제안 API는 `/api/v2` 아래에 둡니다. 기존 전역 API는 인증과 여행 범위가 적용되기 전 외부 베타에 노출하지 않습니다.

| API | 역할 |
| --- | --- |
| `GET /trips`, `POST /trips`, `GET /trips/{id}`, `PATCH /trips/{id}` | 여행 목록·생성·조회·수정 |
| `GET /trips/{id}/bookings`, `PATCH /trips/{id}/bookings/{booking_id}`, `DELETE /trips/{id}/bookings/{booking_id}` | 예약 목록·교정·개별 삭제 |
| `POST /trips/{id}/documents`, `GET /jobs/{id}` | 비동기 업로드와 상태 확인 |
| `POST /trips/{id}/recommendations` | 조건을 검증하고 추천 작업 생성, 202 반환 |
| `GET /trips/{id}/recommendations/{run_id}` | 완료·부분 완료 결과 조회 |
| `GET /trips/{id}/places/{place_id}` | 여행 조건에 맞춘 상세와 공급자 정보 표시 |
| `POST /trips/{id}/itineraries` | 초안 생성 작업 요청 |
| `GET /trips/{id}/itineraries/{itinerary_id}` | 저장된 일정 조회 |
| `PATCH /trips/{id}/itineraries/{itinerary_id}` | 버전을 지정해 편집 |
| `POST /trips/{id}/ask` | 해당 여행의 예약·리서치 근거로 답변 |
| `DELETE /trips/{id}` | 원문·구조화 기록·인덱스·작업 참조 삭제 |

서버는 요청의 `user_id`를 신뢰하지 않고 인증 세션에서 소유자를 결정합니다. 모든 조회·작업 상태·다운로드에 동일한 권한을 적용합니다. 외부 URL 검색에는 예약번호·이메일 원문·전화번호를 보내지 않고 필요한 도시·날짜·인원 조건만 보냅니다.

## 신뢰성과 운영 요구

- 유료 인스턴스와 영구 디스크를 사용하고 사용자 모드는 `SEED_ON_EMPTY=0`으로 운영합니다. 데모는 별도 환경입니다.
- 업로드·추천·일정 작업은 DB에 기록합니다. 재시작 후 미완료 작업을 재시도하고 동일 요청이 중복 데이터나 무제한 과금을 만들지 않게 합니다.
- 웹 검색 또는 장소 공급자가 실패하면 기존 예약·저장 일정은 계속 열립니다. 부분 결과와 실패한 항목을 함께 반환합니다.
- LLM·검색·지도 호출에 시간 제한, 최대 호출 수, 사용자별 일일 한도와 전역 한도를 둡니다. 예산 알림과 실제 호출 차단을 구분합니다.
- `live`와 `ready` 상태를 구분합니다. 준비 상태는 DB·저장소 접근을 검사하며 외부 유료 API를 매번 호출하지 않습니다.
- 로그에는 메일 원문·예약번호·토큰을 남기지 않습니다. 공개 연구 원문 속 지시는 데이터로 처리합니다. 사용자 history의 역할은 user/assistant만 허용합니다.
- 삭제는 재인덱싱 큐까지 반영합니다. 백업에서 삭제 데이터가 즉시 사라지는지 여부와 보관 기한을 문서화합니다.

초기 성능 목표는 정상 상태에서 여행·일정 조회 p95 1초 이내, 비동기 요청 접수 2초 이내, 추천 첫 결과 20초·최종 결과 60초 이내입니다. 실측 전 목표이며 보장 수치가 아닙니다. 부하 테스트 조건은 동시 활성 사용자 5명과 문서·추천 작업 각 1개로 시작합니다.

### 베타 품질 목표

고정된 평가 여행 10개와 실패 사례를 포함한 최소 30개 시나리오를 운영합니다. 추천 장소의 지점 일치, 사실별 출처, 일정 충돌을 사람이 검토합니다. 실제 공급자 데이터 수집은 이용 가능 범위에서만 합니다.

- 미확인 인원·좌석·리뷰 비율을 확정한 사례 0건.
- 사용자가 확정한 예약을 자동 변경한 사례 0건.
- 추천 이유의 사실 문장에 검증 가능한 출처 연결 100%.
- 시간 충돌 검증 시나리오 통과 100%.
- 상위 5개 추천 중 사용자가 최소 1개 저장한 세션 비율 60%를 초기 제품 가설로 측정.
- 현지 탐색 만족도는 방문 후 “기대했던 분위기였는가”로 수집. 실제 주민 비율 조사로 해석하지 않음.
- 회당 비용·처리시간·정보 부족률을 측정하고 권장 예산 안에서 돌아가는지 판단.

샘플이 적을 때 비율만 보고 성공을 선언하지 않고 분자·분모와 기간을 함께 기록합니다.

## 데이터 신선도와 비용 관리

추천 목록은 가능한 한 준비된 후보팩과 유효한 근거로 응답합니다. 대기 시간이 긴 크롤링은 별도 작업으로 표시하고, 사용자 요청 한 번이 전체 도시 재수집을 유발하지 않게 합니다.

| 정보 | 제품상 갱신 제안 | 만료 시 동작 |

| 최근 리뷰 집계 | 활성 여행 후보 주 1회 또는 명시적 갱신 | 마지막 관측 시각 표시, 엄격 배지 보류 |
| 영업시간·예약 규칙 | 일정 작성 시 확인, 방문이 가까워졌을 때 재확인 | provisional로 전환, 확인 업무 생성 |
| 실시간 슬롯 | 공급자 유효시간 | 만료 즉시 미확인. 예약 가능으로 유지하지 않음 |
| 이동시간 | 날짜·이동수단·경로가 바뀌면 계산 | 기존 시간은 추정/과거 값으로 표시 |

위 표는 제품 운영 주기 제안이며 데이터 보관 허가가 아닙니다. 실제 보관·갱신은 공급자별 허용 기간과 호출 예산 중 더 엄격한 조건을 따릅니다. 갱신·알림 기능을 기획했다고 현재 사용자의 계정에 자동 스케줄을 생성하지 않습니다.

초기 예산은 고정 서버와 AI·검색·수집 변동비를 분리합니다. 수집 도구의 최소 결제액과 무료 크레딧을 실제 사용량 단가와 구분합니다. 장면별 예산은 신규 후보팩 구성, 추천 조회, 상세 조회, 수집 갱신, 일정 재계산으로 나눠 기록합니다. 사용자가 버튼을 여러 번 눌러도 idempotency와 공개 집계 재사용으로 중복 과금을 줄입니다.

## 출시 단계와 개발 순서

`연구 통과`와 `제품 출시`를 같은 상태로 취급하지 않습니다. 리뷰 수집이 되더라도 원문·비용·권리·품질 조건이 부족하면 최근 리뷰 필터의 제품 활성화는 보류할 수 있습니다. 다른 기능의 출시를 막는 이유와 기능별 보류 이유를 분리합니다.

| 릴리스 | 포함 범위 | 통과 기준 |
| --- | --- | --- |
| R0 데이터·기술 검증 | 현재 예약 회귀, 수집 6곳 smoke와 10곳 검증, 언어 품질·권한 확인 | 실험 결과와 비용·한계 재현 가능 |
| R1 비공개 핵심 베타 | F01~F05·F07 핵심, F09~F10, 기본 F14. F06은 다음 행의 조건부 기능 | 본인·지인 격리, 두 추천 구획, 상세·일정·복구 테스트 통과 |
| R1 조건부 언어 기능 | F06 observed_window | 데이터 이용·원문·범위·언어 품질 gate 통과 |
| R2 여행 실사용 보강 | F08, F11, F12, F13과 오류 신고 | 예약 업무·대안·오프라인·가격 미확인 동작 검증 |
| R3 공유·확장 | 동행 투표, 다도시 커버리지, 고급 공급자 | 공유 권한·비용·관측 지표 기준 재설계 |

개발 패키지는 안정화 → 인증·여행·영구 작업 → 수집·언어와 근거 → 추천·상세 → 일정·편집 → 배포·복구 순서입니다. 데이터 공급자 검증은 안정화와 병행합니다. 예약 할 일·대안·오프라인은 핵심이 통과한 뒤 붙입니다.

작업량은 1인 기준 핵심 베타 약 4~6주, 실사용 보강까지 약 6~10주를 **범위 추정**으로 둡니다. 학습 시간, 공급자 계약, 실제 데이터 검증 대기와 피드백 반영은 별도입니다. 이전의 좁은 기능 범위 추정을 이번 확장 범위의 납기로 사용하지 않습니다.

세부 구현 계약은 [기술 명세](TECHNICAL_SPEC.md), 검증 항목은 [인수시험](ACCEPTANCE_TESTS.md), 실행 요청은 [개발 프롬프트](IMPLEMENTATION_PROMPTS.md)를 연결합니다. 해당 문서와 PRD가 충돌하면 현재 코드·사용자 요구를 확인하고 결정 기록을 갱신한 뒤 구현합니다.
