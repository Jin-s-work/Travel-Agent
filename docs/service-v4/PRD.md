# 고잉 v4 PRD — 리뷰로 발견하고, 내 여행에 연결하기

작성: 2026-10-07 · 상태: 구현 전 기획 · 대상: 본인과 초대한 소수 지인

이 문서는 현재 구현을 폐기하는 재설계가 아니다. 인증·여행·메일·예약·보관함·추천·일정·작업·비용·피드백을 재사용하면서, 실제 연결 결함을 해결하고 제품의 차별점을 완성한다. 검증 근거는 [AUDIT.md](AUDIT.md), 판정은 [ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md), 실행은 두 [구현 프롬프트](prompts/01-reliable-journey.md)로 분리한다. 이 문서의 목표 수치는 달성 실적이 아니다.

## 1. 제품이 약속할 가치

**고잉은 최근 원문 리뷰의 언어 근거로 식당을 발견하고, 유명한 장소도 함께 고른 뒤, 내 숙소·예약·일정에 연결하는 여행 서비스다.**

사용자는 다음 두 질문을 독립적으로 해결한다.

1. “한국어 후기가 많은 곳 말고, 현지어 후기가 충분히 쌓인 식당을 찾아보고 싶어요.”
2. “그래도 이 도시에 왔으니 유명한 식당과 꼭 가볼 만한 명소는 놓치고 싶지 않아요.”

핵심 경험은 `현지어 리뷰로 찾기`와 `유명한 곳`이다. 음식점·카페·볼거리는 추천 방식과 별개의 종류다. 유명한 식당도 두 번째에 들어갈 수 있고, 검증을 모두 통과한 장소는 두 구획에 다른 이유로 등장할 수 있다.

현지어 리뷰는 거주지 조사가 아니다. 일본어 작성자는 일본어를 쓰는 관광객일 수 있고, 스페인어 리뷰는 바르셀로나 주민만의 리뷰가 아니다. 서비스가 검증할 것은 **관측한 원문 리뷰의 구성**이며 “현지인 80%”, “한국인 없는 식당”, “주민 인증 맛집”을 만들지 않는다. 사용자에게는 이 한계를 긴 경고문 대신 근거 옆 한 문장으로 알려준다.

## 2. 현재 상태와 해결 순서

이미 존재하는 기능을 새로 만드는 작업으로 포장하지 않는다.

| 영역 | 현재 확인한 상태 | 이번 결정 |
| --- | --- | --- |
| 기본 여행 관리 | 인증·소유권·메일 추출·교정·작업 상태·새로고침 복원 기반 존재 | 유지하고 대표 회귀 흐름 검사 |
| 장소 추천 | 공식 후보와 공개지도 후보, 현지 탐색/대표 명소 구획 존재 | 거짓 0건과 일정 연결 문제 먼저 해결 |
| 숙소와 거리 | 숙소 모델·원점·직선거리·경로 계약 존재 | 숙소 주변 후보가 실제 수집·선별 범위에 들어가게 연결 |
| 일정 | validator·preview/apply/undo 존재 | 공개지도 후보의 잠정 배치와 날짜 맥락 연결 |
| 리뷰 분석 | Apify/fake 어댑터·집계·평가·운영 화면 존재 | 지점 연결 및 실제 공급자 계약/도시별 품질 경로 완성 |
| 엄격 언어 추천 | 현재 운영 OFF, 실제 음식점 리뷰 평가 완료 근거 없음 | 설정 하나로 켜지 않고 단계별 증거 통과 후 활성화 |
| 도시 | 100개 도시 입력 가능. 자료 수준은 도시별로 다름 | 입력 지원·장소 검색·검수·언어 검증을 각각 표시 |
| 운영 | Render Free + Supabase, 장기 작업과 예산 기반 존재 | 저장 데이터 읽기 성능·정리 작업 진행성 우선 개선 |
| 화면 | 고잉 이름·현재 색·Pretendard·직접 선택 필터가 이미 있음 | 브랜드 재변경보다 맥락 유지와 다음 행동 개선 |

감사에서 재현한 문제는 크게 세 종류다.

- **연결:** 공개지도 후보가 추천 카드에는 있지만 잠정 일정 생성에서 404, 카탈로그 지점과 리뷰 수집 지점의 연결 부족.
- **선별:** 사용자 조건 평가 전에 12개 후보로 자르는 문제, 식당 자료 때문에 카페 수집을 생략하는 문제.
- **체감:** 읽기 경로의 반복 SQL·정리 작업, 무관한 정책 변경으로 과거 결과 유실, 탐색 선택/날짜 맥락 유실.

1단계에서 여행 흐름의 연결과 성능을 바로잡고, 2단계에서 리뷰 차별점과 유명 장소 구획을 실제 데이터 계약에 연결한다. 1단계를 통과하지 못한 항목을 2단계에서 완료했다고 처리하지 않는다.

## 3. 범위와 비범위

### 포함

- 기존 흐름 안정화와 의미 있는 상태·복구 안내.
- 사용자 조건에 맞는 후보 구성, 숙소 원점, 부분 갱신.
- 두 추천 방식과 독립적인 장소 종류 필터.
- 공식 지점과 리뷰 공급자 ID 연결, 검증 이력.
- 원문 언어 관측 근거를 카드·상세·비교·일정까지 전달.
- 유명 식당과 명소의 출처 기반 선정.
- 작은 실제 파일럿과 재실행 가능한 평가 도구.
- 모바일·키보드·날짜/인원 수정·탐색 맥락 보존.

### 제외

- 기존 UI 전체 재작성, 새 프레임워크로의 일괄 이전.
- 자동 결제·자동 예약·메시지 발송·외부 예약 취소.
- 모든 도시의 리뷰를 미리 전수 수집하는 작업.
- 언어로 작성자의 국적·거주지·민감한 속성 추정.
- 추천 클릭마다 리뷰 재수집, 모든 리뷰의 LLM 분류.
- 별점·언어 조건의 무단 완화, 합성 카드로 실제 지원 도시 확대.
- 무료 호스팅에서 항상 즉시 응답한다는 약속.
- 이 기획 작업 자체에서 계정 생성·유료 실행·배포.

## 4. 사용자 흐름

### 흐름 A: 여행을 처음 만들 때

1. 도시, 시작일·종료일, 인원을 입력한다. 연도는 네 자리로 검증하고 잘못된 입력을 보존한다.
2. 숙소는 선택 입력이다. 기존 예약에서 추출된 숙소는 “이 숙소를 기준으로 찾기”로 확인받는다.
3. 여행 생성 후 `예약 가져오기`와 `장소 찾아보기`를 나란히 제공한다. 둘 중 하나가 다른 하나의 필수 절차가 아니다.
4. 탐색은 해당 여행 날짜·도시·인원을 자동으로 사용한다. 체류 구간이 애매하면 해당 날짜/도시만 짧게 수정한다.
5. 선호를 입력하지 않았다는 이유로 전체 순위가 자료 부족에 빠지지 않도록, “선호 미지정”을 지원하는 별도 버전 모델을 설계한다. 기존 모델의 null을 1점으로 채우거나 남은 가중치를 몰래 재분배하지 않는다. 모델 변경 전후를 고정 fixture로 비교한다.

### 흐름 B: 현지어 리뷰로 식당 찾기

1. `현지어 리뷰로 찾기` 탭에 도시와 방문일, 출발점이 먼저 보인다.
2. 해당 도시의 기능 상태를 표시한다: `이용 가능`, `자료 검증 중`, `아직 지원하지 않음`, `자료 갱신 필요`.
3. 이용 가능한 경우, 기본 조건과 마지막 확인일을 요약하고 결과를 표시한다.
4. 카드에서 관측한 현지어·한국어·미판별 건수, 숙소 기준 거리, 방문 조건 미확인을 확인한다.
5. `근거 보기`에서 기간·분모·수집 종료 이유·모델/정책 버전까지 확인할 수 있다.
6. `저장` 또는 `일정에 담기`를 선택한다. 두 행동의 저장 상태를 명확히 구분한다.
7. 일정에 넣을 날짜는 탐색 방문일을 우선한다. 방문 시각은 자동 확정하지 않고 가능한 시간/미확인을 보여준다.
8. 실제 휴무·확정 예약 충돌은 차단하고, 미확인은 사용자가 동의한 잠정안에서만 허용한다.

### 흐름 C: 유명한 곳 찾기

1. `유명한 곳` 탭은 리뷰 언어 조건과 독립적이다.
2. `음식점 / 카페 / 볼거리`를 선택하면 그 종류 안에서 대표성과 여행 적합성을 설명한다.
3. `공식 대표 명소`, `공개 평가가 많은 식당`, `편집 근거가 있는 장소`의 근거 유형을 구별한다.
4. 전체 평가 수를 실시간 방문객 수나 잔여석으로 표현하지 않는다.
5. 현지어 추천이 0건이어도 유명한 곳이 영향을 받아 사라지지 않는다.
6. 조건에 맞는 후보가 부족하면 부족 사유와 사용자가 선택할 대안을 제공한다.

### 흐름 D: 자료가 아직 없을 때

- `검증된 현지어 리뷰 자료가 아직 없어요`를 표시한다. `한국어 0%` 같은 수치를 만들지 않는다.
- `유명한 곳 보기`, `주변 장소 참고하기`, `이 장소 검토 요청`을 제공한다.
- 참고 후보는 별도 제목과 설명을 사용하며 엄격 결과 목록에 섞지 않는다.
- 일반 사용자의 검토 요청은 수요 기록이다. 요청할 때마다 유료 수집을 자동 실행하지 않는다.
- 관리자 승인된 기존 유효 집계가 있으면 즉시 재사용한다. 새 수집은 job 상태로 추적한다.

## 5. 정보 구조와 UX

상위 메뉴는 기존 `여행 / 탐색 / 일정 / 예약`을 유지한다. 준비·지출·질문·리뷰 운영 등의 기존 기능 진입점도 유지한다. 새 최상위 메뉴를 늘리는 대신 사용자 행동이 필요한 위치에 배치한다.

### 탐색 화면 구조

```text
[현재 여행 · 11/7 도쿄 · 성인 2명]
[숙소 기준 ▼] [11월 7일] [2명] [조건 변경]

[현지어 리뷰로 찾기] [유명한 곳]
[음식점] [카페] [볼거리]

현지어 자료 4곳 확인 · 최근 180일 · 기준 보기
[사진 / 이름 / 핵심 근거 / 거리 / 미확인 / 저장 / 일정에 담기]

별도 참고: 아직 리뷰 언어를 확인하지 못한 주변 장소
```

- 언어 추천이 식당만 지원하는 도시에서는 카페·볼거리의 지원 범위를 명시한다. 필터를 누르면 아무 설명 없이 0건을 반환하지 않는다.
- 도시는 여행 구간에서 결정하되 변경이 필요하면 해당 항목만 수정한다.
- 인원 한 번 수정하려고 예산·음식·이동 4개 탭을 다시 거치지 않는다.
- 많은 고급 조건은 요약된 버튼으로 열고, 실제 상태 변경에는 라디오·세그먼트·칩을 사용한다. 숨겨진 구현용 checkbox를 무조건 제거하는 작업은 하지 않는다.
- 모달은 제목·닫기·초기 포커스·Escape·포커스 복귀를 보장한다.
- 화면 복귀 시 마지막 탭·필터·스크롤·선택 장소를 복원한다. 브라우저 뒤로도 단계에 맞게 작동한다.
- 공개 URL에는 여행 개인정보·좌표·세션 정보를 넣지 않는다. URL 상태는 안전한 최소 식별자만 사용한다.

### 카드와 상세

카드의 우선순위는 이름 → 추천 이유 → 중요한 미확인 → 거리/가격 → 행동이다.

- 장소 사진 최대 3장. 기존 라이선스·지점 일치 검증을 유지한다. 음식·실내 사진이 없으면 다른 지점의 사진으로 채우지 않는다.
- 원어명은 복사 가능하게, 주소·공식/지도 링크는 상세에서 제공한다.
- 이유는 최대 2~3개. “AI가 추천”보다 “판별한 190건 중 일본어 150건”처럼 근거를 쓴다.
- 수치가 복잡해지면 카드에는 건수+기간 요약, 상세에는 전체 분모와 엄격 판정을 표시한다.
- “방문 조건 확인 필요”는 무엇이 미확인인지 적는다. 예: 4인 예약, 해당 날짜 운영, 마지막 주문.
- 비교는 같은 날짜·인원 기준 최대 3곳이며, 같은 지점의 두 구획 카드는 중복 선택하지 않는다.
- 사진·언어 비중·순위·검증 상태를 한 종류의 점수나 배지에 압축하지 않는다.

| 추천 결과 확인 중 반복 정리·SQL 발생 | 읽기는 일괄 조회, 정리는 별도 작업 | 무료 환경의 대기 감소 |
| 오래된 결과가 통째로 없어짐 | 권한 있는 이전 결과를 과거 조건으로 표시, 재계산 안내 | 비교·저장 맥락 보존 |
| 수정한 예약의 대표 시각과 구간 시각이 분리 | 구간을 기준으로 일관된 교정 폼과 영향 미리보기 | 날짜별 조회/일정 시간 불일치 방지 |

## 6. 1단계: 정확한 결과와 끊기지 않는 여행 흐름

### 6.1 후보 구성

후보 순서는 `사용 가능한 데이터 범위 → 지점/종류 → 원점·거리 및 필수 조건 → 자료 자격 → 점수·다양성 → 표시 수 제한`이다.

- 도시 중심 상위 12개를 먼저 자르지 않는다. 후보를 가져오는 상한과 화면에 보여주는 상한을 분리한다.
- 숙소/수동 출발점이 선택되면 수집 범위·캐시 키·근거리 선별 기준을 모두 같은 원점 snapshot으로 묶는다.
- 공급자가 원점 기반 요청을 지원하지 않으면 해당 제한을 표시하고 지원 범위 안에서 사용한다. “숙소 주변”이라고 허위 표시하지 않는다.
- 공개 검색 캐시는 정확한 개인 숙소 좌표를 공용 키/로그에 노출하지 않는 검토된 타일 단위와 범위를 사용한다. 최종 거리 필터는 실제 사용자 원점으로 서버에서 계산한다.
- 카테고리별 유효 후보 수가 충분한지 확인한 후 추가 검색 여부를 정한다. 다른 종류의 후보 존재만으로 전체 검색을 생략하지 않는다.
- 검수 후보 100개 제한도 종류·영역·사용 가능한 근거 기준보다 먼저 적용하지 않는다. 공급자/CPU 상한과 제외 건수를 결과에 기록한다.
- 폐업·명시 휴무·인원 불일치는 점수와 관계없이 제외한다.

### 6.2 공개 후보의 일정 연결

지점 신뢰도와 방문 조건 확인 상태를 별도 모델로 유지한다.

- 지점이 식별된 공개 후보를 사용자가 잠정 초안으로 선택하면 일정 validator에 전달할 수 있어야 한다.
- 원문 영업/좌석 정보가 없으면 unknown을 그대로 전달한다. 단순히 candidate status를 approved로 바꾸지 않는다.
- strict 일정은 unknown을 미배치하고 이유를 반환한다. 잠정 일정은 명시 동의 후 provisional로 배치할 수 있다.
- 식별 자체가 모호한 다른 지점, 삭제·철회된 자료는 잠정 모드에서도 사용할 수 없다.
- preview/apply/undo 모두 같은 정책을 쓰고, 저장/적용 성공을 구별한다.

### 6.3 성능과 결과 복원

- 추천 읽기에서 `purge()`와 전역 쓰기 잠금을 제거하고 별도 만료 정리로 이동한다. 단, 조회 시 만료/권한 검사는 계속 수행한다.
- 장소 사실·출처·리뷰 근거를 일괄 조회한다. 후보 수에 비례해 connection checkout/SQL 왕복이 증가하지 않도록 한다.
- 결과 생성 전후 검증은 관련 지점·정책·모델의 버전을 비교한다. 무관한 공급자 정책 변경이 모든 결과를 지우면 안 된다.
- 유효한 예전 결과는 이력으로 보존하되 오래된 조건임을 표시한다. 권한 철회·삭제된 근거는 노출하지 않는다.
- 예약 메일 추출이 실패해도 기존 활성 예약이 유지되는 회귀 검사를 한다.
- dispatcher 승격 시 정리/유지보수 task도 시작되고, leader 상실 시 정리 side effect도 fencing으로 차단되어야 한다.
- 객체 정리는 완료된 삭제 항목 때문에 뒤 항목이 굶지 않도록 커서/안정 정렬·상태 전이를 구현한다.

### 6.4 진행 표시

실제 job 상태와 단계·처리 건수만 표시한다.

| 내부 상태 | 사용자 문구 | 행동 |
| --- | --- | --- |
| queued | 앞선 작업을 마치면 시작해요 | 기존 결과 보기 / 취소 요청 |
| 후보 확인 | 저장된 장소와 조건을 확인하고 있어요 | 현재 조건 유지 |
| 외부 수집 | 주변 장소를 찾고 있어요 | 범위·호출 단계 표시 |
| 검증/계산 | 방문 조건과 근거를 확인하고 있어요 | 처리 건수 있으면 표시 |
| partial | 일부 자료만 확인했어요 | 사용 가능한 결과·부족 이유 |
| failed | 이번 조회를 마치지 못했어요 | 동일 요청 재시도 / 조건 수정 |
| stale | 조건이나 자료가 바뀌었어요 | 이전 결과 구분 / 다시 계산 |
| budget_exhausted | 새 조회 한도에 도달했어요 | 저장된 결과·예약 계속 보기 |

새로고침은 기존 job을 복원하며 새 작업을 만들지 않는다. 가짜 백분율, 끝나지 않는 spinner, 외부 호출 없는 단계에서 “AI가 분석 중” 표시는 사용하지 않는다.

## 7. 2단계: 리뷰 차별점을 실제 추천으로 연결

### 7.1 지점 식별

기존 `place_identities`와 후보를 보존하고, 공급자별 ID를 검증된 동일 지점에 연결하는 관계를 추가한다.

필요 계약 예시:

```text
place_external_links
  id, canonical_place_id, provider, external_place_id
  status: pending / verified / rejected / revoked
  source_id, checked_at, expires_at, identity_version
  verifier_id, address_match, coordinate_match, branch_match
```

- 명칭 유사도만으로 자동 병합하지 않는다. 상호·주소·좌표·공식 링크·지점을 대조한다.
- 공급자+외부 ID의 유효 연결은 하나의 canonical 지점에만 속한다. 동시 승인 충돌을 트랜잭션으로 막는다.
- 기존 여행·보관함·일정 참조 ID를 일괄 갈아엎지 않는다. dry-run으로 매핑 후보·충돌·미확인을 보고한다.
- 리뷰 집계는 `canonical_place_id + 외부 연결 버전 + 수집 run`을 통해 연결한다.
- 연결 철회 후 이전 리뷰 배지가 남지 않아야 한다. 늦은 job 완료가 철회된 연결을 활성화하면 안 된다.
- 공용 장소 근거와 개인 여행 선택/메모는 분리한다.

### 7.2 수집과 공급자 계약

기존 `ReviewCollectionProvider`, job, 비용 예약/정산, 관리자 scope를 사용한다. 새 리뷰 job 체계를 따로 만들지 않는다.

- 첫 후보는 기존 Apify `compass/google-maps-reviews-scraper` 어댑터다. 장소 검색 Actor와 리뷰 Actor를 혼동하지 않는다.
- build 고정, 입력 스키마·정렬 의미·원문 분리·반환 필드·비용 확인 결과를 버전별 evidence record로 보존한다.
- 기본값: 최신순, 최근 180일, 최대 200개 **고유 레코드**, 별점만 있는 기록 포함, 최대 20페이지, 페이지당 최초 포함 2회 시도.
- `reviewsOrigin=google`, 키워드/별점/언어 선택 수집 없음. 표시 locale을 원문 언어로 쓰지 않는다.
- Apify dataset의 offset 페이지와 Google 원천 페이지를 구분한다. 어댑터로 통제하지 못하는 내부 페이지/재시도는 “확인 완료”로 기록하지 않는다.
- 원천 정렬·연속성이 확인되지 않으면 strict gate는 계속 닫는다. 표본 몇 개의 수작업 확인만으로 전체 연속성을 인증하지 않는다.
- 수집 기술/데이터 이용 범위/원문 품질/언어 모델/제품 활성화를 각각 관리한다.
- 공급자가 필요한 증거를 제공하지 못하면 읽기 전용 참고 집계 또는 교체 가능한 공급자 검토로 남긴다. 품질 flag를 강제로 true로 바꾸지 않는다.

### 7.3 원문·언어·집계

[기존 REVIEW_DATA_SPEC](../service-v2/REVIEW_DATA_SPEC.md)의 계약을 유지한다.

- 원문 확보, 번역만 있음, 혼합, 실제 별점-only, 추출 불명, 판별 불가를 구분한다.
- `T=본문 존재 확인`, `C=언어 판별`, `U=미판별`, `L=현지어`, `K=한국어`.
- `T=C+U`, `L+K≤C`. 분모 0은 null이다.
- 표시 비율은 `L/C`, `K/C`. 엄격 조건에는 `L/T`, `(K+U)/T`를 쓴다.
- 보수적 상하한은 미판별에 관한 범위이며 통계적 신뢰구간이나 오분류 보정치가 아니다.
- 실제 주민 수, 전체 플랫폼 리뷰 언어 비율, 전체 방문객 비율로 확대하지 않는다.

초기 가설 기준:

| 조건 | 기본값 |
| --- | --- |
| 판별 가능한 본문 | C ≥ 100 |
| 미판별 비중 | U/T ≤ 10% |
| 현지어 보수적 하한 | L/T ≥ 60% |
| 한국어 보수적 상한 | (K+U)/T ≤ 10% |
| 플랫폼 평가 | 같은 플랫폼 5점 만점 4.2 이상 |
| 플랫폼 전체 평가 수 | 200건 이상 |

평점/규모와 언어 표본 수는 별개다. 기본값은 운영 정책 버전으로 저장하며 사용자가 완화하면 **새 요청·별도 표시**다. 사용자가 변경할 수 있는 값은 현지어 비중 하한·한국어 비중 상한·평점·전체 평가 수다. C 최소값과 U/T 품질 한도, 원문·정렬·지점·이용 범위·모델 평가 gate는 사용자 완화 대상이 아니다. 언어 비중이나 평점 기준을 기본보다 완화한 결과는 현지어 탭 안의 `직접 설정한 기준` 묶음으로 표시하고 기본 엄격 통과 배지를 주지 않는다. 원문 품질·이용 권한·지점 확인 조건은 사용자의 취향 설정으로 완화할 수 없다.

예시(합성): `T200 / C190 / U10 / L150 / K4`이면 현지어 78.9%, 한국어 2.1%(판별 190건 기준), 보수적 현지어 하한 75%, 한국어 상한 7%. `K0 / U70`을 한국어가 거의 없는 장소로 확정하지 않는다.

### 7.4 언어 프로필과 100개 도시

- 도쿄 `ja`, 바르셀로나 `es+ca`를 첫 실증 대상으로 한다.
- Madrid 등 다른 도시에도 현지어 집합·모델 평가·실제 지점 연결이 필요하다. 국가 언어 하나를 모든 도시에 강제하지 않는다.
- 다언어 도시는 현지어 집합을 버전 관리한다. 한국어가 현지어 집합에 들어가는 서울처럼 `L`과 `K`가 겹치는 도시는 기존 `L+K≤C` 계약을 적용할 수 없다. 초기 “한국어 비중 낮음” 프로필은 unavailable로 두고 별도의 목적/수학 계약을 정의하기 전에는 켜지 않는다.
- 영어가 널리 쓰이는 도시에서도 영어 비중으로 주민 비율을 주장하지 않는다.
- 100개 도시에 대해 `input_supported / public_candidates / curated_candidates / review_research / language_ready / iconic_ready` 능력 상태를 관리한다. 준비되지 않은 도시에도 여행·메일·수동 예약 기능은 계속 제공한다.
- 첫 실증은 도쿄·바르셀로나에 집중하고 사용자가 저장/요청한 도시 순서로 확대한다. 전 도시의 빈 탭을 숨기고 지원하는 척하지 않는다.

### 7.5 언어 모델 평가와 출시 gate

기존 Lingua 기반 판별기를 우선 재사용한다. 일반 문장 진단과 실제 음식점 리뷰 평가는 별개다.

- 권한 있는 실제 원문 리뷰를 개발/조정용과 최종 평가용으로 분리한다.
- 도시별 최소 100개 독립 평가 리뷰, 원문 대조 20개 이상, 한국어 정답 사례를 포함한다.
- 한국어 표본이 적으면 보충된 언어 평가 corpus를 별도로 만든다. 이 corpus는 정확도 평가용이며 장소 언어 비중 계산에 섞지 않는다.
- 현지어 precision·한국어 recall 각각 95%를 초기 목표로 사용하되 TP/FP/FN·실제 분모·unknown·불일치 사례를 함께 보고한다. 지표별 최소 분모는 초기 정책으로 `한국어 정답 50건`, `현지어 정답 50건`, `현지어로 판정한 50건` 이상을 제안한다. 도시별 전체 평가 100건 조건과 함께 적용하고 정책 버전으로 관리한다. 이 표본 수가 통계적 보장을 뜻하지는 않는다. 정책 미설정·분모 미달이면 통과할 수 없으며 한국어 1건을 맞힌 100%를 출시 근거로 쓰지 않는다.
- 번역/원문 오인, 짧은 메뉴명, 이모지, 혼합 언어, 일본어 한자 단문, es/ca 혼동을 포함한다.
- 모델 버전·라이선스·메모리·지연을 기록한다. 무료 앱 서버에서 감당 못 하면 별도 배치 결과만 적재하는 방식을 비교한다.
- 실제 조건을 통과한 도시·업종·모델·공급자 build만 활성화한다. ON/OFF는 전 세계 공통 하나의 불리언에만 의존하지 않는다.

### 7.6 유명한 곳의 선정

현재 `landmark` 계약을 버전 호환으로 확장한다. UI 이름은 `유명한 곳`이며 식당도 포함한다.

- `official_landmark`: 관광청·시설 공식 자료의 대표성 근거.
- `platform_popular`: 같은 플랫폼의 평가 규모와 평점, 확인일·비교 범위.
- `editorial_recognition`: 허용된 편집 자료의 명시적 선정 근거와 출처.
- 관광지라는 카테고리만으로 대표성이 확인된 것으로 간주하지 않는다.
- 지도 검색 상위 노출이나 OSM 등록 자체를 유명함의 증거로 쓰지 않는다.
- 실제 방문객 통계가 있으면 별도 항목으로 보존하되, 평가 수와 혼합하지 않는다.
- 순위는 해당 구획 안에서만 비교하고 현지어 조건을 자동 적용하지 않는다.
- 리뷰 자료가 없다면 공식 대표성으로 추천할 수 있지만, 음식점의 플랫폼 인기 점수를 임의로 채울 수는 없다.
- 베타 목표: 파일럿 도시별 검수 후보 6곳 이상(유명 음식점 3 + 볼거리 3)을 준비하되 실제 부족하면 부족 수를 보고한다. 수량을 채우기 위한 근거 없는 승인은 금지한다.

### 7.7 추천 모델과 설명

- `local_observed_v1`: 언어25/지역근거20/취향20/이동15/플랫폼품질10/방문조건10.
- `local_editorial_v1`: 지역근거35/취향25/이동20/방문조건10/가격10. 주변 참고 또는 별도 편집 후보에 사용하며 현지어 검증 배지를 주지 않는다.
- `iconic_v1`: 대표성30/취향25/이동20/방문조건15/가격10.
- 기존 movement v2가 적용된 입력은 호환해 보존한다. 모델 버전 이름을 되돌리지 않는다.
- 필요한 성분이 없으면 null/부족 이유. 언어 기준을 통과했어도 모든 추천 점수가 완성된 것은 아니다. `언어 조건 통과 · 방문 확인 필요`처럼 두 상태를 함께 보여준다.
- 선호 미입력 모델이 필요하면 명시적 새 모델로 정의·평가한다. null을 유리하게 대체하지 않는다.
- 점수는 내부 설명 도구이며 사용자에게 과도한 소수점 종합점수로 신뢰를 유도하지 않는다.
- LLM은 서버 후보·순위·근거를 설명하는 용도만 사용한다. 새로운 가게·리뷰 수·영업·잔여석을 만들면 validator가 거절하고 템플릿으로 복구한다.

## 8. 상태·API·저장 계약

아래는 제안 계약이다. 기존 API와 스키마를 먼저 조사하고 이미 있는 필드를 재사용한다. 새 이름은 마이그레이션 설계 후 확정한다.

| 계약 | 필수 정보 |
| --- | --- |
| 탐색 context | owner 서버 결정, trip_id, city/stop, visit_date, party, origin/version, category, discovery_mode, conditions_version |
| 결과 section | mode, eligibility_state, items, reference_items, reason_counts, data_as_of, run_id, policy/model version |
| 리뷰 근거 | canonical_place_id, external_link_version, run_id, T/C/U/L/K, observed_window, order basis, stop reason, computed/expiry, gates |
| 도시 능력 | city_id, category, capability, state, source/version, ready_count, last_checked, missing_reasons |
| 사용자 초안 | trip_id, owner_id, version, selected_place_ids, context, expires_at, updated_at |
| 검토 요청 | actor scope, place/city/category, reason, dedupe key, state, created_at; 원문/개인 메모 없음 |
| 관리자 큐 | 기술·이용·지점·원문·언어·신선도 상태, 비용 예약/정산, job/remote 참조 |

추천 결과 status와 job status는 다르다. job succeeded지만 엄격 결과 0일 수 있고, 카드가 있어도 방문 적합성이 provisional일 수 있다.

읽기 API는 저장된 데이터를 반환하며 유료 수집을 시작하지 않는다. 생성 API는 Idempotency-Key를 사용한다. 공급자 수집은 관리자 scope 또는 허용된 요청→관리자 승인 경로를 거친다. 타 사용자 ID 접근은 404, owner_id는 서버에서 결정한다.

## 9. 비용·운영 정책

### 원칙

유효 집계를 공유 재사용하고 필요할 때만 갱신한다. 여행 조건 변경으로 리뷰를 다시 수집하지 않는다. 같은 지점의 리뷰 한 번 수집이 여러 사용자에게 쓰이더라도 개인 메모·숙소·여행 정보는 공유 데이터에 넣지 않는다.

- 공급자 run 시작 전 원자적 예산 예약, 시작 응답 유실은 unknown, 자동 새 run 금지.
- 무료 크레딧은 남아 있는지 확인해야 하며 지출 승인이 아니다.
- 기존 OpenAI 분석 예산 승인을 리뷰 공급자 예산 승인으로 확대하지 않는다.
- API 운영비와 여행 예상 지출을 분리한다.
- 수집/언어 판별은 추천 HTTP 읽기와 분리하고 기존 단일 dispatcher 동시성 정책을 따른다.
- 매일 자동 수집보다 TTL+수요+관리자 검토 우선순위를 사용한다. 만료 전 갱신 실패 시 이전 자료의 마지막 확인일을 유지하고 엄격 자격은 만료 처리한다.
- raw 리뷰·작성자 프로필·예약 원문을 일반 로그나 예약 검색 벡터에 넣지 않는다.

### 파일럿

| 단계 | 최대 범위 | 확인할 것 | 다음 단계 조건 |
| --- | --- | --- | --- |
| 오프라인 | 기존 합성 24사례 + 신규 연결/오류 fixture | 계산·상태·지점 연결·UI | 전체 계약 통과 |
| A 기술 smoke | 6곳 × 100레코드 | 원문/번역/비용/종료·지점 | 실패 이유 확인, 허용 비용 내 |
| B 품질 | 10곳 × 200레코드 | 도시별 독립 라벨·정렬·원문·strict | 모든 gate의 증거 |
| 제한 베타 | 통과한 도시/업종만 | 실제 이유·저장·일정 채택 | 미측정 지표를 성과로 만들지 않음 |

A+B는 최대 2,600레코드의 수집 계획이다. 같은 지점이 중복될 경우 유효한 결과 재사용을 고려한다. 최종 가격·무료 잔액·최소 결제·세금·시작/저장/읽기/재시도 비용은 실행 직전에 확인한다. 기존 문서의 $3은 제안 상한이며 자동 실행 권한이 아니다.

현재 공식 페이지는 Places API 리뷰 최대 5개를 명시하지만, 이는 해당 API의 한도이며 웹 수집의 기술적 상한은 아니다. Apify는 별도 리뷰 수집과 원문/번역 필드를 문서화한다. 그러나 공개 페이지나 공급자 결제만으로 수집·저장·집계·표시 권한까지 확인된 것으로 취급하지 않는다. 관련 확인 경로는 [외부 근거](AUDIT.md#외부-공식-근거)에 정리했다.

## 11. 추가 기능 우선순위

이미 구현된 ICS·Plan B·오늘 보기·피드백·예상 지출을 다시 신규 기능으로 추가하지 않는다. 먼저 아래 하나씩 가치를 검증한다.

| 순서 | 제안 | 관측 근거와 사용자 가치 | 비용/데이터 의존성 | 범위 |
| --- | --- | --- | --- | --- |
| 1 | 여행 준비에서 다음 행동 3개 | 예약/후보/일정 상태가 흩어짐. 지금 해야 할 일을 바로 제시 | 기존 SQL·validator, 외부 호출 불필요 | 1단계에 작은 상태 요약 |
| 2 | 검토 요청 기반 도시 확장 | 100도시 입력과 실제 근거 범위 차이 | 수요 중복제거, 관리자 검수·제한 수집 | 2단계 |
| 3 | 예약 변경 영향 미리보기 | 시간 교정 후 일정/숙소/경로 영향 파악 필요 | 기존 booking_events·itinerary validator | 1단계 시간 일관성 후 후속 |
| 4 | 친구와 후보 투표 | 소수 지인에게 공동 선택 가치 가능, 아직 수요 미검증 | 공유 권한·초대·충돌 모델 추가 필요 | 베타 사용 후 결정 |
| 5 | 식사 취향의 선택적 반영 | 피드백 기능 존재, 자동 변경은 부담 | 동의 기반 선호, 실제 피드백 필요 | 기존 기능 관측 후 |

음성 비서·자동 예약·전 세계 리뷰 대량 수집은 이번 두 단계에 넣지 않는다. 핵심 추천 근거와 일정 연결보다 먼저 만들 이유가 아직 없다.

## 12. 단계 완료 정의

### 1단계 완료

거짓 0건 재현, 공개 후보 일정 연결, 반복 SQL, 결과 유실, 선택/날짜/교정 UX의 테스트가 통과한다. 원문·예약·소유권·예산·job 회귀도 통과한다. 수정 전후 실행 결과와 실제 브라우저 검증 범위를 남긴다. 브라우저 접근이 차단되면 테스트와 구분한다.

### 2단계 코드 완료

정상 관리자 API로 지점 매핑→수집→검증→추천→카드 근거→일정의 합성 E2E가 통과한다. 유명한 곳은 독립적으로 동작한다. 설정/권한/품질이 없는 도시에서 데이터 없음이 정직하게 표시된다.

### 2단계 실제 서비스 활성화

실제 공급자 계약, 이용 범위, 지점, 품질, 예산을 검증한 도시·업종에만 ON. 코드 완료와 실제 수집/품질 완료를 별도 표로 기록한다. 실제 자료가 없으면 연결 도구·fixture·실행 설정·보고서까지 완료하고 운영 기능은 OFF로 남긴다.

## 13. 데이터 기반 추천 모델의 구체 구현

사용자의 추가 요청을 반영해 [RECOMMENDATION_MODEL.md](RECOMMENDATION_MODEL.md)에 특징 사전, 기본/취향 모델, 정렬 규칙, 평가 계약을 별도로 정의했다. 핵심 결정은 다음과 같다.

- 새 사용자에게 취향·숙소·예산 입력을 강제하지 않는다. 자료가 충분하면 명시적 일반 정렬 모델로 시작한다.
- 현재 v1/v2 모델은 재현 기준선으로 남긴다. `score=null`과 `rankable=false`를 구분하는 v3 계약을 추가한다.
- 현지어 핵심 구획은 검증된 관측 리뷰 모델로 고정한다. 후보마다 편집 모델로 바꿔 빈자리를 채우지 않는다.
- 유명한 곳은 언어 모델과 독립이며 근거 유형별로 정렬한다. 실제 유명 식당의 기존 landmark membership은 재사용한다.
- 개인화는 사용자 명시 선호를 반영하는 단계부터 시작한다. 분석·향후 학습 동의는 별도다.
- 데이터 수집과 모델 평가 도구를 완성하되, 실제 데이터가 부족한 동안 학습 모델의 효과를 주장하지 않는다.
