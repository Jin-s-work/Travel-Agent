## 실제 문제 6개

### 1. 핵심 차별점인 리뷰 신호가 카탈로그로 연결되지 않는다 — P1, 합성 API 재현 + 코드확인

공식팩은 `manual_official` provider로 지점을 만든다. 리뷰 지점은 `apify`로 별도 생성되며, 같은 external ID·이름·주소를 넣어도 내부 ID가 다르다. 수집은 장소 provider와 리뷰 provider의 일치를 강제하고 추천은 카탈로그 ID 그대로 리뷰 집계를 읽는다. 동일 지점임을 검증하여 두 ID를 연결하는 API/모델이 없다.

**재현:** 같은 지점을 양쪽 API에 등록 → 다른 ID; 공식팩 ID로 수집 접수 → `409 REVIEW_POLICY_UNAVAILABLE`; 리뷰 ID의 카탈로그 membership=0; 외부 호출0. 단순히 리뷰 ON으로 바꾸어 해결되는 문제가 아니다.

근거: [공식팩 생성](../../../src/discovery/service.py#L266), [리뷰 지점 생성](../../../src/research/service.py#L111), [수집 provider 검사](../../../src/research/service.py#L153), [추천의 리뷰 조회](../../../src/recommendations/service.py#L123).

추가 차단도 있다. 기본 실제 Apify 객체는 `contract_verified=False`, `sort_basis=unknown`, `continuity_verified=False`로 생성된다. 서버 생성 경로는 token/build만 전달하므로 정상 배선만으로 이 계약 검증 상태를 바꾸지 못한다. 품질 gate는 정렬시점·수집연속성 검증을 요구한다. 이는 외부 공급자가 실제로 부적합하다는 결론이 아니라 **검증 결과를 제품 실행 경로에 연결하는 작업이 남았다는 코드 확인**이다. [생성](../../../src/research/service.py#L59), [어댑터 기본값](../../../src/providers/apify_reviews.py#L26), [gate](../../../src/research/metrics.py#L173).

수용기준: 검증된 canonical place↔provider ID 연결을 통해 ‘공식 후보→수집→집계→같은 후보의 현지어 근거 카드’ API E2E가 통과한다. 동명 타지점·주소변경·삭제/철회는 차단한다. 계약 검증은 증거/버전/만료를 갖고 기본값은 미검증으로 유지한다. 미검증을 true로 하드코딩하지 않는다.

### 2. 도심순 12개를 먼저 잘라 숙소 근처에 실제 후보가 있어도 0건이 된다 — P1, 합성 API 재현

`_public_catalog`는 분류·제외 조건만 적용한 뒤 12개로 자른다. 거리 조건은 이후 추천 엔진에서 적용한다. 정렬은 수집 시 도심 중심 순서다.

**재현:** SQL 캐시13곳, 13번째 지점과 같은 원점·100m 조건 → 앞12개 전부 거리탈락, `displayable_count=0 / CONDITIONS_NOT_MET`. 13번째는 원점0m인데 검토하지 않는다. 실제 전수검색이 아닌 제한 검색임에도 사용자 조건 수정으로 안내한다.

근거: [도심순 정렬](../../../src/discovery/public_places.py#L123), [12개 선제한](../../../src/discovery/service.py#L399), [이후 거리 판정](../../../src/recommendations/engine.py#L522).

수용기준: 기존 최대60개 캐시의 저비용 필터·원점 기준 후보선택을 먼저 수행하고 최종 표시만12개 제한한다. 같은 합성 사례에서 13번째가 노출되어야 한다. 도심3km 밖 숙소는 검색범위 부족으로 구분하고 반경을 몰래 늘리지 않는다. 경로 호출 상한은 유지한다.

### 3. 검수 식당이 하나라도 있는 도시에서는 카페의 무료 발굴도 막힌다 — P1, 합성 API 재현

공개 검색을 생략하는 `reviewed` 쿼리가 도시의 검수 지점 존재만 본다. 요청한 분류·관점·제외 목록·신선도·자료충족 여부는 반영하지 않는다.

**재현:** 도쿄 검수팩을 식당만으로 구성, 카페 요청 → Photon 호출0, `REVIEWED_CATALOG_AVAILABLE`, 표시0, `CATEGORY_NO_CANDIDATES`.

근거: [검색 생략 조건](../../../src/recommendations/service.py#L145).

수용기준: 요청 분류/관점에 실제 이용 가능한 후보가 부족한 경우에만 기존 무료 한도 안에서 보충한다. strict 언어 요건은 공개지도 카드로 대체 통과시키지 않는다. 검수 식당 존재+카페 요청 회귀를 추가한다.

### 4. 공개지도 카드의 ‘일정에 넣기’가 404로 끝난다 — P1, 합성 API 재현

카드는 저장·비교·일정 버튼을 제공하지만 일정 `_data`는 approved+verified 후보만 읽는다. recommendation_run에 허용된 공개 ID도 마지막 missing-place 검사에서 거절한다.

**재현:** 정상 공개 추천 카드→일정 생성(`allow_provisional=True`) → `404 NOT_FOUND: 사용 가능한 선택 장소를 찾을 수 없습니다.`

근거: [버튼](../../../web/js/foundation.js#L1299), [일정 데이터 조건](../../../src/itineraries/service.py#L48), [최종 거절](../../../src/itineraries/service.py#L185), [검증기 지점차단](../../../src/itineraries/constraints.py#L162).

수용기준: 사용자가 고른 공개 장소를 ‘방문 후보/잠정 일정’으로 지속 보관하고 미확인 영업·경로를 표시한다. verified로 승격하지 않는다. 엄격 일정에는 구체적인 정보부족 이유를 주되404를 쓰지 않는다. 예약잠금·실제 충돌·출처철회 차단은 유지한다.

### 5. 사실 하나의 만료로 저장된 추천 전체가 사라진다 — P2, 합성 API 재현; 만료 차단 자체는 정상

카탈로그 digest가 달라지면 GET에서 저장된 `result_json/candidates_json` 전체를 NULL로 만든다. UI의 ‘다시 추천’은 존재하지만 어떤 카드/사실이 바뀌었는지와 유효한 나머지 결과를 이어 보는 경로가 없다. 공식팩은 추천 버튼으로 원문을 재확인하지 않으므로 만료된 사실을 복구하려면 별도 운영 검수가 필요하다.

**재현:** 공개 카드2개 중 fact1개만 과거 만료로 설정→기존 run `result=null/data_status=stale`. 다른 지점 자료는 변경하지 않음.

근거: [전체 무효화](../../../src/recommendations/service.py#L266), [stale UI](../../../web/js/foundation.js#L1100), [팩 확인 기한](../../service-v3/reports/official-restaurant-sources.md#L24).

수용기준: 사용자 선택/보관함은 유지하고 만료·철회·조건변경·공급자장애를 구별한다. 유효한 카드와 갱신대상을 나누고 재검증 전후 변경을 보여준다. 철회/표시권 만료 payload는 재노출하지 않는다. 갱신 실패가 이전 **아직 유효한** 근거를 지우지 않아야 한다.

### 6. 선택 입력을 비우면 두 관점 모두 순위가 없어지고 유명 구획의 근거도 좁다 — P2, 순수엔진 재현 + 코드확인

가격·취향·이동 등 어느 점수성분 하나라도 없으면 총점=null이다. 취향은 기본 빈 배열, 예산은 선택사항인데 이를 생략하면 충분한 합성 근거를 가진 장소도 `items`에서 `insufficient_data`로 이동한다. **재현:** 동일 완전 fixture에서 예산/선호태그만 제거→두 구획 각각 순위0·참고2.

근거: [선택 입력 기본값](../../../src/discovery/models.py#L78), [미입력 예산](../../../src/recommendations/engine.py#L363), [null 총점](../../../src/recommendations/engine.py#L565).

`landmark`는 이미 유명 식당을 담는다. 실제팩의 보틴·7 Portes·다이코쿠야가 해당하지만 iconic 근거는 보틴만 있다. 현행 iconic 점수는 관광청/유산 등 근거이며 평점·평가량으로 일반 인기 장소를 발굴하는 경로는 아니다. [기존 membership](../../service-v3/data/official-restaurants-2026-10-06.json#L843), [iconic 판정](../../../src/recommendations/engine.py#L431), [관점 membership 검사](../../../src/recommendations/engine.py#L665).

수용기준: 방문 실행가능성의 미확인과 ‘선택 선호를 입력하지 않음’을 분리한다. 미입력 성분을 0점/허위점수로 만들지 않고 버전 있는 선택적 점수 또는 근거별 정렬을 제공한다. 인기/유명 근거 유형·출처·기준시점을 별도 모델링하고 식당/카페/명소 모두 허용한다.

## 비용 대비 가치가 높은 확장 3개

1. **근거가 보이는 두 구획.** 현지 구획 상단에는 검증된 ‘최근 현지어 리뷰 신호’를, 일반 유명·인기는 별도 구획으로 둔다. 현지 구획의 리뷰자료 없음/표본부족/검증실패/갱신중 상태를 구분하고 검수 지역자료·공개지도는 별도 보조영역으로 표시한다. 같은 장소가 두 조건을 충족하면 양쪽 표시하되 보관함/일정에서는 canonical ID로 중복 제거한다. 기존 두 관점과 카드/비교 UI를 재사용하므로 새 추천 서비스 전체를 만들 필요가 없다.
2. **한 도시 소규모 리뷰 파이프라인 제품화.** 기존 180일·최대200건 수집과 분류/집계/보관기한을 재사용해 10~20개 지점부터 운영자 검토 큐를 만든다. 원문언어·번역분리·중복·미분류·최소표본·정렬/연속성·한국어 재현율/현지어 정밀도를 먼저 검증한다. 도시별 활성화로 확대하며 원문을 주민 신분/전체 리뷰 비율로 추정하지 않는다. ‘현지어 비중 80%’ 대신 ‘최근 관측 본문 n건 중 현지어 n건, 미분류 n건, 확인일’이 제품의 주된 증거가 된다. 일반 사용자의 추천 요청마다 유료 리뷰를 다시 수집하지 않는다.
3. **선택 보존 + 근거 갱신 + 캐시 응답 최적화.** 이미 있는 캐시/작업상태/원자적 접수/편집이력을 연결해 재시도와 만료 복구를 짧게 만든다. 저장소 기록상 공개 첫 요청52.89초, 외부호출0인 재요청44.45초다. 현재 성능 재측정이 아닌 당시 관측이며, 반복 SQL·전수 manifest·지점별 evidence 호출 비용은 프로파일링 가설이다. [관측](../../service-v3/reports/going-design-search-validation.md#L69), [후보별 evidence](../../../src/recommendations/service.py#L121). 수용기준은 warm fixture 후보12개/60개에 SQL횟수와 p50/p95를 기록하고 read model/batch 조회 후 상대50% 개선·동일조건 캐시재사용 외부호출0, 개인 소유권·삭제·철회 fence 유지다. 실제 free-host 목표치는 측정 후 결정한다.

## 2단계 구현 분할

**1단계: 추천을 끝까지 사용할 수 있는 기반.** 문제2/3/4/5를 해결하고 warm 응답을 계측한다. 도시×분류×관점의 자료 수·신선도·검색범위·공급자 상태를 사용자 문구와 연결한다. 추천 결과가 0이어도 다음 행동이 원인에 맞고, 선택한 공개 장소가 잠정 일정까지 이어져야 한다. 기존 공급자 OFF/한도/권한을 유지하며 외부호출 없이 합성 API→브라우저 흐름, 상태복원·만료·동명지점·100도시 metadata 전수를 검증한다. 위 재현 4개가 기대 동작으로 바뀌는 것을 완료 gate로 둔다.

**2단계: 현지어 리뷰 + 유명·인기 추천의 실제품화.** canonical 지점과 provider reference를 분리하고 검증된 매핑/철회/버전 전파를 구현한다. 기존 `local_editorial/local_observed/iconic`를 사용자에게 보이는 근거 유형과 대응시킨다. 현지어 검증 gate/집계 freshness를 관점별로 적용하고 유명·인기 관점을 해당 리뷰요건과 독립적으로 제공한다. 문제6의 선택입력 정렬을 보완한다. 합성에서는 두 관점 동시노출·겹치는장소·하나만0·부분갱신·리뷰 gate 실패·언어자료 없는 유명식당의 비차단을 검증한다. 실제 공급자 계약/표본평가/가격/개인정보 처리 검토와 허가된 소액 파일럿이 완료되어야 운영 활성화한다. 코드 구현완료와 실데이터 추천 검증완료를 별도 보고한다.

유명 구획을 살리려고 현지어 기준을 느슨하게 하거나, 현지 신호가 없는 공개지점을 ‘현지인 맛집’으로 표시해서는 안 된다. 반대로 유명·인기 구획에는 현지어/한국어 비중 통과를 일률적으로 요구하지 않는다.
