## 1. 먼저 합성 데이터로 문제를 고정해

AUDIT.md의 재현 스크립트를 참고해 실패 조건을 현재 테스트 구조에 맞게 옮겨. 외부 API를 부르지 않는 fake provider와 임시 DB를 사용해.

필수 재현:

1. 같은 도시 공개 후보 13개 중 도심 기준 13번째 장소만 숙소 100m 안에 있다. 해당 장소가 평가 전에 잘려 추천 결과가 0건이 되어서는 안 된다.
2. 공식 검수 식당은 있지만 카페는 없는 도시에서 카페를 요청한다. 다른 카테고리의 검수 장소 존재가 공개 카페 검색을 막으면 안 된다.
3. 검수 식당 100개 뒤에 유효 카페 1개가 ID 순으로 정렬된다. cafe 요청에서 앞 100개 제한 때문에 없어지면 안 된다.
4. 식별된 공개지도 후보를 allow_provisional=True로 일정 생성에 전달한다. 내부 catalog membership 차이로 404가 나면 안 된다.
5. 한 여행의 저장 추천을 읽다가 무관한 도시/공급자 policy 한 행이 추가된다. 결과가 NULL로 덮이면 안 된다.
6. 처음에는 follower로 시작했다가 leader가 된 앱에서 maintenance가 시작되어야 한다.
7. 오래된 원문 orphan 250개에서 앞 100개의 완료 항목만 계속 삭제해 뒤 150개의 처리가 계속 누락되면 안 된다.

정상으로 바꿀 기대값과 현재 실패를 나누어 기록해. 감사용 스크립트가 assert current_bug를 포함한다면 수정 후 회귀 테스트에는 정상 동작을 assert해야 한다.

## 2. 후보 구성 순서를 수정해

### 2.1 표시 개수와 조사 개수를 분리

`안전한 자료 범위 → 지점/카테고리 → 원점/필수 조건 → 근거 자격 → 점수/다양성 → 화면 limit`을 따라.

- src/discovery/service.py의 공개 후보 제한과 승인 후보 쿼리를 함께 점검해.
- `[:12]`, `[:100]`를 단순 삭제하고 무제한 수집하는 방식도 금지해.
- 후보 수집 상한, 조건 평가 대상 수, 제외 사유별 수, 최종 표시 수를 결과에 보존해.
- 필터를 통과할 후보를 raw ID 순으로 먼저 자르지 마. 필요한 카테고리/원점에 맞는 결정적 예비 선별을 해.
- 등록 순서와 응답 순서가 결과를 바꾸지 않도록 안정적인 tie-break를 써.
- 실행 시 candidate capture와 apply/get 때 재검증은 같은 선택 규칙을 써.
- 제외·삭제·철회·만료 장소가 유효 후보 cap을 소비하지 않게 해.

### 2.2 숙소 원점까지 실제 연결

기존 accommodation/origin snapshot을 재사용해.

- 숙소·수동 출발점·도심 중 현재 선택 원점을 표시해.
- 수집 범위와 거리 계산 기준이 다르면 한 계약으로 정렬해. 지원하지 않는 공급자 기능은 있다고 가정하지 마.
- 공용 캐시에 개인의 정밀 숙소 좌표·owner_id를 넣지 않도록 범위/타일 캐시 설계를 검토해. 최종 거리 계산과 개인 선택은 사용자 scope에 남겨.
- 원점/날짜/숙소 버전 변경은 관련 추천을 stale로 표시하되, 안전한 이전 결과와 사용자의 선택을 없애지 마.
- 도심 자료만 있는 상황에서는 “숙소 주변에서 찾았어요”라고 표시하지 마.
- 직선거리와 공급자 경로 시간을 구분해. 도보 경로가 없으면 거리에서 임의의 도보 분을 만들지 마.
- 숙소를 입력하지 않아도 도심/직접 선택 출발점으로 작동하게 해.

### 2.3 검색 생략 조건

- 도시 안 검수 장소가 1개라도 있다는 조건을 사용하지 마.
- 선택 카테고리·영역·사용 가능한 근거·명시 조건에 맞는 유효 후보 수를 기준으로 보완 검색 여부를 정해.
- 엄격 언어 조건이 필요할 때 공개지도를 리뷰 자료의 대체재로 쓰지 마.
- 반복 클릭/새로고침이 중복 공급자 요청을 만들지 않도록 기존 Idempotency-Key/job/예산/caching을 써.
- 공급자 실패·사용량 한도·데이터 없음·조건 제외를 각각 reason code와 다음 행동으로 반환해.

## 3. 공개지도에서 일정으로 이어지게 해

단순히 모든 public_map 후보를 approved/verified로 승격하지 마.

- `지점 식별 상태`, `출처 사용 가능 상태`, `방문 조건`, `추천 점수 완성 여부`를 분리해.
- 지점이 식별되고 출처 사용이 가능한 후보는 일정의 입력 객체로 전달할 수 있어야 해.
- 영업·경로·예약 조건이 unknown이면 strict 모드에서는 unplaced와 구체 이유를 반환해.
- 사용자가 잠정 초안을 허용한 경우에만 unknown을 provisional로 배치해.
- 명시 휴무·인원 초과·고정 예약 충돌·지점 모호·권한 철회는 잠정 모드에서도 차단해.
- itinerary 생성과 add preview가 서로 다른 catalog 규칙을 쓰지 않게 해.
- 양쪽 이동, 체류 시간, 영업 전체 구간, 마지막 입장, timezone/DST, 예약 buffer를 기존 validator로 재검증해.
- 외부 예약이나 잠긴 고정 항목을 자동으로 변경하지 마.
- preview는 원 일정을 수정하지 않고, apply는 version/삭제/사실 신선도를 다시 검사하고 새 revision으로 저장해.
- 실패는 대상 없음과 방문 조건 미확인을 구분해. 실제로 보이는 장소를 넘겼는데 원인 없는 404가 나오는 흐름을 없애.

## 4. SQL 성능을 측정하고 일괄화해

현재 이미 PostgreSQL connection pool이 있다. 풀 추가나 크기 증대만으로 해결했다고 하지 마.

### 4.1 계측

- 테스트 전용 counter 또는 개인정보 없는 stage instrumentation을 사용해.
- request/job 단계별 elapsed, DB checkout, SELECT/쓰기/transaction 수, pool wait, queue wait, 외부 provider 호출을 구분해.
- SQL parameter·질문·원문·예약번호·정밀 위치·token을 로그에 남기지 마.
- 6/12/50/100개 후보, fresh/cached/get을 같은 fixture로 비교해.
- 기존 감사에서 후보 12개를 대상으로 측정한 execute 667 SQL/get 244 SQL은 SQLite의 특정 측정 범위에 해당해. 운영 PostgreSQL 수치로 그대로 인용하지 마.

### 4.2 구현

- 장소 팩·사실·출처·리뷰 집계·사진을 bounded batch로 가져와.
- 후보별 reviews.evidence → repo.get_trip → purge → policy query 반복을 제거해.
- trip ownership을 한 번 확인한 뒤 내부 일괄 조회에 안전하게 전달해. 외부에서 임의 actor scope를 주입할 수 없게 해.
- 읽기 경로에서 전역 purge/쓰기 잠금을 없애. 만료/철회 조건 검사는 조회 predicate/현재 정책으로 계속 적용해.
- trip_places 연결은 읽기 반복에서 분리해 필요한 생성/캡처 트랜잭션에 넣어.
- candidate 수 증가에 따른 선형 SQL 왕복을 제거해. 메모리 cap은 유지해.
- 큰 join으로 사실/출처 조합이 폭증하지 않게 집계/페이지 전략을 검토해.
- 각 DB backend의 row 타입과 dict/tuple 변환을 확인해. SQLite에서 값인 것이 PostgreSQL에서는 key 목록이 되지 않게 해.

### 4.3 결과 유효성

- 전체 provider_policies/aggregate/place의 전역 해시를 개별 여행의 dependency로 쓰지 마.
- 실제 참조한 지점·외부연결·사실·policy·aggregate·model version을 manifest에 저장해.
- 무관한 도시/정책 추가로 해당 결과가 stale이 되거나 NULL로 덮이지 않게 해.
- 해당 근거 철회/삭제, 전역 기능 OFF, 세션/소유권 변경은 즉시 반영해.
- 오래된 추천 결과를 읽기만 했다는 이유로 파괴하지 마. 안전하게 표시할 수 있는 과거 결과와 재계산 필요 상태를 분리해.
- 이전 결과를 보여주는 동안 현재 조건의 결과가 아님을 표시하고, 원인이 된 대상/조건을 설명해.
- 철회된 사실·수치·사진을 “과거 결과”라는 이유로 다시 노출하지 마.

## 5. 유지보수와 삭제 진행성을 고쳐

- FastAPI lifespan에서 처음 획득한 leader boolean을 프로세스 수명 전체의 결론으로 사용하지 마.
- follower → leader 승격 후 maintenance를 시작하고 leader 상실 후 새 side effect를 차단해.
- lease/fencing은 기존 jobs 계약을 재사용해. dispatcher만 살아 있고 정리가 멈춘 상태를 정상으로 보고하지 마.
- maintenance 마지막 시작/성공/실패/현재 소유자/지연을 운영 상태에 추가해. 유료 health 호출은 금지해.
- Supabase object/import manifest 정리에서는 LIMIT 100 범위가 안정 정렬·지속 커서 또는 next_reconcile_at과 완료 상태에 따라 전진하게 해.
- 완료된 deleted 100개가 매 cycle을 독점하지 않게 해.
- 늦은 업로드가 살아나지 않도록 tombstone·유한 재확인·저장소 삭제 영수증을 유지해.
- 일부 DELETE 실패가 다른 키 처리를 막지 않게 해. 재시도는 기존 예산/정산 계약을 따라.
- 운영 데이터로 삭제 시험하지 마. 임시 PostgreSQL + mocked storage를 우선 사용하고 불가능하면 해당 backend 미검증이라고 기록해.

## 6. 사용자가 다시 입력하지 않도록 화면을 연결해

### 6.1 짧은 조건 수정

- 날짜·인원·출발점은 현재 요약 옆에서 해당 값만 수정하게 해.
- 성인 수를 바꾸려고 전체 4개 탭을 다시 읽게 하지 마.
- 필수 식단/이동 조건은 한국어 선택명과 내부 키를 분리해. vegan 같은 문자열 문법을 사용자에게 요구하지 마.
- 필수/선호와 미확인/조건 불충족 구분을 유지해.
- 연도 네 자리, 유효 날짜, 여행 구간·도시 정합성을 client/server에서 검사해.
- 실패 후 입력값, 포커스, inline 오류를 보존해.

### 6.2 예약 교정

- 한 식당 예약의 시작 시각은 한 번 입력하면 관련 구간/대표값의 일치하는 변경안을 보여줘.
- 왕복 항공·다중 구간은 해당 구간만 수정해. 가는 편 변경으로 오는 편이나 도착 timezone을 덮지 마.
- 출발/도착·체크인/체크아웃·방문 시각 등 사용자 의미에 맞는 필드를 써.
- 날짜만 있는 원문에 임의의 00:00을 추가하지 마.
- 원문/교정값/유효값과 충돌을 같은 화면에서 확인하게 해.
- 409에서는 현재 저장값/내 입력/기준 버전을 비교하고 임의 덮어쓰지 마.
- 재추출 실패·임베딩 실패 때 기존 활성 예약을 계속 읽을 수 있어야 해.

### 6.3 탐색 맥락과 일정 담기

- 현재 탭·종류·방문일·조건·스크롤·선택 후보를 여행별로 보존해.
- A 여행의 미완성 선택이 B에 노출되지 않고 B → A 때 이어지게 해.
- 새로고침 복원이 필요한 초안은 소유권 있는 서버 데이터로 저장해. 원문/개인정보를 임의 localStorage에 넣지 마.
- 새 draft 스키마가 필요하면 기존 snapshot/bookmark/selection 저장과 중복 여부를 먼저 판단해. version·TTL·삭제·소유권·409를 설계해.
- 로그아웃·계정 변경·삭제 시 메모리와 해당 초안을 지워.
- 추천/저장 카드의 일정 행동을 공통 UI로 연결해.
- 일정 날짜의 초기 제안은 현재 탐색 방문일로 해. 사용자가 삽입 화면에서 날짜를 직접 바꾼 이후에는 그 명시적 선택을 우선해. 마지막으로 본 다른 일정 날짜가 조용히 우선하거나 사용자 선택을 덮지 않게 해.
- 첫 일정도 작은 날짜/시각/체류 요약 → preview → apply로 연결하고 고급 버퍼는 선택적으로 보여줘.
- 예상 시간은 제안이며 예약 확정으로 표현하지 마.
- 구체 예약명·충돌 대상 클릭은 목록이 아닌 해당 상세/필드로 연결하고 수정 후 원래 흐름으로 돌아오게 해.

### 6.4 진행과 접근성

- 이미 구현된 job SSE/reconnect/Last-Event-ID를 재사용해.
- 버튼은 즉시 진행 상태를 보이되 실제 queued/running/stage/count와 일치시켜.
- 실제 계산되지 않은 퍼센트·남은 시간을 만들지 마.
- 필터 변경 중 기존 결과를 유지하고 “이전 조건” 표시를 해. 늦은 응답이 최신 결과를 덮지 않게 해.
- partial/failed/cancelled/budget/stale/session 상태마다 가능한 행동을 달리해.
- hint와 error를 aria-describedby에 연결하고 이동 후 포커스와 스크린 리더 안내를 처리해.
- 320/390/768/1440px, 글자 200%, 긴 다국어 이름, 키보드 Tab/Escape, 모바일 소프트 키보드를 확인해.
- 일반 메뉴 이동마다 확인창을 추가하지 마. 원하지 않는 모달 중첩도 피해야 해.

## 7. 홈에는 다음 행동만 작게 보완해

새 대시보드나 점수 체계를 만들지 말고 기존 SQL 상태에서 중요한 작업 최대 3개를 제시해.

예: 시각 충돌 예약 확인, 숙소 지점 확인, 일정의 미배치 후보 검토.

- 같은 문제를 여러 곳에서 중복 집계하지 마.
- 가장 가까운 방문일/확정 예약에 미치는 영향을 기준으로 결정적으로 정렬해.
- 버튼 클릭만으로 확인 완료로 처리하지 마.
- 해당 예약/장소/필드로 직접 이동해.
- 리뷰 자료가 없는 도시를 “여행 준비 실패”로 만들지 마.
- 새 외부 호출/알림/메일 발송은 필요 없다.

## 8. 검증

기존 테스트를 확인하고 변경 관련 회귀 → 전체 테스트 순으로 실행해. 환경 문제와 실제 회귀를 구분하고 실패를 숨기지 마.

필수 시나리오:

- 사용자 A/B의 여행 각각 2개, 같은 파일명, 왕복 메일, 날짜만 있는 예약, 하루 예약 8개 + 수동 예약.
- 메일 재추출 실패/동시 질문/사용자 교정 유지/세션 만료/타인 요청 404.
- 숙소 근처의 13번째 후보/식당이 있는 도시의 카페/100번째 이후의 적합 후보.
- 공개 후보의 strict 모드 미배치·잠정안 성공·확정된 위반 차단.
- 무관한 정책 변경 시 결과 보존·관련 출처 철회 시 차단·global OFF·삭제와 완료의 경쟁.
- A/B 전환·refresh 시 선택 복원·늦은 응답·조건 취소·409 시 입력 보존.
- 고정 예약 보존·preview의 원본 미변경·apply 실패·undo 시 새 revision 생성.
- leader 교대·orphan 250개·실패한 키 이후의 처리 지속·재시작·늦은 업로드.
- 로컬 SQL 측정과 disposable PostgreSQL 실행을 구분해.
- 브라우저에서 로그인 → 여행 → 메일 → 교정 → 탐색 → 저장 → 일정 preview/apply → refresh → undo.

브라우저 권한이 막히면 우회하지 마. 가능한 자동화 검증을 완료하고 정확히 어떤 UI 검증을 하지 못했는지 남겨.

## 9. 종료 산출물

- 실제 수정 코드와 필요한 버전이 명시된 migration, dry-run/rollback.
- docs/service-v4/IMPLEMENTATION_STATUS.md에 구현·검증·미검증 구분.
- reports/stage1-validation.md와 개인정보 없는 계측 JSON.
- 수정 전후 SQL/checkout/단계 시간, 실제 외부 호출 수, fixture 범위.
- 실제 브라우저/OS/화면 폭, 검증하지 못한 기기/경로, screenshot 증거.
- 기존 색/브랜드를 유지한 Before/After/Why.
- 테스트 명령·pass/fail/skip·실패 이유·후속 조치.
- 2단계가 재사용할 API/스키마/선별/초안 계약.

“로컬 테스트 통과”를 “운영 배포 완료”로 보고하지 마. 운영 수정/지출은 기존 명확한 승인이 있는 범위만 실행해. 1단계에서는 실제 리뷰 수집·언어 품질·전 세계 지원이 완료됐다고 주장하지 마.
