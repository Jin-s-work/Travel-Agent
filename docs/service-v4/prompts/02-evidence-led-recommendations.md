## 1. 이미 있는 두 구획을 정확한 제품 경험으로 확장하세요

현재 `local_discovery`와 `landmark` 구획, famous 식당 membership, `local_observed`·`local_editorial`·`iconic` 모델이 이미 있습니다. 이를 전부 새로 만들지 마세요.

사용자에게 표시하는 이름은 다음을 기본으로 하세요.

- `현지어 리뷰로 찾기`: 원문 언어 관측과 엄격 gate를 통과한 후보.
- `유명한 곳`: 공식 대표성, 플랫폼 평가 규모, 편집 선정 근거가 있는 장소.
- 보조 묶음 `주변 장소 참고하기`: 공개 지도·편집 자료는 있지만 핵심 근거가 부족한 후보.

음식점·카페·볼거리는 추천 방식과 독립적인 필터입니다. 같은 장소가 두 핵심 구획에 서로 다른 이유로 등장할 수는 있지만, 저장·비교·일정에서는 같은 canonical ID를 사용해 중복을 막으세요.

현지어 리뷰 작성자를 현지 주민으로 판정하지 마세요. 한국어 원문 리뷰가 적다는 사실을 한국인 방문객이 없다는 뜻으로 표현하지 마세요. “현지인 맛집”은 사용자의 탐색 의도이며, 서비스가 보장하는 속성이 아닙니다.

## 2. canonical 지점과 리뷰 공급자 ID를 연결하세요

감사에서는 공식 카탈로그의 `manual_official` 지점과 Apify 리뷰 지점이 같은 외부 ID·주소를 가리켜도 서로 다른 내부 ID를 만들고, 정상 API로 리뷰를 추천에 연결하지 못하는 문제가 재현되었습니다.

### 2.1 모델과 마이그레이션

- 기존 `place_identities`, `research_candidates`, `trip_places`, bookmark, itinerary의 참조 관계를 조사하세요.
- canonical 지점과 공급자별 외부 ID 사이의 검증된 관계를 설계하세요. 예를 들어 `place_external_links`를 사용할 수 있습니다.
- link에는 서버가 생성한 ID, `canonical_place_id`, `provider`, `external_place_id`, `status`, `source_id`, `checked_at`, `expires_at`, `identity_version`, 검수 근거를 포함하세요.
- 같은 `provider/external_id`의 활성 연결이 여러 canonical 지점에 생기지 않도록 DB 제약과 트랜잭션으로 보호하세요.
- 사용자의 개인 메모·숙소·여행 정보를 공용 지점에 저장하지 마세요.
- 기존 ID를 전부 교체하지 마세요. 기존 구조에 추가하는 마이그레이션(additive migration), dry-run, 충돌 보고, 복구 절차를 제공하세요.
- 모호한 매핑(ambiguous mapping)을 이름 유사도만으로 승인하지 마세요.

### 2.2 관리자 흐름

공식 후보 선택 → 외부 지점 후보 조회·입력 → 이름·주소·좌표·지점 대조 → 연결 미리보기 → 승인·거절 → 리뷰 수집 준비로 이어지도록 구현하세요.

- 같은 체인의 다른 지점, 이전·폐업, 좌표 불일치, 주소 변경을 다루는 fixture를 포함하세요.
- canonical 지점의 이름이 같다는 이유만으로 리뷰를 합치지 마세요.
- 연결 변경·철회 후에는 과거 집계가 노출되거나 진행 중인 job이 이를 다시 활성화하지 못하도록 차단하세요.
- 해당 연결을 참조한 추천만 `stale/revalidation`으로 표시하세요. 무관한 도시의 추천은 유지하세요.
- 일반 사용자에게 관리자 승인 API를 열지 마세요.
- 같은 지점을 여러 사용자가 요청해도 공용 검토 작업이 중복되지 않도록 하세요.

정상 공개 API를 사용하는 `공식 후보 → 외부 ID 연결 → 수집 → 집계 → 같은 카드의 근거 표시` 합성 E2E를 만드세요. DB를 수동으로 조작해야만 통과하는 테스트를 근거로 완료했다고 보고하지 마세요.

## 3. 실제 공급자 계약 검증 결과를 실행 경로에 연결하세요

현재 Apify 생성자는 `contract_verified=False`, `sort_basis=unknown`, `continuity_verified=False`가 기본값이며, 서버의 생성 경로는 token과 build만 전달합니다. 이 기본값을 `true`로 바꾸는 것은 해결책이 아닙니다.

### 3.1 계약 증거 저장

공급자·build·adapter version별로 다음 정보를 구조화하세요.

- 입력·출력 스키마 확인일, 공식 문서 URL, 보고서 hash.
- 원문·번역의 분리 방식과 `originalLanguage`의 의미.
- `published/edited/unknown` 정렬 기준.
- 공급자가 관측 가능한 형태로 제공하는 페이지·연속성의 범위.
- 수집·계산·보관·표시의 이용 범위와 만료.
- 실제 검증 표본, 실패 유형, 검토자, 승인·보류·철회 상태.
- 가격표 확인일, 과금 단위, 실행 상한, 추가 비용 범위.

검증된 기록을 runtime provider에 안전하게 전달하세요. build가 바뀌거나 증거가 만료되면 자동으로 재검토 대상으로 처리하고, 예전 승인을 그대로 승계하지 마세요.

### 3.2 데이터 수집 계약

기존 `ReviewCollectionProvider`, admin scope, durable job, 비용 wrapper를 재사용하세요.

- 기본값은 최신순, 최근 180일, 고유 리뷰 레코드 최대 200개, 최대 20페이지, 페이지당 최초 시도를 포함한 2회 시도입니다.
- 별점만 있는 레코드(rating-only)도 200개 상한에 포함하세요. 본문 200개를 채우려고 무한 수집하지 마세요.
- 언어·keyword·star 필터로 골라 수집한 리뷰를 일반적인 언어 분포로 사용하지 마세요.
- original, translated, 원문 언어, review ID, 발행·수정 시각, cursor를 정규화하세요.
- 작성자 이름·사진·프로필·다른 방문 이력은 결과 모델에서 제외하세요.
- fetched, unique, text, rating_only, extraction_unknown, 기간, 정렬, 종료 사유, 비용을 보존하세요.
- 반복 cursor, 중복 ID, 정렬 역전, 날짜 모호성, 중간 실패를 감지하세요.
- `record_cap/date_boundary/exhausted`와 page·time·budget·provider 실패를 구분하세요.
- `exhausted`는 공급자 자료가 끝났다는 뜻이며, Google 리뷰를 전수 확보했다는 뜻이 아닙니다.
- dataset offset을 Google 원천 cursor처럼 취급하지 마세요.
- 공급자의 내부 수집 페이지·재시도를 통제하거나 관측할 수 없다면 그 범위를 기록하고, strict 검증을 완료했다고 주장하지 마세요.
- 공급자 응답을 일반 로그나 예약 Chroma에 넣지 마세요. 기존 원격 dataset·run 삭제 계약을 유지하세요.

### 3.3 공급자 선택과 비용

- 기존 Apify 리뷰 Actor의 현재 공식 문서·가격·build를 다시 확인하세요. 장소 검색 Actor와 리뷰 Actor를 혼동하지 마세요.
- “API 최대 5개”는 Places API의 한도이며, 웹 수집량의 상한은 아니라는 구분을 유지하세요.
- 공급자의 기술적 가능성, 이용 범위, 품질, 제품 ON 여부를 별도로 판정하세요.
- 필요한 정렬·원문·연속성 증거를 얻을 수 없다면 같은 인터페이스로 대체 provider를 검토하거나 strict를 OFF로 남기세요.
- 읽기 API나 추천 버튼이 리뷰 수집을 직접 시작하지 않도록 하세요. 유효한 집계는 공유해서 재사용하세요.
- 유료 실행 전에 현재 계정 잔액, 기존 승인 범위, 최소 결제, 실험 전체 상한을 확인하세요. 기존 OpenAI 사용 허용을 Apify 사용 허용으로 확대하지 마세요.
- 계정이나 허가가 없다면 fake 어댑터, 실행 경로 연결, fixture, 실행 설정, 보고서까지 완성하고 라이브 실행만 `not_run`으로 기록하세요.
- 새 계정이나 지출이 필요하다면 코드와 구체적인 대상·설정·예상 비용·상한·복구안을 먼저 완성하고, 마지막 단계에서 승인을 받으세요.

## 4. 언어와 집계의 수학적 계약을 보존하세요

`T=본문 존재 확인`, `C=언어 판별`, `U=미판별`, `L=현지어`, `K=한국어`입니다.

- `T=C+U`, `L+K≤C`를 검사하세요. 음수나 불가능한 합계는 거절하세요.
- 표시 비율에는 `L/C`와 `K/C`를, 엄격 판정에는 `L/T`와 `(K+U)/T`를 사용하세요.
- 분모가 0이면 null입니다. 플랫폼 전체 평가 수를 언어 비율의 분모로 사용하지 마세요.
- 원문이 없고 번역만 있다면 본문이 있는 것으로 확인된 T와 미판별 U에 포함하세요.
- 본문 존재 여부조차 불명확한 레코드를 `rating_only`로 만들지 마세요.
- 언어별 합계, 추출 불명, 중복 제거 사이의 관계를 검증하세요.
- 표시 아이콘·게이지에도 분모와 관측 기간을 제공하세요.
- 상하한은 unknown의 가능 범위이며, 통계적 신뢰구간이나 분류 오류의 보정값이 아니라는 의미를 유지하세요.

초기 strict 가설은 `C≥100`, `U/T≤10%`, `L/T≥60%`, `(K+U)/T≤10%`입니다. 같은 플랫폼의 5점 만점 기준 4.2 이상, 전체 평가 수 200건 이상은 별도의 자격 조건입니다.

- `T200/C190/U10/L150/K4`에서 표시 비율 `78.9%/2.1%`, 보수적 비율 `75%/7%`가 나오는지 검증하세요.
- `K0/U70`을 한국어 비중이 낮다고 확정하지 마세요.
- 기준 완화는 사용자가 선택한 새 요청이어야 하며, 버전과 조건 요약에 표시하세요.
- 지점, 이용 범위, 원문·언어 품질 조건을 사용자 선호 설정으로 완화하지 마세요.

## 5. 도시별 언어 프로필과 독립 평가를 구현하세요

- 도쿄 `ja`, 바르셀로나 `es+ca`에서 시작하세요.
- 100개 도시 registry는 그대로 유지하되, 모든 도시의 언어 기능이 준비되었다고 표시하지 마세요.
- 다언어 도시 프로필에는 version, source, checked_at을 포함하세요.
- 현지어 집합과 한국어가 겹치는 도시는 기존 `L+K≤C` 계약 및 탐색 목적과 맞지 않으므로 초기 프로필을 unavailable로 두세요. 수식을 조용히 바꾸거나 잘못 적용하지 마세요.
- 기존 Lingua 로컬 모델을 재사용하고, 평가 후 필요한 경우에만 교체하세요. 모든 리뷰를 LLM으로 보내지 마세요.
- 모델 버전, 라이선스, 메모리, 처리 시간, 원문 대조 결과, 혼동행렬을 기록하세요.
- 개발·조정용 자료와 최종 평가용 자료를 분리하고, 중복 원문이나 같은 지점으로 인한 평가 자료 유출을 검토하세요.
- 도시별 실제 리뷰 100개 이상, 원문 대조 20개 이상을 확보하고 한국어 양성 사례를 포함하세요.
- 현지어 precision과 한국어 recall의 초기 목표는 각각 95%입니다. TP·FP·FN과 분모를 함께 보고하세요.
- 한국어 정답 사례가 0개이면 recall은 null이며 통과할 수 없습니다. 표본이 적은 경우도 별도로 표시하세요.
- 한국어 평가용 자료를 추가하더라도 장소별 관측 분포에 합치지 마세요.
- 합성 계산 테스트나 일반 문장 corpus의 성공을 실제 식당 리뷰 정확도로 주장하지 마세요.
- 공급자 build·도시·업종·언어 모델·정책의 조합별로 출시 gate를 관리하세요.
