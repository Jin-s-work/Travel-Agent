## 1. 묶음 A — 최대 200개 후보를 실제로 평가하는 구조

### 1.1 후보 수와 처리 순서

설정은 최소한 다음을 분리해.

| 설정 | 기본값 | 단위 |
| --- | --- | --- |
| candidate_pool_limit | 200 | 고유 canonical 지점 |
| raw_record_limit | 400 | 중복 제거 전 장소 레코드, 공급자/예산 상한 우선 |
| initial_visible_limit | 6~12 | 처음 보여줄 카드 |
| result_page_size | 12 | 고정 결과 추가 보기 |
| review_record_limit_per_place | 200 | 별점 전용 포함 고유 리뷰 레코드 |
| review_window_days | 180 | 리뷰 관측 기간 |

처리 순서는 조건 snapshot → 저장 카탈로그/유효 캐시 후보 구성 → 부족 범위만 수집 → 지점 중복 제거 → 도시/분류/지리 범위 자격 → 최대200 pool → 방문/언어 필수 조건 → 모델 점수 → 다양성 → 저장된 순위 → 설명이야.

- SQL 카탈로그, 검수 팩, 공급자 캐시의 동일 지점을 한 번만 세어. 같은 지점이 현지어와 유명한 곳에 함께 나와도 pool 수를 부풀리지 마.
- 동일 이름을 같은 지점이라고 판단하지 마. 외부 ID·주소·좌표·공식 링크를 대조하고 모호하면 unresolved로 남겨.
- 200개를 넘으면 범위·거리·자료 자격을 이용한 결정적 사전 선택 규칙을 버전 관리해. API 응답 순서나 이름순으로 잘라 우연히 뒤쪽 좋은 후보를 버리지 마.
- 200개 pool의 적합 후보를 모두 평가한 뒤 상위 목록을 만들어. 초기12개/60개를 잘라 놓고 점수를 계산하지 마.
- 200번째 후보가 가장 적합한 fixture에서 실제로 상위에 나올 수 있어야 해.
- 자료가 37곳뿐이면37곳이 정상적인 부분 결과야. 무관한 식당·다른 도시·합성 장소를 채우지 마.
- 종류별 분포·제외 사유를 기록해. 볼거리 자료가 식당 요청의 후보 수를 채우지 않게 해.

`requested_limit, fetched_count, unique_count, deduped_count, eligible_count, scored_count, displayed_count, deferred_count, coverage, truncation_reason`의 의미와 중복 집계 여부를 명세해. 추출 불명·조건 탈락·예산 중단·공급자 종료를 분리해.

### 1.2 현재 공개지도 공급자의 범위를 해결해

현재 코드의 도심 고정 검색과 MAX_CANDIDATES=60 제한을 확인해. 상수만200으로 바꾸고 끝내지 마.

- 공급자가 공식적으로 지원하는 페이지/cursor/지리 검색 계약과 상한을 조사해.
- 허용되는 경우 cursor 또는 예산 내 공개 지역 분할로 후보를 합쳐. 반복 cursor, 중복 지점, 정렬 불안정, 전체 deadline을 처리해.
- endpoint 교체로 공유 한도를 우회하거나 실패 시 무한 재시도하지 마. 기존 rate limit·cooldown을 보존해.
- 공급자가 목표 범위를 제공하지 못하면 능력을 명시하고, 허용된 대체 카탈로그/검수 팩 또는 별도 provider 인터페이스로 보완해. 새 유료 공급자는 승인된 예산·키·이용 범위가 있을 때만 활성화해.
- 후보 확보를 위해 필요한 실제 외부 요청 수를 기록해. ‘200곳 pool’이 ‘200회 외부 호출’을 의미하지 않게 해.

### 1.3 숙소와 출발점

출발점은 명시 선택 → 방문일의 확인 숙소 → 선택 동네 → 도시 중심 순으로 결정하고 실제 사용한 기준을 표시해.

- 도심 후보를 숙소에서 가까운 순으로 정렬한 것을 숙소 주변 후보 수집으로 부르지 마. 검색 범위와 정렬 원점을 별도로 기록해.
- 개인 숙소 좌표/주소를 외부로 보낼 때 기존 `consent_to_provider` 및 제공자별 승인 범위를 확인해. 이미 차단된 전송을 다른 공급자로 우회하지 마.
- 동의가 없으면 저장 지점과의 내부 거리 계산 또는 사용자가 선택한 공개 동네로 동작해. 사용자가 고르지 않은 개인 위치를 공용 캐시/로그/분석 이벤트에 넣지 마.
- 공용 후보 캐시는 provider/version/city/public-area/category/radius 등을 키로 사용하고 개인 여행 조건은 분리해.
- 직선거리 계산은 가능하면200곳 전체에 적용해. 유료 경로 matrix는 상위8~12곳 또는 선택한 장소만, 예산과 동의 범위에서 조회해.
- 경로 실패는 unknown이야. 0분이나 임의 도보 시간으로 채우지 마. 최대 이동시간이 필수 조건이면 unknown을 충족으로 처리하지 마.

### 1.4 결과 snapshot과 재사용

조건·후보 ID/버전·사실·정책·모델·clock을 저장해. 추가 보기와 상세 읽기는 동일 run을 읽으며 후보 재수집·재정렬을 하지 않아야 해.

이용 권한 철회·삭제·지점 병합 정정이 있으면 의존성을 찾아 해당 자료를 숨기거나 재확인으로 돌려. 오래된 snapshot이라는 이유로 철회 자료를 계속 제공하지 마. 반대로 무관한 지점 변경으로 모든 여행 추천을 무효화하지 마.

## 2. 묶음 B — 실제 리뷰와 관측 범위

### 2.1 현행 Apify 계약의 막힌 부분부터 해결해

기획 당시 어댑터의 `source_pagination_observable=False` 때문에 기존 strict 공개가 차단돼 있었어. Apify dataset의 offset을 Google 원천 페이지 cursor로 취급하거나 검사값을 True로 바꿔 통과시키지 마.

먼저 `docs/service-v5/reports/REVIEW_OBSERVATION_ADR.md`에 두 경로를 비교해.

- A: 원천 정렬·페이지 연속성·원문을 검증하여 기존 strict 계약을 충족하는 공급자/실행 방식.
- B: 반환받아 검증한 표본만 설명하는 새 `bounded_observation_v1` 계약. source coverage는 provider_observation이며 전수성·원천 페이지 연속성을 주장하지 않는 방식.

B는 자동 승인된 변경이 아니야. 타당성 조사와 코드 준비는 진행하되 데이터 이용 범위, 지점 일치, 원문/번역 분리, 개별 날짜, 무필터 관측, 언어 모델 평가, 비용 상한을 통과하고 관리자 정책 승인 기록이 있어야 공개해. 기존 strict_ready·배지를 재사용하지 마. 과거 run은 과거 정책으로 재현해.

어떤 계약도 성립하지 않으면 현지어 기능을 OFF로 유지하고 원인·가능한 대안·실행 도구까지 완성해. 기능 이름만 바꿔 검증 미완료 자료를 소비자 추천으로 노출하지 마.

### 2.2 실제 공급자 확인과 실행 상한

공식 Apify actor 입력/출력·build·현재 요금과 계정 잔여량을 확인해. 키 존재와 설정명만 검사하고 비밀값을 로그나 문서에 남기지 마.

- 검증된 지점 ID, actor/adapter version과 numeric build, Google 원천, 정렬, 기간, 최대 기록 수를 명시해. actor 기본값에 최대 수를 맡기지 마.
- 작성자 이름·사진·프로필·방문 이력은 출력·저장 모델에서 제거해. 가능한 제공자 옵션도 꺼.
- `language`/`hl`은 표시 언어일 수 있어. 리뷰 원문 언어로 복사하지 마.
- 발행일과 수정일 정렬을 구분해. UTC 요청 경계와 시설/도시 timezone 변환을 기록해.
- 원천 페이지 수와 dataset 읽기 페이지 수를 다른 항목으로 관리해. 원천 페이지·내부 재시도 상한을 제어할 수 없다면 unknown이지20페이지/2회 보장이 아니야.
- 공통 비용 wrapper로 실행 전에 예약하고 완료 후 정산해. 원격 총 과금 상한·timeout·취소 가능 범위를 현재 actor/API 계약으로 검증해. 오류나 응답 유실은 자동 환불하지 말고 unknown으로 남겨.
- 원격 run ID·checkpoint를 저장해. 서버 재시작이나 결과 GET 실패 때문에 동일 actor를 다시 실행하지 마. 실행 완료 후 dataset을 다시 읽는 일과 새 원격 실행을 구분해.
- 관리자 공용 장소 조사에는 별도 scope_kind와 관리자 권한을 사용해. 임의 개인 여행에 넣지 마.

무료 우선을 유지해. 파일럿 제안 상한은 배치당 $1이지만, **현재 설정·기존 승인·잔여 무료 크레딧보다 커질 수 없고 새 지출 승인이 아니다.** 계정 전체 동시 사용량도 검사해. 플랜 업그레이드·추가 충전·자동 top-up을 하지 마. 현재 범위에서 실행이 불가능하면 설정·비용 산정·중단/복구안을 완성하고 필요한 부분만 구체적으로 알리면 돼.

### 2.3 단계적 실수집

검수된 도쿄·바르셀로나 지점 중 실행 자격이 있는 대상으로 진행해.

1. 1곳×최대40건: 필드/원문/날짜/지점/원격 비용 계약 smoke.
2. 첫 실행이 통과하면3곳×최대200건: 중복·별점 전용·기간·정렬·원문 품질 확인.
3. 앞 단계와 잔여량 확인 후 두 도시 합계10곳×최대200건: 도시별 공개 가능성 평가.

앞 단계의 유효 데이터를 재사용하고 같은 지점을 무조건 다시 호출하지 마. 40건 계약 시험은 C≥100 추천 자격 통과 근거가 아니야. 결제·한도·자료 조건이 부족하면 가능한 단계까지만 실제 실행하고 나머지는 fake provider로 검증해. 수 주를 기다리거나 합성 데이터를 실제 수집으로 바꾸지 마.

### 2.4 정규화·중단·언어

- 원문 확보, 번역문만, 원문/번역 혼합, 실제 rating-only, 추출 불명, 언어 unknown을 구분해.
- 본문 존재가 확인되면 번역만 있어도 T와 U에 포함해. 본문 존재가 불명확하면 rating-only로 세지 마.
- review ID로 중복 제거하고 발행·수정 시각, cursor/offset, 관측 기간, 원문 확보 상태를 보존해. 별점 전용도 최대200 레코드에 포함해.
- 반복 cursor, 중복 ID, 정렬 역전, 날짜 불명, 중간 실패, time/budget cap을 감지해. 정상 record_cap/date_boundary/provider_exhausted와 partial을 구분해.
- B 계약의 날짜 불명 레코드는 기간 집계에서 제외하고 건수를 남겨. 순서가 검증되지 않으면 ‘최신200개’라고 표현하지 마. 부분 실패 결과는 관리자 진단용이고 소비자 추천에는 쓰지 마.
- 공급자 종료는 Google 전체 리뷰를 전수 확보했다는 뜻이 아니야.
- T=C+U, L+K≤C, 음수/중복 합계 금지를 순수 함수로 검증해. 표시 비율은 L/C·K/C, 보수 조건은 L/T·(K+U)/T이며 분모0은null이야.
- 기본 조건은 C≥100, U/T≤10%, L/T≥60%, (K+U)/T≤10%, 같은 플랫폼 평점≥4.2/5·전체 평가≥200을 버전 관리해. 전체 평가 수를 언어 비율 분모에 넣지 마.
- ‘관측 리뷰 모두 현지어’는 L=T=C, K=U=0, 영향을 줄 추출 불명0과 나머지 자격을 모두 요구해. 한국어0건만으로 통과시키지 마.
- 도쿄 ja, 바르셀로나 es/ca를 유지해. 도시 입력100개 지원과 도시별 언어 정책/실제 데이터 지원은 별개야.
- 가벼운 기존 로컬 언어 판별기를 우선 사용해. 모든 리뷰를 LLM에 보내지 마. 짧은 메뉴명·이모지·혼합 언어를 과신하지 마.

### 2.5 실제 언어 품질 평가와 화면

모델/라이선스/메모리/판별 threshold를 기록해. 개발 자료와 최종 평가를 분리하고 실제 원문에 사람이 검토한 정답을 사용해. 번역문을 원문 정답으로 쓰지 마.

현지어 precision, 한국어 recall, unknown 비율, 언어별 표본 수와95% 구간을 보고해. 한국어 정답 표본이 없으면 recall=null이며 품질 통과가 아니야. 합성 계산24사례를 통과했다고 언어 정확도를 입증했다고 쓰지 마.

관리자는 장소별 상태·비용·수신/고유/본문/판별/미판별·기간·종료 이유를 확인할 수 있어야 해. 소비자는 짧은 관측 근거와 상세의 분모·미판별·확인일을 볼 수 있어야 해. 추천 버튼을 누를 때마다 재수집하지 말고 유효한 집계를 재사용해.

## 3. 묶음 C — 사진이 실제로 표시되는 경로

현재 사진은 정확한 지점 Commons/Wikidata 연결이 중심이야. 사진이 없는 비율과 네트워크 실패 비율부터 나눠 측정해.

- 상태는 available/loading/no_photo/provider_failed/expired/policy_blocked/identity_unresolved로 구분해.
- 사진마다 canonical 지점, provider/asset ID, 출처, 표시 권한, attribution, 만료/갱신 규칙을 보존해.
- 기존 허용 사진을 재사용하고, 추가 공급자는 지점 일치·이용 가능 범위·비용이 확인된 경우만 연결해. Google Place Photos를 쓰면 이름 만료·캐시 제한·저작자 표시 계약을 별도로 구현해.
- Apify 리뷰 토큰만으로 별도 사진 API가 준비됐다고 판단하지 마. 새 계정/유료 공급자가 필요하면 독립 OFF 상태로 완료해.
- 허용된 사진이 있으면 음식·내부·외관을 섞어 최대3장 보여줘. 분류 근거가 없으면 unknown을 유지해. 다른 지점·도시 일반 사진·생성 이미지를 실제 식당 사진으로 넣지 마.
- 첫 사진 우선, 나머지는 lazy load. 폭/높이 예약으로 레이아웃 변화를 줄여. 잘못된 MIME·과도한 크기·redirect·내부망 URL·만료를 기존 fetch 정책으로 검사해.
- no_photo negative cache와 provider_failed backoff를 구분해. 404/권한 철회/만료를 무한 재시도하지 마.
- 사진 클릭/슬라이드 때문에 리뷰 수집·추천 job을 실행하지 마.
- 식당 적합성 점수에 사진 개수를 몰래 넣지 마. ‘사진이 있는 곳’이라는 명시적 선택 기능을 도입한다면 별도 필터로 기록해.

실제 노출한 허용 사진 중 img load 성공률, 사진 미보유율, 지점 오류, 비용을 별도로 보고해. 3장이 있는 장소만 골라 전체 서비스의 사진 성공률처럼 보고하지 마.

## 4. 묶음 D — 모델을 비교하고 좋아진 경우에만 바꿔

### 4.1 현재 기준선 고정

현행 hybrid_v5는 TF-IDF/태그·보정 평점·거리 등의 결정적 비학습 모델이야. 먼저 실제 코드를 확인하고 입력, 성분, 누락 처리, famous 근거 유형 우선순위, 실행별 IDF·평점 prior를 문서화해.

후보를200개로 늘리면 IDF·prior가 달라질 수 있어. ‘후보 확대+v5’와 ‘동일 후보+v6’를 별도 실험해. 과거 hybrid-v4 합성 개발 점수를 v5/v6 실서비스 정확도라고 옮겨 적지 마.

### 4.2 v6 실험

- 현지어와 유명한 곳의 자격·점수 모델을 구분해. 언어가 확인되지 않은 유명 식당을 현지어 모델로 승격하지 마.
- 명시 cuisine·태그·다국어 음식 별칭과 취향 일치를 개선해. 건강/식단 필수 조건은 의미 유사도로 추정 확정하지 마.
- famous의 official/platform/editorial 고정 우선순위와 유형별 순위 후 interleaving을 비교해. 서로 다른 척도의 점수를 검증 없이 합치지 마.
- 같은 체인·동네·유형의 독점을 줄이는 soft 다양성을 적용할 수 있어. 필수 조건·언어 자격을 완화해서 결과 수를 채우지 마.
- 같은 입력과 clock에서 결과가 같도록 안정적인 tie-break와 후보/feature/model/policy 버전을 기록해.
- 사용자 피드백은 명시적으로 선택한 범위에서만 반영해. 단순 노출·클릭을 장기 취향 정답으로 사용하지 마.
- 누락 feature는null과 자료 부족 상태로 남겨. 남은 가중치를 몰래 재분배하거나 missing을 유리한 숫자로 채우지 마.
- 선택적으로 기존 text-embedding-3-small을 허용된 공용 장소 설명에 사전 계산하는 실험을 추가할 수 있어. 매 요청200개 호출은 금지야. 본문·모델·정책 해시로 재사용하고 비용 wrapper·예산을 적용해.
- embedding 미설정/예산 소진 시 완전한 v5 경로로 작동해. 같은 run 안에서 전환을 숨기지 말고 사용한 버전을 기록해.
- LLM은 서버 후보와 근거를 설명하는 역할만 맡아. 새 장소·순위·예약 사실을 만들면 validator가 거절하고 템플릿으로 복구해.

### 4.3 평가 자료와 성능 주장

실제 두 도시의 허용 장소 자료로60개 질의를 목표로 해. 도시별30개 중 개발10/최종평가20개를 분리해. 부족하면 확보한 수와 미측정을 그대로 남겨. 합성 질의는 경계·회귀 시험용이지 실제 추천 만족도의 대체물이 아니야.

질의에는 숙소 원점, 음식 선호, 가격, 무선호, 현지어, 유명한 곳을 포함해. 사람이 모델 순위를 보지 않고0~3 관련성 라벨과 이유를 작성하도록 평가 도구를 제공해. 코드 feature를 그대로 정답 label로 생성하지 마. 사람이 검토하지 않은 라벨은 unlabeled야.

독립적인 관련 장소 목록을 사용해 Candidate Recall@200을 측정해. 후보 목록에서 누락된 정답도 분모에 포함해. 후보로 들어온 장소만 평가해 recall을 높게 만들지 마.

동일 후보·사실·정책·clock에서 v5/v6의 NDCG@5, Precision@5, 결과5개 충족률, 다양성, 필수 조건 위반을 비교해. 개발/holdout의 동일 질의·복제 리뷰·지점 누출을 점검하고 질의/여행 그룹 분할을 기록해. test set을 보며 튜닝하지 마.

PRD의 관련성 기준(label≥2), Precision@5 고정 분모5, NDCG gain=2^label−1, 분모0/미라벨 처리도 구현해. 결과가2개라고 Precision의 분모를2로 바꿔 성과를 높이지 마. 모델이 달라지면 미라벨 상위 결과가 생길 수 있으므로 평가에서 숨기지 말고 추가 블라인드 검토 대상으로 분리해.

초기 전환 가설은 holdout NDCG@5 절대+0.03 이상, 주요 도시/방식에서 -0.02 초과 퇴행 없음, 필수 위반0, warm p95 기준선 대비20% 초과 악화 없음이야. paired bootstrap 구간, 질의별 변화와 표본 수를 함께 보고해. 근거가 불충분하면 v5 유지·v6 shadow로 남겨.

LLM 설명 충실도와 결정적 순위 평가는 별도야. 실제 저장률·방문 만족도는 관측하지 않았다면 미측정으로 두고 재실행 방법만 제공해. 수 주를 기다리거나 가짜 성과를 만들지 마.

## 5. 동시성·운영·회귀 검증

PRD D01~D06, R01~R07, M01~M05와 1단계 핵심 흐름을 실행해. 기존 provider/normalization/language/metrics/recovery/remote_cleanup/contract/recommendation/photo 테스트를 조사하고 영향 범위에 맞게 확장해.

필수 경계 시험:

1. 후보200개 중 마지막에 있는 적합 장소, 중복 공급자, raw400 상한, 실제37개.
2. 전체 후보 평가 후 페이지 조회, 추가 보기 외부 호출0, snapshot 순서 고정.
3. 개인 숙소 외부 전송 동의 없음, 다른 사용자 run/cursor·사진 manifest 접근.
4. T200 C190 U10 L150 K4 계산과 한국어0/unknown70, 분모0, rating-only·추출 불명.
5. Apify 원천 페이지 비관측, dataset pagination과 원천 pagination 혼동 차단.
6. 원격 성공 후 응답 유실/프로세스 종료, checkpoint 복구, lease 만료 후 늦은 결과 fencing.
7. 마지막 예산에 동시 요청2개, 중복 key, 같은 key 다른 payload409, unknown 비용 보존.
8. 부분 수집·정렬 역전·날짜 불명·반복 cursor와 정상 종료 분리.
9. 사용자가 여행을 지운 뒤 늦은 작업 완료, 이용 권한 철회와 결과 캐시 무효화.
10. 사진 없는 장소·잘못된 지점 사진·만료·404·attribution·큰 이미지.
11. 동일 pool v5/v6 비교, 사진 유무만 변경, 임베딩 장애, 실제 평가 표본 부족.
12. 합성 사용자5명, 문서 분석과 추천 작업이 겹치는 환경에서 queue wait·p50/p95·메모리·오류·재시도·실제 provider call 수·비용.

무료 Render의 cold start는 warm 성능에서 분리하고 측정값의 환경을 명시해. 깨우기용 인위적 ping이나 자동 증설로 목표를 맞추지 마.

브라우저에서는 여행/방문일/숙소 확인→현지어/유명한 곳 전환→사진→저장→상세→일정 preview/apply→새로고침을 검증해. 실제 자료와 합성 자료의 확인 경로를 분리해. 지점 수·표본·확인일이 화면 계약과 맞는지 확인해.

기존 `scripts/review_language_eval.py`, `scripts/build_recommender_benchmark.py`, `src/research/evaluation.py`와 CLI를 재사용해. 명령의 실제 인자와 출력 형식을 확인하고 재현 가능한 실행 예시를 남겨. 필요한 새 명령은 구현·실행한 뒤 문서화해. 존재하지 않는 평가 명령을 만들어 적지 마.
