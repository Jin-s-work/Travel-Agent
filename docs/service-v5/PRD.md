# 고잉 v5 PRD — 적게 입력하고, 고를 만한 장소를 찾기

2026-10-08 · 구현 전 기획 · 본인과 초대한 소수 지인용 비공개 베타

이 문서의 수치와 새 계약은 목표·가설이다. 실제 사용자 성과나 출시 완료를 뜻하지 않는다. [현재 확인한 근거](AUDIT.md)를 바탕으로 하며, 기존 인증·예약·일정·예산·삭제 계약은 보존한다.

## 1. 제품 방향

**여행의 도시와 날짜만 정하면 고를 만한 장소가 보이고, 마음에 든 곳을 저장해 예약과 일정까지 이어 쓴다.**

차별점은 ‘관측한 원문 리뷰에서 현지어가 충분하고 한국어가 적은 식당 찾기’다. 처음 방문하는 도시의 유명 식당과 대표 명소를 찾는 경험도 독립적으로 제공한다. 현지어 비율을 주민 비율·국적·맛의 보증으로 바꾸지 않는다.

이번에는 기능의 개수를 늘리는 것보다 아래 문제를 해결한다.

1. 첫 결과까지 무엇을 입력하고 눌러야 하는지 헷갈린다.
2. 후보가 적거나 필요한 지역에 없으면 좋은 모델도 적절한 식당을 추천할 수 없다.
3. 사진과 실제 리뷰가 부족한 상태를 UI 변경만으로 해결하려고 해서는 안 된다.
4. 추천·보관함·일정이 각각 존재해도 사용자가 같은 선택을 반복해야 하면 연결된 경험이 아니다.

이름·로고·색·Pretendard를 유지한다. 새 프레임워크로 옮기거나 이미 구현한 기능을 다시 만드는 프로젝트로 확대하지 않는다.

## 2. 최신 출발점

| 영역 | 재사용할 구현 | 이번에 해결할 부분 |
| --- | --- | --- |
| 여행과 예약 | 초대 인증, 여행 구간, 메일 분석·교정·수동 입력 | 맥락 재입력 방지와 한 번에 이해되는 다음 행동 |
| 홈과 탐색 | 최근 장소, 질문 입력, 탐색 자동 시작, 조건 초안 복원 | 추천 방식 구분, 활성 조건·진행 결과 일치 |
| 추천 모델 | hybrid_v5, 버전 snapshot, TF-IDF·평점·직선거리 | 후보 확보와 독립 평가를 먼저, 개선은 v6 후보로 비교 |
| 장소 데이터 | 공개지도 캐시, 검수 팩, canonical 지점 | 도심 60개 제한을 최대 200개 후보 비교 구조로 확장 |
| 리뷰 | Apify 키 연결, 어댑터, 집계·언어·관리자 계약 | 실제 수집과 어댑터 한계를 해결하는 명시적 관측 계약 |
| 사진 | 정확한 지점의 Commons 연결, 허용 사진 manifest | 음식·내부 사진 공급, 실패·빈 결과 구분 |
| 일정 | validator, preview/apply/undo, 잠정안 | 저장한 선택과 날짜를 이어받는 짧은 편집 흐름 |
| 운영 | Render Free, Supabase, job·예산·복구 | 수집과 조회 분리, 도시별 공개, 자원 측정 |

기획 시점의 현지어 리뷰 실수집·실제 언어 품질 평가·엄격 기능은 미완료/OFF다. 100개 도시 입력 지원을 100개 도시의 충분한 추천 자료 확보로 표현하지 않는다.

## 3. 범위와 구현 순서

### 1단계: 쉽게 찾고 저장하며, 이어서 쓰기

- 첫 진입, 홈/탐색, 조건 입력, 저장·일정 연결의 일관성.
- 설명 가능한 상태와 실패 복구, stale 결과·늦은 응답 처리.
- 추천 결과 계약과 측정 기반. 200개 후보를 받아도 UI가 동작하도록 구성.
- 현재 자료와 현재 모델로 완성. 실제 리뷰 공개나 새 유료 공급자가 선행조건은 아니다.

### 2단계: 후보·리뷰·사진을 채우고 품질을 비교하기

- 지점 중복을 제거한 최대 200개 후보 확보·평가.
- 숙소 원점의 지리 범위, 유형별 자료, 실제 리뷰 수집.
- 어댑터의 관측 가능 범위·언어 품질을 분리하고 도시별 공개.
- 사진 공급과 lazy loading, 평가 자료, v5/v6 비교.
- 성능 향상이 입증되지 않으면 v5를 기본으로 유지.

자동 예약·결제·메시지 발송, 친구 초대 자동 발송, 지도 제공자 무제한 호출, 협업 필터링의 즉시 도입, 공개 서비스 전환, 발표 자료 수정은 제외한다.

## 4. 사용 흐름과 행동 수

행동 수는 인증 후 화면의 의미 있는 클릭 기준이다. 날짜 입력의 각 키 입력을 클릭 수에 넣지 않는다. 첫 로그인·동의·확정 예약 보호를 억지로 세 번 안에 맞추지 않는다.

| 사용 상황 | 목표 흐름 | 목표 |
| --- | --- | --- |
| 기존 여행에서 장소 찾기 | 추천 화면 진입 후 기존 조건·결과 확인 | 조회에 추가 필터 입력 0회 |
| 새 여행 만들기 | 도시·날짜 입력 후 만들기, 탐색 자동 연결 | 생성 후 별도 ‘초기 설정 완료’ 화면 없음 |
| 마음에 든 장소 저장 | 카드의 저장 | 1회, 성공 후 상태 유지 |
| 추천 방식 변경 | 현지어 리뷰 / 유명한 곳 선택 | 유효 저장 결과가 있으면 수집 없이 보기 전환 |
| 조건 수정 | 날짜·출발점·음식 취향 중 필요한 것만 수정 | 전체 조건 폼 재입력 없음 |
| 저장 장소로 일정 만들기 | 날짜와 선택 목록 확인, 미리보기, 적용 | 기존 입력 재사용, 확정 단계는 유지 |
| 예약 질문 | 메인 질문란에 입력, 전송 | 메뉴를 먼저 찾지 않아도 됨 |

### 첫 진입 기본값

- 로그인 후 마지막 여행과 마지막 화면을 복원한다. 복원할 상태가 없으면 ‘찾기’가 첫 행동이다.
- 여행 도시는 방문일에 해당하는 단일 체류 구간을 사용한다. 여러 구간이 겹치면 도시만 짧게 선택한다. 구간이 없으면 날짜/도시 불일치 한 곳을 수정하게 한다.
- 방문일은 여행 기간 내 현지 오늘, 미래 여행은 시작일, 종료 여행은 마지막 선택일 또는 시작일을 사용한다. 자동 결정의 근거를 context에 남긴다.
- 인원은 여행의 저장 값을 재사용한다. 미입력 아동·식단·접근성 조건을 임의로 충족 처리하지 않는다.
- 숙소는 해당 날짜의 확인된 숙소를 우선 제안한다. 숙소가 여러 개면 이름으로 고르게 한다. 숙소 미정이어도 탐색할 수 있다.
- 서버와 화면 모두 연도 네 자리, 유효 날짜, 시작≤종료, 도시별 timezone을 검사한다. 잘못된 필드 옆에 오류를 표시하고 나머지 입력은 유지한다.

## 5. 정보 구조

상위 이동은 ‘찾기 / 저장한 곳 / 일정 / 예약’으로 정리하는 안을 기본으로 한다. 기존 홈은 로고로 돌아가는 여행 요약으로 유지할 수 있다. 구현 전 모바일에서 기존 메뉴 대비 과업 시간을 비교하고 불필요한 메뉴 이동을 늘리지 않는다.

‘여행에 물어보기’는 홈 입력란과 항상 접근 가능한 명확한 버튼으로 유지한다. 숨겨진 더보기 안에만 두지 않는다. 질문 화면의 URL/진입 경로도 유지한다. 새 알림·예산·설정 메뉴를 상단에 늘리지 않는다.

### 찾기 화면

```text
도쿄 여행   11월 7일   2명
출발: 선택한 숙소                     조건 수정

현지어 리뷰         유명한 곳
음식점   카페   볼거리                음식 취향

사진 / 원어명 / 선택 이유 / 거리·가격 / 저장
사진 / 원어명 / 선택 이유 / 거리·가격 / 저장

추가 장소 보기
주변 장소 둘러보기
```

- 두 핵심 구획의 자격과 결과는 섞지 않는다. 일반 지도 후보는 ‘주변 장소 둘러보기’라는 별도 영역이다.
- 홈 미리보기도 현지어와 유명한 곳을 구분한다. 유명 후보가 먼저 3개를 채워 다른 구획을 가리지 않도록 한다.
- 현지어 미지원 도시는 준비 중 한 문장과 ‘유명한 곳 보기’ 또는 ‘주변 장소 보기’를 제시한다. 사용자가 고른 탭을 몰래 바꾸지 않는다.
- 모든 종류가 자료를 가진 것처럼 보이는 필터를 만들지 않는다. 미지원 종류에는 미지원 상태를 보여준다.
- 숫자 조절은 기본 화면에서 빼고 ‘리뷰 기준’으로 옮긴다. ‘현지어 위주’, ‘관측 리뷰 모두 현지어’를 기본 선택지로 둔다.
- ‘관측 리뷰 모두 현지어’는 공급자가 제공한 전수나 Google 전체 리뷰가 아니라, 검증된 관측 범위의 본문을 뜻한다. 표본 수는 숨기지 않는다.

### 카드·상세·비교

- 카드: 사진 최대 3장, 이름·원어명, 선택 이유 최대 2개, 출발점 기준 거리, 비교 가능한 가격, 저장. 내용이 없는 칸을 경고문으로 채우지 않는다.
- 언어 카드에는 ‘관측 본문 180건 중 일본어 160건’처럼 관측 범위가 드러나는 짧은 근거를 둔다. 정확한 분모·미판별은 상세에서 확인한다.
- 방문일의 확정 휴무·정원 위반은 추천에서 제외한다. 가격·좌표 누락은 해당 값을 미확인으로 남긴다.
- 카드에서 강하게 보여줄 미확인은 선택을 바꾸는 항목 1개가 우선이다. 나머지는 상세의 ‘방문 전 확인’에 정리한다. 법정/공급자 attribution은 제거하지 않는다.
- 사진 없음 확정 상태는 텍스트 중심 카드로 전환한다. 로딩 상태와 실패·사진 미보유를 같은 빈 이미지로 처리하지 않는다.
- 상세의 우선순위는 방문 판단, 운영·예약, 가격, 리뷰 근거다. 원어명·주소 복사와 지도 열기를 가까이 둔다.
- 비교는 같은 방문일·인원으로 최대 3곳. 빠진 가격이나 거리 때문에 다른 조건의 수치를 섞지 않는다.

### 저장과 일정

저장은 서버 성공 뒤 확정 표시한다. 낙관 UI를 쓰면 실패 시 되돌리고 이유를 알려준다. 중복 클릭·화면 재진입·홈/탐색 간 상태를 공유한다. ‘이미 저장됨’을 실패로 표시하지 않는다.

저장한 곳에서는 날짜를 바꾸지 않고 ‘일정 미리보기’로 이어간다. 잠정안 허용은 별도 선택이며 확인된 휴무·예약 충돌은 허용하지 않는다. apply 직전 version·삭제·권한·고정 예약·신선도를 재검증한다. undo는 새 revision으로 복원한다.

## 6. 필터·로딩·실패 계약

보기 상태와 서버 입력 상태를 분리한다.

- 화면 탭·사진 넘기기·저장 목록 정렬은 표시 상태다. 외부 호출이나 새 추천 job을 만들지 않는다.
- 방문일·도시·출발점·필수 조건·언어 기준 변경은 추천 입력이다. 이전 결과를 유지하고 ‘이전 조건’ 표시 후 새 결과로 교체한다.
- 짧은 분류 선택은 한 번의 요청으로 합친다. 상세 조건 패널은 ‘적용’ 한 번에 제출한다. 모든 키 입력에 job을 만들지 않는다.
- intent와 Idempotency-Key는 서버 기준 payload hash로 재사용한다. 같은 key의 다른 입력은 409다.
- 클라이언트 trip_epoch/request_seq, 서버 snapshot/version을 함께 검사한다. 늦은 응답이 현재 여행·조건을 덮어쓰지 못하게 한다.
- 목록 골격은 처음에만, 자료가 있으면 기존 목록을 유지한다. 완료 퍼센트 대신 ‘저장 자료 확인’, ‘주변 장소 조회’, ‘조건 비교’와 실제 처리 건수를 보여준다.
- 완료 job과 결과 조회 실패를 구분한다. 결과 읽기 재시도 때문에 외부 작업을 재실행하지 않는다.

### 상태는 한 enum으로 모두 합치지 않는다

`job_state`, `availability_state`, `freshness_state`, `result_count`, `blocking_reason`, `warnings[]`, `next_actions[]`를 구분한다. 실제 DB 구조는 기존 상태 모델을 확장하되 중복 저장을 최소화한다.

| 사용자 상태 | 예시 문구 | 다음 행동 |
| --- | --- | --- |
| 기능 미지원/검증 중 | 이 도시의 현지어 리뷰를 준비하고 있어요 | 유명한 곳 / 주변 장소 |
| 조건 불충족 | 현재 조건에 맞는 곳이 2곳 있어요 | 2곳 유지 / 조건 수정 |
| 공급자 실패 | 새 자료를 가져오지 못했어요 | 유효 기존 결과 / 재시도 가능 시각 |
| 예산 소진 | 추가 조사는 잠시 멈췄어요 | 저장된 장소 계속 보기 |
| 결과 읽기 실패 | 추천은 끝났어요. 결과를 다시 불러올게요 | 같은 run GET 재시도 |
| 세션 만료 | 다시 로그인하면 이어갈 수 있어요 | 안전한 복귀 / 개인정보 캐시 정리 |
| 조건 버전 충돌 | 다른 화면에서 조건이 바뀌었어요 | 값 비교, 선택 후 재시도 |

운영 OFF가 다른 UNKNOWN 사유 때문에 ‘추천 0건/품질 부족’으로 보이지 않도록 우선순위를 명세하고 시험한다.

## 7. 후보 상한: 장소 200곳과 리뷰 200건을 분리

**사용자 요청 반영: 한 추천 요청에서 중복 지점을 제거한 장소 후보를 최대 200곳까지 비교한다. 기존 60곳을 제품 기준으로 유지하지 않는다.**

| 설정 | 의미 | 초기값 |
| --- | --- | --- |
| candidate_pool_limit | 도시·유형·탐색 범위 안의 고유 지점 후보 상한 | 200곳 |
| raw_record_limit | 중복 제거 전 읽을 원시 장소 레코드의 안전 상한 | 400건, 공급자·예산 상한이 우선 |
| initial_visible_limit | 화면 첫 노출 | 6~12곳 |
| result_page_size | 저장된 run의 추가 보기 | 12곳 |
| review_record_limit_per_place | 별점만 있는 기록을 포함한 고유 리뷰 수 | 200건 |
| review_window_days | 관측 대상 기간 | 최근 180일 |

- 200곳은 매번 200회의 유료 상세 조회를 하거나 반드시 200곳을 만들어야 한다는 뜻이 아니다.
- 기존 SQL 카탈로그·검수 팩·유효 캐시에서 후보를 합치고 지점을 중복 제거한다. 부족한 범위만 공급자로 보충한다.
- 도시/분류/지리 범위와 지점 자격을 적용한 뒤 200곳 pool을 만들고, 세부 방문·언어 조건 평가 후 순위와 다양성을 계산한다. 수집 초기 12개/60개를 잘라 놓고 모델을 적용하지 않는다.
- 후보 수가 넘으면 범위·거리·자료 자격에 따른 사전 선택 규칙을 버전 관리한다. 단순 공급자 응답 순서·이름 순서로 자르지 않는다.
- 최종 제외 후보도 집계해 수집 부족/조건 탈락을 구분한다. 수집 범위를 넓히거나 필수 조건을 자동 완화하지 않는다.
- 공유 지점은 한 번만 pool에 포함한다. 현지어/유명한 곳에서 각각 평가할 수 있지만 후보 수를 두 번 부풀리지 않는다.
- UI 추가 보기는 고정 snapshot을 cursor로 읽는다. 더 보기만으로 재수집하거나 기존 순서를 바꾸지 않는다.
- `requested_limit, fetched_count, unique_count, deduped_count, eligible_count, scored_count, displayed_count, deferred_count, coverage, truncation_reason`을 기록한다.
- provider가 한 번에 60개만 주면 무조건 limit=200으로만 바꾸지 않는다. 공식 계약이 허용하는 cursor/페이지 또는 범위 분할과 전체 예산을 사용한다. 지원하지 않는 provider는 부분 결과를 반환한다.

## 8. 숙소 주변 후보와 거리

현재 도심 고정 검색과 숙소 기준 재정렬을 구분한다. 목표는 ‘숙소 근처에 있는 후보를 확보한 뒤 비교’하는 것이다.

- 원점 우선순위: 명시적으로 고른 출발점, 해당 날짜 확인 숙소, 사용자 선택 동네, 도시 중심. UI에 실제 기준을 보여준다.
- 외부에 숙소 좌표·주소를 전송할 때는 기존 `consent_to_provider`와 승인 범위를 확인한다. 예전 차단을 우회하거나 동의를 다른 제공자에 자동 재사용하지 않는다.
- 동의가 없으면 이미 저장된 지점과의 거리를 서버에서 계산하거나 사용자가 고른 공개 동네 범위를 사용한다. 이를 숙소 주변 전체 검색이라고 부르지 않는다.
- 캐시는 provider/version/city/public-area/category/radius 단위로 저장한다. 개인 숙소명·상세 위치를 공용 캐시 키·로그·URL에 넣지 않는다.
- 후보 200곳 전체에 유료 경로 matrix를 돌리지 않는다. 직선거리로 비교 후 상위 8~12곳 또는 사용자가 선택한 곳만, 예산과 동의 범위에서 경로를 확인한다.
- 경로가 없으면 거리만 표시한다. 도보 0분·도시 중심으로부터의 거리를 숙소 거리로 표시하지 않는다.
- 가까운 곳 우선은 순위 선호이고 최대 거리/이동시간은 필수 조건이다. 둘을 혼용하지 않는다.

## 9. 리뷰 수집과 제품 공개

### 현재 막힌 지점을 해결하는 방식

현재 Apify 어댑터는 dataset offset과 Google 원천 페이지를 구분해 strict 공개를 막는다. 이 검사를 True로 바꾸는 것은 해결이 아니다.

2단계에서 먼저 짧은 ADR을 작성한다.

- A: 원천 정렬·페이지 연속성·원문을 입증할 수 있는 수집 계약. 기존 엄격 판정을 그대로 충족할 때만 사용한다.
- B: 공급자가 반환한 **관측 표본**만 설명하는 새 `bounded_observation_v1`. 원천 전수성·페이지 연속성은 주장하지 않는다. 기존 strict_ready나 strict 배지를 재사용하지 않는다.

권장안은 B의 타당성을 먼저 검증하는 것이다. 현재 제품이 사용자에게 제공하려는 값이 ‘관측 리뷰의 언어 구성’이기 때문이다. 단, 이름만 바꾸고 품질을 완화하지 않는다. 데이터 이용 범위·지점·원문 분리·날짜·무필터 수집·언어 평가·비용은 반드시 통과해야 한다. 관리자 보고서가 새 정책을 명시적으로 승인하기 전에는 공개하지 않는다. 과거 run은 기존 정책으로 재현한다.

### B의 구체적 경계

- `coverage_kind=provider_observation`과 `order_assurance=verified/unknown`, 수신·고유·본문·별점 전용·추출 불명 건수를 저장한다.
- ‘최근 180일 중 반환받아 확인한 표본’으로 표현한다. 날짜를 확인하지 못한 레코드는 기간 집계에서 제외하고 사유를 남긴다.
- 최신순의 발행/수정 의미를 확인하지 못하면 ‘최신 200개’라고 표현하지 않는다. 개별 날짜 검증과 관측 시작·종료는 별도다.
- 언어·키워드·별점 선택 수집은 일반 언어 구성에 사용하지 않는다. 일부 실패 결과는 관리자 진단용이며 소비자 추천에서는 제외한다.
- 노출 카드에서 ‘관측’과 건수는 유지한다. 모든 카드에 긴 기술 경고를 반복하지 않는다. 상세에서 수집 범위를 확인한다.
- 리뷰 본문 원문을 일반 검색 Chroma·로그·분석 이벤트에 넣지 않는다. 작성자 이름·프로필·사진·방문 이력은 제거한다.
- B가 승인되더라도 전체 리뷰 언어 분포·현지 주민 비율·거주지 판정을 하지 않는다.

### 수집 기본 계약

검증된 canonical 지점과 Google 외부 ID를 입력으로 받아 최신순·최근 180일·최대 200개 고유 레코드로 시작한다. 별점만 있는 기록도 상한에 포함한다. 실행 시 actor numeric build, 옵션, 기간 UTC 변환, 시도·시간·페이지·비용 상한을 고정한다.

원천 페이지 상한과 dataset 읽기 페이지 상한은 다른 설정이다. 공급자가 원천 페이지·내부 재시도를 제어할 수 없으면 unknown으로 기록하며 보장했다고 표시하지 않는다. 반면 원격 총 과금 상한·시간 제한은 반드시 실제 계약으로 검증한다.

실행 단계: 1곳×최대40건 계약 smoke → 3곳×최대200건 → 도쿄·바르셀로나 합계10곳×최대200건. 이전 단계가 통과하고 잔여 크레딧·상한을 다시 확인했을 때만 다음 단계로 간다. 40건 smoke는 언어 추천 C≥100의 통과 증거가 아니다.

### 언어와 집계

T=본문 존재 확인, C=판별, U=미판별, L=현지어, K=한국어. T=C+U, L+K≤C를 검증한다. 번역문만 있는 본문은 U, 본문 존재 불명은 별도 추출 불명이다. 분모 0은 null이다.

- 표시: L/C, K/C와 분모.
- 보수적 조건: L/T, (K+U)/T.
- 기본 조건: C≥100, U/T≤10%, L/T≥60%, (K+U)/T≤10%, 같은 플랫폼 평점≥4.2/5, 전체 평가≥200. 기존 가설값을 버전으로 유지.
- 모두 현지어: 위 자격 유지, L=T=C, K=U=0, 추천에 영향을 줄 추출 불명 0. Google 전체 리뷰가 모두 현지어라는 뜻은 아님.
- 도쿄 ja, 바르셀로나 es/ca. 다른 도시의 현지어 집합을 국가명만으로 자동 확정하지 않는다.
- Lingua 등 현재 로컬 판별기를 기준선으로 평가한다. 한국어 정답이 없으면 recall=null. 음식명·짧은 문장·이모지·혼합언어·번역 사례 포함.
- 기존 품질 정책을 우선 재사용하고, 현지어 precision·한국어 recall의 실제 표본 수와 95% 구간을 함께 기록한다. 작은 평가의 100%를 서비스 정확도 100%로 표시하지 않는다.

## 10. 사진 품질

첫 단계는 스켈레톤을 늘리는 것이 아니라 지점별 사진 수와 빈 원인을 측정하는 것이다.

- `available/loading/no_photo/provider_failed/expired/policy_blocked/identity_unresolved`를 분리한다.
- exact branch Commons/기존 허용 manifest를 유지한다. 추가 공급자는 지점 ID·표시 권한·attribution·저장 가능 기간·만료 대응을 확인한 뒤 연결한다.
- Google 사진 사용은 별도 선택 기능이다. 사진 API와 비용이 준비되지 않았다면 Apify 리뷰 토큰으로 해결된 것처럼 보고하지 않는다.
- 허용된 실제 사진이 있으면 음식, 내부, 외관을 우선 조합해 최대 3장. 종류 근거가 없으면 unknown을 유지한다. 다른 지점·도시 일반 이미지·생성 사진으로 대신 채우지 않는다.
- 첫 화면은 첫 사진만 우선, 나머지는 가까워졌을 때/갤러리 사용 시 가져온다. 이미지 크기를 예약해 레이아웃이 튀지 않게 한다.
- 실패 재시도는 상한과 backoff. 최근 ‘사진 없음’은 negative cache로 반복 수집을 막되 provider 장애와 다른 TTL을 둔다.
- 사진 충실도를 추천 적합성 점수에 몰래 섞지 않는다. 사진 없는 좋은 식당이 모델 평가에서 불리해지지 않게 별도 진단한다.

## 11. 추천 모델 개선과 평가

### 우선순위

후보 누락 해결 → 지점·조건 자격 → 설명 가능한 v5 기준선 → 다양성과 취향 개선 → 독립 평가 → 선택적 semantic 모델 순서다. LLM 모델 크기를 키우는 일을 추천 성능 개선과 동일시하지 않는다.

### v6 실험 후보

- 후보를 200개까지 확장하되 데이터 retrieval 변경과 ranker 변경을 별도 실험한다.
- 명시적 cuisine·태그·음식 별칭을 개선한다. 식단/알레르기처럼 필수 조건은 유사도나 언어 모델의 추론으로 확정하지 않는다.
- 유명한 곳의 official/platform/editorial을 무조건 고정 우선하는 현행 순서와, 유형 내부 순위 후 번갈아 배치하는 구성을 비교한다. 다른 척도의 점수를 그냥 합치지 않는다.
- 같은 체인·인접한 동일 유형이 상위 목록을 독점하지 않게 한다. 다양성은 soft 선호이며 지점·언어·필수 조건은 불변이다. 완화 여부는 diagnostics에 기록한다.
- 실제 동의한 ‘이 여행에서 제외’와 ‘다음 추천 취향에 반영’을 구분한다. 클릭만으로 선호를 영구 변경하지 않는다.
- 필요할 때 기존 text-embedding-3-small을 공개·허용 장소 설명에만 사전 계산하는 실험을 추가한다. 후보 전체를 매 요청마다 임베딩하지 않는다. 모델/본문/정책 해시로 캐시하고 비용 wrapper를 사용한다.
- embedding 미설정·예산 소진이어도 v5로 서비스가 작동해야 한다. 모델 전환은 run 단위로 기록하고 누락 성분은 null로 유지한다.

### 독립 평가 팩

실제 두 도시의 허용된 장소 자료로 총 60개 여행 질의를 목표로 구성한다. 도시별 30개, 개발 10/최종 평가20개로 나눈다. 자료가 부족하면 확보한 수와 미측정 항목을 보고하고 합성 자료로 숫자를 채우지 않는다.

질의에는 숙소 원점, 음식 선호, 예산, 무선호, 유명한 곳, 현지어 조건을 균형 있게 포함한다. 사람이 모델 순위를 보지 않고 0~3 관련성 라벨과 이유를 작성한다. 모델 특징에서 정답 라벨을 자동 생성하지 않는다. 개발/평가 간 동일 질의·복제 리뷰·같은 장소의 누출을 점검하고 분할 단위를 기록한다.

분리 측정:

1. 후보 평가: 독립적으로 만든 관련 장소 집합 대비 Candidate Recall@200. 탐색 범위가 다른 공급자끼리는 범위를 함께 기록.
2. 순위 평가: 같은 후보·사실·clock·정책으로 NDCG@5, Precision@5, 5개 결과 충족률, 체인·동네 다양성.
3. 필수 조건/지점/권한/언어 자격 위반: 0건.
4. 언어 모델: 실제 원문 평가의 현지어 precision, 한국어 recall, unknown, 표본 수.
5. 운영: warm/cold 분리 지연, 캐시 적중, 외부 호출 수, CPU·메모리·비용.
6. 실제 사용: 노출 후 저장, 일정 apply, 방문 후 피드백. 충분한 관측 전에는 미측정.

평가 정의도 버전으로 고정한다. 관련성 0~3 중 2 이상을 관련 장소로 보고, Precision@5는 관련 결과 수/5로 계산해 빈 슬롯을 감추지 않는다. NDCG@5는 gain=2^label−1을 사용하고 이상적 DCG가 0인 질의는 미측정으로 분리한다. Candidate Recall@200은 독립 정답 장소 중 pool에 포함된 수/전체 정답 수이며, 정답 수0 또는 정답 미작성은 미측정이다. 미라벨 결과를 자동으로 오답이나 정답으로 채우지 않고 평가 범위·누락 수를 보고한다.

초기 전환 가설은 holdout NDCG@5 절대 +0.03 이상, 주요 도시/추천 유형에서 -0.02보다 큰 퇴행 없음, 필수 위반0, warm p95가 기준선보다 20% 넘게 악화되지 않음이다. paired bootstrap과 질의별 변화도 보고하며 작은 표본의 통계적 확실성을 과장하지 않는다. 기준 미달 또는 신뢰구간이 불명확하면 v5 유지·v6 shadow로 남긴다.

## 12. 데이터·비용·운영 계약

- source/identity/fact/review/photo/model의 버전과 의존성을 저장한다. 무관한 출처 변경으로 모든 결과를 버리지 않는다. 관련 철회 데이터는 stale 표시만으로 계속 노출하지 않는다.
- 허용된 유효 데이터만 cache-first. 만료 사실을 확정으로 보여주지 않는다. 표시가 허용되는 오래된 결과는 시점과 만료 상태를 표시한다.
- 저장 결과 GET·탭 전환·더 보기는 paid provider 호출0, DB 쓰기0이 원칙이다. 새 데이터 수집은 기존 durable job 경로다.
- 조회/추천 캐시와 개인 초안은 사용자·여행 범위를 검증한다. 공개 지점 데이터와 개인 숙소·메모·제외 목록은 분리한다.
- 수집 전에 비용 예약, 호출 후 정산, 응답 유실은 unknown. SDK 재시도·Actor 원격 실행·공유 계정 사용량도 상한 계산에 포함한다.
- 무료 우선 정책 유지. 초기 파일럿 제안 상한은 배치당 $1, 기존 설정·승인·잔여 무료 크레딧 중 더 작은 값이다. 이 문서만으로 한도를 올리거나 유료 플랜에 가입하지 않는다.
- Render가 잠들면 dispatcher도 실행되지 않을 수 있다. 요청 시 재개·누적 작업 상태를 제공하고 정확한 시각의 상시 갱신을 약속하지 않는다. 단지 서버를 깨우기 위한 인위적인 ping을 추가하지 않는다.
- 서비스 운영 API 비용과 사용자의 여행 예상 지출은 별도다.

## 15. 공개와 다음 기능

1단계 UI는 독립 feature flag로 롤백 가능하게 한다. 2단계 후보 수집, 관측 리뷰, 새 ranker, 추가 사진 provider는 서로 독립적으로 켠다. 단계별 code/synthetic/browser/live_provider/rights/quality/city_enabled 상태를 기록한다.

우선 추가할 기능은 **이번 여행에서 덜 보기/제외**다. 기존 피드백을 재사용하고 적용 범위와 철회를 명확히 하므로 적은 비용으로 반복되는 후보를 줄일 수 있다. 그다음은 **저장한 장소끼리 가까운 순서 보기**다. 새로운 수집 없이 저장 데이터로 여행 결정을 돕는다. 둘 모두 1단계 핵심 흐름을 지연시키지 않는 작은 범위로 추가한다.

실시간 대기·잔여석, 자동 예약, 리뷰의 감성으로 맛 점수 만들기, 지인 공동편집은 후순위다. 추가하려면 관측 근거, 반복되는 사용자 문제, 비용, 필요한 외부 데이터를 먼저 확인한다. 단지 기능이 없다는 이유로 넣지 않는다.
