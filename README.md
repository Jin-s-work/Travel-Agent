## 개요

여행 한 번을 준비하면 확인 메일이 대여섯 통씩 쌓입니다. 항공권은 항공사에서, 숙소는 예약
사이트에서, 투어는 또 다른 플랫폼에서 옵니다. 필요한 정보는 모두 도착해 있지만 서로 다른
메일에 흩어져 있습니다.

체크아웃 시간을 확인하려면 메일함을 검색해 프로모션 메일을 지나 확인 메일을 찾고, 본문
중간의 표에서 시간을 읽어야 합니다. 환불 규정은 메일 하단 약관에 있습니다. 예약 메일은
발신 업체마다 형식이 달라 키워드 검색으로는 잘 걸리지 않습니다.

이 프로젝트는 메일을 구조화해 일정으로 정리하고, 자연어 질문에 **어느 메일이 근거인지
함께** 답합니다.

| 하루치 조회 | 날짜가 정해진 질문은 유사도 대신 범위 필터로 전부 가져옵니다 |

```
        ▼

        ▼

```

## 해결 내용

### 1. 메타데이터 기반 타입 필터링

유사도만으로는 주제가 비슷하되 대상이 다른 질문을 구분할 수 없습니다. 평가 과정에서 다음
사례가 나왔습니다.

```console
Q. 렌터카 예약은 몇 시에 픽업이야?
A. 픽업 시각은 07:40입니다.
```

렌터카 예약이 존재하지 않는데 투어의 집합 시각을 픽업 시각으로 답했습니다. 이때 유사도는
0.512로, 정상 질문 구간(0.27~0.65)보다 오히려 높았습니다. "픽업"과 "집합"이 의미적으로
가깝기 때문입니다. 임계값을 0.52까지 올리면 이 오답은 차단되지만 정상 질문의 절반이 함께
탈락합니다.

그래서 질문에서 예약 종류가 식별되면 해당 종류로 검색 범위를 제한하도록 했습니다. 종류가
일치하는 예약이 없으면 검색 결과가 0건이 되고, LLM을 호출하지 않고 거절합니다. 모델의
판단에 의존하지 않으므로 결과가 안정적입니다.

프롬프트로 동일한 제약을 시도했으나 실패했습니다. "종류가 다르면 답하지 않는다"는 규칙을
명시했음에도 모델이 무시했습니다.

> [!NOTE]
> 날짜 범위 필터에는 Chroma의 제약이 있습니다. `$gte`와 `$lte`는 문자열을 받지 않고
> int/float만 허용합니다. 따라서 표시·정렬용 `YYYY-MM-DD` 문자열과 필터용 `YYYYMMDD`
> 정수를 분리해 저장합니다.

### 2. 환각 방지 3단 구조

여행 예약은 오답의 비용이 큽니다. 체크아웃 시간을 잘못 알면 추가 요금이 발생하고, 환불
기한을 놓치면 금전 손실로 이어집니다. 동시에 LLM은 이 도메인의 일반 상식을 충분히 학습한
상태여서 그럴듯한 값을 채워 넣기 쉽습니다.

| 단계 | 방식 |
| :--- | :--- |
| 검색 | 절대 유사도와 1위 대비 상대 비율로 무관한 결과를 제거합니다 |
| 호출 | 임계값을 통과한 근거가 0건이면 LLM 자체를 호출하지 않습니다 |
| 생성 | 검색된 내용만 사용하도록 제약하고 답변에 출처를 표기합니다 |

거절 여부 판정은 고정 문구 하나에 의존하지 않습니다. "확인할 수 없", "찾을 수 없" 등 여러
표현을 함께 검사해 같은 의미의 다른 표현이 실패로 집계되지 않도록 했습니다.

### 3. 청킹 전략

예약 메일은 1~2KB 수준으로 짧습니다. 세분화하면 예약번호와 환불 규정이 서로 다른 청크로
분리되어 검색 성능이 오히려 떨어집니다. 메일 1건을 1청크로 유지하고, 2000자를 초과하는
경우에만 분할합니다.

### 4. 평가 설계

오답이 발생했을 때 수정 대상이 달라지므로 실패 원인을 네 가지로 분류합니다.

| 실패 원인 | 수정 대상 |
| :--- | :--- |
| 검색 실패 (top-k 밖) | 임베딩·청킹 |
| 임계값 탈락 (검색은 성공) | 임계값 설정 |
| 타입 필터 탈락 | 종류 감지 키워드 |
| 생성 실패 | 프롬프트 또는 인덱싱 데이터 |
| 환각 (거절 실패) | 파이프라인 전반 |

초기 버전은 앞의 항목들을 "검색 실패"로 묶어 분류했고, 그 결과 임계값 문제를 검색 문제로
잘못 짚었습니다. 분류를 분리한 뒤에야 원인이 특정됐습니다.

`recall@k (임계값 후)`는 `answer_question()`이 생성 단계로 실제 전달한 근거를 기준으로
측정합니다. 타입 필터가 추가로 적용되므로 검색 결과만 보면 실제와 어긋납니다.

### 5. 추출 불안정성 보정

타입 필터(1번)는 `type` 값이 맞다는 전제 위에서 동작합니다. 그런데 같은 메일이 실행할
때마다 다르게 분류되는 일이 반복됐습니다.

| 대상 | 관측된 값 | 올바른 값 |
| :--- | :--- | :--- |
| 후지산 투어 | `렌터카` | `투어` |
| 신주쿠 호텔 `provider` | `Booking.com` | `Hotel Gracery Shinjuku` |
| ANA 귀국편 | `투어` | `항공` |

ANA 귀국편이 `투어`가 되자 항공 관련 질문에서 해당 예약이 통째로 누락됐습니다. 필드
설명에 판정 기준을 자세히 적는 방식으로는 재발을 막지 못했습니다.

그래서 LLM 결과를 원문으로 검증합니다. 종류별 신호를 정규식으로 세고, 신호가 2개 이상
잡히면서 LLM 결과와 다를 때만 덮어씁니다.

```python
"항공": (
    re.compile(r"\b[A-Z]{2}\s?\d{2,4}\b"),          # 편명 KE703, NH 867
    re.compile(r"e-?ticket|항공권|탑승|boarding|PNR", re.I),
    re.compile(r"\b(ICN|NRT|HND|GMP|KIX|CTS|FUK)\b"),
    re.compile(r"위탁\s*수하물|checked\s*baggage", re.I),
)
```

개입 조건을 좁게 잡은 것이 핵심입니다. 신호가 하나뿐이면 지나가는 단어일 수 있어 근거로
삼지 않고, 1위가 단독이 아니면 판단을 보류합니다. 규칙이 확신할 때만 LLM을 이깁니다.

같은 불안정성이 `time`에도 있었습니다.

| 필드 | 원문 | 실행 A | 실행 B |
| :--- | :--- | :--- | :--- |
| ANA `time` | `Departure 18:55` / `Arrival 21:35` | `18:55 ~ 21:35` | `18:55` |
| 투어 `time` | `집합 07:40 (출발 08:00)` | `07:40 ~ 08:00` | — |

도착 시각이 빠지면 답변에서 그 정보가 사라지고, 투어에 범위가 들어가면 화면에 투어가
08:00에 끝나는 것처럼 보입니다. 두 가지를 종류에 따라 정리합니다.

- **투어**는 집합 시각 하나만 남깁니다. 짝이 되는 종료 시각이라는 개념이 없습니다.
- **항공·숙소·렌터카**는 시각이 하나만 잡히면 원문에서 `출발`/`도착`, `체크인`/`체크아웃`,
  `픽업`/`반납` 라벨이 붙은 줄을 찾아 나머지 한쪽을 채웁니다.

여기서도 개입 조건을 좁혔습니다. 규칙이 찾은 시작 시각이 모델이 준 값과 **일치할 때만**
채웁니다. 다르면 규칙이 엉뚱한 줄을 봤을 수 있어 모델 판단을 그대로 둡니다. 메일 7건에서
규칙은 5건의 시각 쌍을 정확히 찾아내고, 실제로 값이 빠진 1건만 보정합니다.

샘플·데모 메일 7건에서 규칙만으로 전부 정확히 분류되며, 1위와 2위의 점수 차는 최소
3대 1입니다.

| 메일 | 항공 | 숙소 | 렌터카 | 투어 |
| :--- | ---: | ---: | ---: | ---: |
| 대한항공 출국 | **3** | 1 | 0 | 0 |
| ANA 귀국 | **3** | 1 | 0 | 0 |
| 신주쿠 호텔 | 0 | **4** | 0 | 0 |
| 하코네 료칸 | 0 | **3** | 0 | 0 |
| 후지산 투어 | 1 | 0 | 0 | **4** |
| 하코네 렌터카 | 0 | 0 | **4** | 0 |
| 아사쿠사 투어 | 0 | 0 | 0 | **4** |

### 6. 날짜 질문은 검색이 아니라 필터로

"둘째 날 일정 뭐야?"에 이렇게 답한 적이 있습니다.

```console
Q. 둘째 날 일정 뭐야?
A. 둘째 날(2026-10-13) ... 해당 날짜 예약 내역에는 숙박 정보만 등록되어 있습니다.
```

그날 아사쿠사 투어가 인덱싱되어 있는데도 빠졌습니다. `resolve_trip_day`가 날짜를 정확히
계산해도, 뒤이은 `search_bookings`는 의미 유사도 상위 몇 건만 돌려줍니다. 날짜 문자열은
청크 본문과 유사도가 낮아 그날 예약이 상위권에 들지 못했습니다.

날짜가 이미 정해진 질문에 의미 검색을 쓸 이유가 없습니다. `bookings_on_date` 도구를 두고
메타데이터 범위 필터로 그날 예약을 전부 가져옵니다.

```python
where={"$and": [
    {"date_start_int": {"$lte": target}},
    {"date_end_int":   {"$gte": target}},
]}
```

시작·종료를 함께 보므로 3박 4일 숙박이 중간 날짜에도 걸립니다. 유사도가 개입하지 않아
누락이 원리적으로 생기지 않고, top-k에도 영향받지 않습니다.

### 7. 재시작해도 비어 있지 않도록

Render 무료 티어는 디스크가 영구 저장이 아닙니다. 인스턴스가 재시작할 때마다 인덱스가
사라져 데모 링크가 빈 화면이 됐습니다.

추출 결과를 `seed/parsed.json`에 넣어 두고, 기동 시 인덱스가 비어 있으면 그대로 읽어
채웁니다. 파싱은 이미 끝나 있으므로 **기동할 때 LLM 호출은 없고 임베딩만** 합니다.

| | 인덱스 채우기 | LLM 파싱 | 걸리는 시간 |
| :--- | :--- | :--- | :--- |
| 이전 | 수동 업로드 | 메일당 1회 | 분 단위 |
| 현재 | 기동 시 자동 | 없음 | 초 단위 |

인덱스에 데이터가 있으면 건드리지 않으므로 사용자가 올린 메일을 덮어쓰지 않습니다.
메일이나 파서를 고쳤을 때는 `make seed`로 다시 만듭니다. 시드가 낡으면 해시가 어긋나
테스트가 실패합니다.

없게 구성한 질문 6개로 이루어져 있습니다.

| 지표 | 점수 | |
| :--- | ---: | :--- |
| 검색 recall@3 (임계값 적용 전) | **100%** | 14/14 |
| 검색 recall@3 (임계값 적용 후) | **100%** | 14/14 |
| 답변 정확도 | **100%** | 14/14 |
| 환각 방지율 | **100%** | 6/6 |

### 개선 이력

| 단계 | recall@3 | 답변 정확도 | 환각 방지율 |
| :--- | ---: | ---: | ---: |
| 최초 | 85.7% | 85.7% | 83.3% |
| 임계값 0.90 → 0.75 | 100% | 100% | 83.3% |
| 타입 필터 도입 | 100% | 78.6% ↓ | 83.3% |
| 파서 `type` 판정 기준 명시 | 100% | 100% | 100% |
| 규칙 기반 `type`·`time` 보정 | 100% | 100% | 100% |

세 번째 단계에서 지표가 떨어진 것이 가장 중요한 발견으로 이어졌습니다.

타입 필터를 도입하자 투어 관련 질문 3개가 실패했습니다. 원인을 추적한 결과 필터가 아니라
파서에 문제가 있었습니다. 후지산 투어가 `렌터카`로 분류되어 있었고, 메일에 포함된 "왕복
전세버스" 표현이 원인으로 보입니다.

더 중요한 사실은 같은 메일이 실행할 때마다 `투어`와 `렌터카`를 오갔다는 점입니다.
Structured Outputs는 스키마를 강제하지만 값의 정확성까지 보장하지는 않습니다. 의미 검색만
사용할 때는 라벨이 잘못돼도 정답이 반환되어 이 오류가 드러나지 않았습니다.

필드 설명에 판정 기준을 명시하자 지표는 회복됐습니다. 다만 이후 운영 중에 ANA 귀국편이
`투어`로 분류되는 사례가 다시 나왔습니다. 프롬프트만으로는 값이 고정되지 않는다고 보고
[규칙 기반 보정](#5-추출-불안정성-보정)을 덧붙였습니다. 지표는 이미 만점이라 변화가 없고,
개선은 반복 실행 시의 안정성 쪽에 있습니다.

## 시작하기

> [!IMPORTANT]
> Python 3.13이 필요합니다. 3.14에서는 `import chromadb`가 응답 없이 멈춥니다.
> chromadb 1.5.9 기준 공식 지원 범위가 3.13까지입니다.

> [!TIP]
> 가상환경은 iCloud Drive가 동기화하는 위치(macOS의 데스크톱·문서 폴더) 밖에
> 두세요. 의존성 파일이 2만 개가 넘어 임포트할 때마다 파일 공급자를 거치면
> `import chromadb` 하나가 25분까지 걸립니다. 같은 환경을 밖으로 옮겨 4초가
> 됐습니다.

```bash
python3.13 -m venv .venv && source .venv/bin/activate
make install

cp .env.example .env   # OPENAI_API_KEY 입력, TAVILY_API_KEY는 선택
```

### 실행

| 명령어 | 설명 |
| :--- | :--- |
| `make serve` | 웹앱을 실행합니다 (http://localhost:8000) |
| `make index` | 샘플 메일을 인덱싱합니다 |
| `make seed` | 데모 메일을 다시 파싱해 시드를 갱신합니다 |
| `make ask Q="체크아웃 몇 시야?"` | 질문 1건을 실행합니다 |
| `make eval` | 평가를 실행합니다 |
| `make test` | 테스트를 실행합니다 |

메일 탭에서 예약 확인 메일을 올리면 일정 탭에 카드가 날짜순으로 정리됩니다. 질문 탭에서
물어보면 근거와 함께 답합니다. 홈 화면에 추가하면 앱처럼 실행됩니다.

터미널에서도 같은 파이프라인을 그대로 씁니다.

```console
$ make ask Q="체크아웃 시간 언제야?"

[사용한 도구: search_bookings]
체크아웃 시간은 다음과 같습니다.
- Hotel Gracery Shinjuku: 11:00 (예약번호 4471938265)
- Yumotoso Hakone (箱根 湯本荘): 10:00 (예약번호 HK-26-10884)
```

### API

`api.py` 한 프로세스가 JSON과 정적 파일을 함께 서빙합니다. 같은 출처라 CORS 설정이
없습니다. 스키마는 실행 후 `/api/docs`에서 볼 수 있습니다.

| 메서드 | 경로 | 설명 |
| :--- | :--- | :--- |
| `GET` | `/api/bookings` | 예약 목록 (날짜순) |
| `POST` | `/api/ask` | 질문 → 답변·근거·사용한 도구 |
| `POST` | `/api/index` | 메일 업로드 + 인덱싱 |
| `DELETE` | `/api/index` | 인덱스 비우기 |
| `POST` | `/api/trip-start` | "N일차" 기준일 지정 |

무거운 모듈(`chromadb`, `langchain`)은 첫 요청까지 로딩을 미룹니다. 서버는 즉시 기동하고
첫 질문만 느립니다.

## API 키 관리

키는 `.env`에만 저장하고 코드나 커밋에는 포함하지 않습니다. `.gitignore`가 `.env`와 실제
메일이 저장되는 `data/`를 제외합니다.

```bash
git check-ignore -v .env    # 규칙이 출력되면 정상입니다
```

배포 시에는 Render 환경변수로 주입하며, 저장소에는 `.env.example`만 포함됩니다.

> [!WARNING]
> 키가 한 번이라도 커밋되면 파일을 삭제해도 히스토리에 남습니다. 즉시 폐기하고 재발급해야
> 합니다.

배포 전 점검 항목은 [deploy/CHECKLIST.md](deploy/CHECKLIST.md)에, 배포 절차는
[deploy/RENDER.md](deploy/RENDER.md)에 정리했습니다.

## 한계

- **평가셋 규모**: 질문 20개, 메일 5건 규모이며 질문과 정답을 직접 라벨링해 편향 가능성이
  있습니다.
- **채점 방식**: 키워드 포함 여부로 판정하므로 의미를 반영하지 못합니다. "120,000"을
  "12만 원"으로 답하면 정답임에도 실패로 집계됩니다.
- **언어 범위**: 한국어와 영어 메일만 검증했습니다. 일본어 메일은 영문 병기 부분에
  의존합니다.
- **타입 판별**: 질문 쪽 키워드 감지는 "차 빌린 거 몇 시야?" 같은 표현을 놓칩니다.
- **규칙 기반 보정**: 한국어·영어 표현에 맞춰 뒀습니다. 일본어 전용 메일이나 처음 보는
  형식에서는 신호가 잡히지 않아 LLM 결과를 그대로 둡니다.
- **남은 추출 흔들림**: `type`과 `time`은 규칙으로 고정했지만 `provider` 표기는 실행마다
  갈립니다(`대한항공` / `Korean Air`). 둘 다 실제 항공사를 가리키므로 검색에는 영향이
  없고, 화면 표기만 달라집니다.
- **동시 사용**: 인덱스가 전역이라 다중 사용자 환경에서 데이터가 섞입니다.
- **배포 환경**: Render 무료 티어는 디스크가 영구 저장이 아니고 메모리가 512MB입니다.
  인덱스는 기동 시 시드로 복구되지만, 사용자가 직접 올린 메일은 재시작하면 사라집니다.

## 향후 계획

- **하이브리드 검색**: `8KX2QP` 같은 예약번호는 정확 일치가 필요해 임베딩만으로는 약합니다.
  BM25를 결합하면 개선 여지가 큽니다.
- **LLM-as-judge 채점**: 키워드 매칭을 의미 기반 판정으로 대체해 거짓 실패를 없앱니다.
- **임베딩 기반 타입 분류**: 정규식 신호를 수동으로 관리하는 방식에서 전환합니다.
- **추출 안정성 지표**: 같은 입력을 반복 파싱해 필드별 일치율을 측정합니다. 지금은
  불안정성을 사후에 발견하고 있어, 회귀를 수치로 잡을 지표가 필요합니다.
- **세션 단위 컬렉션 분리**: 다중 사용자를 지원합니다.
- **캘린더 연동**: 정리된 일정을 .ics로 내보냅니다.
