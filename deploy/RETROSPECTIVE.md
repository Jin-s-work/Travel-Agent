# 개발 기록

다섯 단계로 나눠 구현했습니다. 각 단계에서 마주친 문제와 해결 과정을 기록합니다.

## 1. 메일 파싱

파서는 gpt-5-mini의 Structured Outputs로 8개 필드를 추출합니다. strict 모드는 모든 필드를
required로 요구하므로 "값 없음"은 `["string", "null"]` 타입의 null로 표현했습니다.

### time 필드 형식 불안정

스키마 설명에 형식을 명시했으나 모델이 원문을 그대로 복사하는 경우가 있었습니다.

```
기대: 15:00 ~ 11:00
실제: 체크인 2026년 10월 12일 (월) 15:00 - 24:00; 체크아웃 ... 11:00까지
```

체크인 가능 시간대(15:00~24:00)를 가져오면서 체크아웃 시각 11:00이 빠졌습니다. 프롬프트를
예약 종류별로 세분화해 개선했지만 실행할 때마다 결과가 달라졌습니다. 결국 후처리에서
`HH:MM` 토큰만 추출해 재구성하는 방식으로 바꿨습니다. 모델 출력과 무관하게 형식이
보장됩니다.

### 정규식 단어 경계 문제

`\b([01]?\d|2[0-4]):([0-5]\d)\b`로 작성했는데 `11:00까지`가 매칭되지 않았습니다. 파이썬
정규식에서 한글은 단어 문자로 취급되어 `0`과 `까` 사이에 단어 경계가 생기지 않습니다.
숫자 룩어라운드로 바꿔 해결했습니다.

## 2. 벡터 검색 구축

### Python 3.14에서 chromadb import 중단

`import chromadb`에서 프로세스가 응답 없이 멈췄습니다. 에러 메시지도 나오지 않았습니다.
단계별 로깅으로 import 지점을 특정했고, chromadb 1.5.9의 공식 지원 범위가 Python 3.13까지인
것을 확인해 venv를 다시 만들었습니다.

### Chroma 비교 연산자의 타입 제약

`{"date": {"$gte": "2026-10-14"}}`가 `ValueError`를 냅니다. `$gte`와 `$lte`는 문자열을 받지
않고 int/float만 허용합니다. 표시·정렬용 `YYYY-MM-DD` 문자열과 필터용 `YYYYMMDD` 정수를
나눠 저장하는 방식으로 우회했습니다. 숙소처럼 기간이 있는 예약은 시작일과 종료일을 모두
보관합니다.

컬렉션을 만들 때 `embedding_function=None`을 명시했습니다. 생략하면 Chroma가 기본 ONNX
모델을 내려받는데, 임베딩은 OpenAI API로 직접 생성하므로 필요하지 않습니다.

### 유사도 분포 확인

초기 검색에서 "체크아웃 시간" 질의의 상위 3건이 0.261, 0.253, 0.247로 나왔습니다. 순위는
정확했지만 변별력이 낮았습니다. 검색용 문장이 "예약번호(확인번호)는 ..." 같은 공통 템플릿을
공유해 문서 간 유사도가 몰린 것이 원인입니다.

## 3. 답변 생성과 도구 라우팅

임계값을 통과한 근거가 0건이면 LLM을 호출하지 않도록 했습니다. 호출하지 않으면 생성 자체가
불가능하므로 가장 확실한 차단 지점입니다.

출처 표기를 구현하다가 메타데이터에 `confirmation_number`가 빠진 것을 확인했습니다.
2단계에서 필터에 필요한 필드만 정의했기 때문입니다. 인덱서를 수정하고 재인덱싱했습니다.

### 지시대명사 처리

도구 라우팅 테스트에서 실패가 나왔습니다.

```
Q. 그 도시 지금 날씨 어때?
[사용한 도구: 없음]
A. 어떤 도시를 말씀하시는 건가요?
```

`web_search` 호출을 예상했는데 되물었습니다. 확인해보니 라우팅이 아니라 테스트 설계의
문제였습니다. "그 도시"는 앞선 문맥이 필요한 표현인데 질문을 매번 새 대화로 실행하고
있었습니다. "도쿄 지금 날씨 어때?"로 바꾸니 `web_search`를 정상 호출했습니다. UI에는 대화
이력을 전달하도록 구현했습니다.

## 4. 평가 시스템

질문 20개를 라벨링했습니다. 답변 가능한 질문 14개와 답할 수 없는 질문 6개로 구성했습니다.
거절 테스트는 단순히 정보가 없는 항목 대신 오답을 유도하기 쉬운 항목으로 골랐습니다.
와이파이 비밀번호 질문은 메일에 있는 호텔 PIN 코드를, 보험 증권번호 질문은 "여행자 보험
포함" 문구를 끌어올 가능성이 있습니다.

### 초기 측정

```
검색 recall@3 (임계값 전)   100.0%   14/14
검색 recall@3 (임계값 후)    85.7%   12/14
답변 정확도                  85.7%   12/14
환각 방지율                  83.3%    5/6
```

두 recall 값의 차이가 문제를 드러냈습니다. 순수 검색은 14건 전부 정답을 찾았는데 임계값을
적용하니 12건으로 줄었습니다. 상대 비율 0.90이 2위로 검색된 정답을 제거하고 있었고, 그
결과 근거가 0건이 되어 답변 가능한 질문에 거절로 응답했습니다. 0.75로 완화하니 두 지표
모두 100%가 됐습니다.

### 타입 불일치 오답

환각 방지율은 그대로였습니다.

```
Q. 렌터카 예약은 몇 시에 픽업이야?
A. 픽업 시각은 07:40입니다.
```

렌터카 예약이 없는 상태에서 투어의 집합 시각을 반환했습니다. 유사도는 0.512로 정상 질문
구간(0.27~0.65)보다 높았습니다. "픽업"과 "집합"이 의미적으로 가깝기 때문입니다. 임계값을
0.52로 올리면 차단되지만 정상 질문의 절반이 함께 탈락합니다.

프롬프트에 종류 불일치 시 답변 금지 규칙을 추가하고 컨텍스트 헤더에 `type=투어`를
명시했습니다. 다시 실행한 결과 답변이 같았습니다. 모델이 규칙을 반영하지 않았습니다.
2단계에서 구현한 메타데이터 필터를 적용하는 방향으로 바꿨습니다.

### 필터 도입 후 지표 하락

필터를 적용하자 답변 정확도가 100%에서 78.6%로 떨어졌습니다. 투어 관련 질문 3건이 전부
실패했습니다. 필터 로직을 의심해 저장된 메타데이터를 직접 확인했습니다.

```
01_korean_air_outbound.txt   type='항공'
02_ana_return.eml            type='항공'
03_shinjuku_hotel.txt        type='숙소'
04_hakone_ryokan.txt         type='숙소'
05_fuji_day_tour.txt         type='렌터카'
```

후지산 투어가 `렌터카`로 저장되어 있었습니다. 렌터카 질의에는 투어가 반환되고 투어 질의에는
0건이 반환된 이유입니다. 필터는 정상 작동했고 데이터가 잘못돼 있었습니다. 메일에 포함된
"왕복 전세버스" 표현이 원인으로 보입니다.

1단계 파싱 시점에는 같은 메일이 `투어`로 분류됐습니다. 같은 입력이 실행마다 다른 값을
반환한 것입니다. Structured Outputs는 스키마를 강제하지만 값의 정확성은 보장하지 않습니다.
의미 검색만 사용하는 동안에는 라벨이 잘못돼도 정답이 반환되어 오류가 드러나지 않았고,
필터를 도입한 시점에 표면화됐습니다.

`type` 필드 설명에 판정 기준을 명시하고 재인덱싱한 뒤 전 지표가 100%가 됐습니다.

### 실패 분류 수정

평가 도구 자체도 수정했습니다. 초기에는 실패 원인을 "검색 실패 / 생성 실패 / 환각" 세
가지로 분류했는데, 임계값에 제거된 두 질문을 검색 실패로 집계했습니다. 검색은 성공한
상태였습니다. 임계값 탈락을 별도 항목으로 분리한 뒤에야 원인이 특정됐습니다. 수정 대상이
임베딩이냐 임계값 설정이냐로 갈리는 문제였습니다.

## 5. UI와 배포 준비

처음에는 Streamlit으로 만들었습니다. 화면은 빠르게 나왔지만 앱처럼 쓰기에는 한계가
분명했습니다. Streamlit은 상호작용마다 스크립트를 다시 실행하는 구조라 하단 탭바, 손가락을
따라오는 스와이프, 시트 드래그 같은 동작을 만들 수 없습니다. 프레임워크를 잘 쓰는 문제가
아니라 실행 모델이 다른 문제였습니다.

그래서 UI 계층만 걷어내고 FastAPI로 바꿨습니다. `src/`의 로직은 한 줄도 옮기지 않았습니다.
함수들이 이미 평범한 dict를 반환하고 있어서 감싸기만 하면 됐습니다.

```python
@app.get("/api/bookings")
def bookings():
    return store().all_reservations()
```

프론트는 의존성 없는 단일 HTML입니다. 한 프로세스가 JSON과 정적 파일을 함께 서빙하므로
같은 출처가 되어 CORS 설정이 없습니다.

세 가지를 신경 썼습니다.

`chromadb`와 `langchain`은 첫 요청까지 로딩을 미룹니다. 모듈 최상단에서 부르면 서버 기동이
수십 초 멈춥니다.

서비스 워커는 앱 셸만 캐시하고 API 응답은 캐시하지 않습니다. 오래된 체크아웃 시간을
보여주는 것이 연결 실패를 알리는 것보다 위험하기 때문입니다.

`sw.js`는 루트 경로에서 서빙합니다. 서비스 워커는 자기가 놓인 경로 이하만 제어할 수 있어서
`/web/sw.js`에 두면 사이트 전체를 잡지 못합니다.

환불 규정은 재인덱싱 없이 처리했습니다. 규정 전문은 메타데이터가 아니라 청크 본문에 있어서,
`all_reservations()`가 문서도 반환하게 하고 API에서 잘라 썼습니다. 스키마 변경과 LLM 재호출
5회를 피했습니다.

요약 카드에 체크인·체크아웃 시각을 표시하려고 `time`은 메타데이터에 추가했습니다. 같은
날짜의 예약은 시각순으로 정렬합니다.

배포를 준비하면서 `.gitignore` 오류를 발견했습니다. `data/`로 디렉터리 전체를 제외했는데,
git은 제외된 디렉터리 내부의 파일을 `!`로 다시 포함시킬 수 없습니다. 그 결과 `.gitkeep`까지
무시되어 디렉터리 구조가 유지되지 않았습니다. `data/*` → `!data/emails/` 순으로 단계적으로
여는 방식으로 수정했습니다.

## 6. 배포한 뒤에 드러난 것들

다섯 단계를 끝내고 배포한 뒤가 오히려 문제가 많았습니다. 대부분 로컬에서는 보이지
않는 종류였습니다.

### 프롬프트로 고정되지 않는 값

`type` 오분류를 필드 설명 보강으로 고쳤다고 봤는데, 운영 중 ANA 귀국편이 다시
`투어`로 분류됐습니다. 해당 예약이 항공 관련 질문에서 통째로 누락됐습니다.

프롬프트를 더 다듬는 대신 원문에서 종류별 신호를 세어 대조하는 방식으로 바꿨습니다.
신호가 2개 이상이고 LLM 결과와 다를 때만 덮어씁니다. 신호가 하나뿐이면 지나가는
단어일 수 있고, 1위가 단독이 아니면 판단을 보류합니다.

같은 불안정성이 `time`에도 있었습니다. ANA 메일에 `Departure 18:55`와
`Arrival 21:35`가 모두 적혀 있는데 실행에 따라 도착이 빠졌습니다. 투어는 반대로
집합 시각과 출발 시각을 둘 다 담아 화면에 투어가 08:00에 끝나는 것처럼 보였습니다.

### 날짜가 정해진 질문에 의미 검색을 쓰고 있었다

"둘째 날 일정 뭐야?"가 그날 투어를 빠뜨리고 "숙박 정보만 등록되어 있습니다"라고
단정했습니다. 날짜 계산은 맞았는데, 뒤이은 검색이 유사도 상위 몇 건만 돌려줬습니다.
날짜 문자열은 청크 본문과 유사도가 낮습니다.

조건이 확정된 질문에 검색을 쓸 이유가 없었습니다. 메타데이터 범위 필터로 그날
예약을 전부 가져오는 도구를 따로 뒀습니다.

### 로컬에서는 절대 재현되지 않는 실패

무료 티어는 재시작할 때마다 인덱스가 사라집니다. 추출 결과를 저장소에 넣어 두고
기동 시 자동으로 채우게 했는데, 배포하니 동작하지 않았습니다. `Dockerfile`이
시드를 복사하지 않았고, 시드가 참조하는 메일은 `.dockerignore`가 제외하고
있었습니다. 로컬에는 파일이 그대로 있으니 재현될 수 없는 종류였습니다.

이후 이미지 구성 자체를 검사하는 테스트를 넣었습니다.

### 응답 시간 — 추측이 두 번 틀렸다

질문 하나에 13초가 걸렸습니다. 재보니 출력 736토큰 중 640이 추론 토큰이었고,
화면에 보이는 답은 96토큰이었습니다.

`reasoning_effort`를 낮추자 평가 지표를 유지한 채 절반 이하가 됐습니다. 다만
`minimal`은 쓸 수 없었습니다. 5건 중 4건에서 근거가 있는데도 거절했고 거절 문구
자체가 "없습니다"에서 "있습니다"로 깨졌습니다. 추론이 정확도를 만들고 있었습니다.

토큰 스트리밍도 예상과 달랐습니다. 추론 모델은 추론이 끝나야 첫 글자가 나오므로
첫 글자까지의 시간이 줄지 않습니다(9.14초). 대신 1초면 끝나는 검색 결과를 먼저
보내 무엇을 찾았는지 바로 보여주는 쪽으로 바꿨습니다.

### 조건문이 낡았다

빠른 경로 조건이 "대화 이력이 없을 때"였습니다. 쓸 당시에는 맞았지만, 나중에
UI가 매 질문에 직전 대화를 함께 보내도록 바뀌면서 두 번째 질문부터는 흔한 질문도
에이전트 경로를 탔습니다. 대화를 이어갈수록 느려지는 상태가 유지됐습니다.

조건을 "이 질문이 스스로 뜻이 서는가"로 바꿨습니다.

### 테스트가 실제 데이터를 지우고 있었다

인덱스가 자꾸 비어서 배포 환경 문제로 봤는데, 원인은 테스트였습니다. "인덱스
비우기"를 검사하는 테스트가 실제 `data/chroma`에 DELETE를 보내고 있었습니다.
테스트는 통과합니다. 검사 대상이 파괴적인 동작이라 성공할수록 데이터가 사라졌습니다.

저장 경로를 환경변수로 분리하고 임시 디렉터리를 쓰게 했습니다. 경로가 실제를
가리키면 테스트가 먼저 실패합니다.

### 코드에 없던 문제

테스트가 20분 넘게 끝나지 않았습니다. 프로세스를 떠 보니 CPU는 0%인데 시간의
99%를 `read()` 시스템 콜에서 쓰고 있었습니다. 프로젝트가 iCloud로 동기화되는
폴더 안에 있었고 가상환경에 파일이 23,541개 있었습니다. 동기화 밖으로 옮기자
`import chromadb`가 1543초에서 4.5초가 됐습니다.

## 정리

평가를 구현하기 전에는 정상 동작한다고 판단했습니다. 검색 결과가 정확했기 때문입니다.
지표를 측정하기 시작하자 임계값 설정 오류, 파서의 종류 오분류, 실패 원인 분류 오류가
차례로 드러났습니다.

타입 필터 도입 후 지표가 떨어진 것이 파서 오분류를 발견한 계기였습니다. 측정 체계가
없었다면 찾지 못했을 문제입니다.

배포 뒤에 겪은 것들은 성격이 조금 달랐습니다. 느린 이유는 검색이 아니라 추론
토큰이었고, 인덱스가 비는 이유는 배포 환경이 아니라 테스트였고, 임포트가 오래
걸린 이유는 코드가 아니라 파일이 놓인 위치였습니다. 세 번 다 고치기 전에 재는
것이 답을 알려줬습니다. 짐작으로 손댔다면 엉뚱한 곳을 고치고 고쳤다고 믿었을
것입니다.

다음 프로젝트에서는 추출 안정성 지표를 먼저 구현할 계획입니다. 같은 입력을 반복
파싱해 필드별 일치율을 측정하는 방식입니다. `type`과 `time`의 불안정성은 모두
사후에 발견했지만 처음부터 측정 대상이어야 했습니다.
